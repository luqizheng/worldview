# 3. Command 执行失败与用户意图

## 3.1 D01-05：执行条件失效

用户明确选择：

Command 无法执行时，系统发出警告，让用户自己处理。

软件是创作软件，应该帮助作者发现设计中的不合理，而不是擅自解决创作问题。

因此：

- 不自动修改路线。
- 不自动延长时间。
- 不自动改变目标。
- 不自动寻找替代方案并直接执行。
- 不自动改变用户 Command。

## 3.2 D01-06：执行条件恢复

阶段性选择：B。

条件恢复后，系统提示用户原 Command 已经具备继续执行的条件。

必须由用户确认后才能恢复。

不允许自动恢复。

后续关于历史修复和重新重建的规则，进一步明确：用户修复的是历史设计，系统需要重新计算受影响的历史，而不是把修复操作当成新的历史时间事件。

## 3.3 D01-07：历史修改后的旧警告

阶段性选择：B。

保留旧警告记录。

当原异常条件不再成立时：

- 将旧警告标记为已解决。
- 不直接删除警告。
- 保留警告产生原因。
- 保留警告解决原因。

需要区分历史发生时间和软件诊断时间。

## 3.4 D01-08：修改已有 Command

阶段性选择：A。

用户直接修改原 Command。

Command 不需要保留版本，不建立 Command Revision 链。

修改意味着作者修正原有创作内容，不是向世界历史追加一个新的命令。

修改后需要重新计算受影响的派生结果、World State、警告和 Branch。

不保留 Command 内容版本，不代表删除所有诊断记录。

## 3.5 D01-09：父地图 Command 修改与 Branch

阶段性选择：A。

父地图 Command 修改后，自动继承修改并重建所有受影响的 Branch。

如果修改导致 Branch 自己的 Command 无法执行：

- 产生警告。
- 不擅自修改 Branch 自己的 Command。

Branch 是父地图历史的动态继承关系，不是创建时刻的静态历史快照。

## 3.6 D01-10：Branch 后续 Command 执行失败

原始讨论选择 C：

按依赖关系停止，无法执行的 Command 及依赖它的后续 Command 受阻；不依赖它的 Command 可以继续执行。

**后续修正：**

D01-58 和 D01-59 改变了完整历史重建的错误处理方式。

最终阶段性规则是：

- 完整历史重建遇到第一个执行错误，立即停止后续重建。
- 不再继续执行无关的后续 Command。
- 不生成错误位置之后的有效 World State。
- 可以保留失败原因和依赖关系等必要诊断信息。

因此，D01-10 原先的“无依赖 Command 仍可继续执行”不再适用于完整历史重建流程。
