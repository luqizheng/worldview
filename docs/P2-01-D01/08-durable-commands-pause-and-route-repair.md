# 8. 持续 Command、暂停与路线修复

## 8.1 D01-50：暂停时目标对象的状态

阶段性选择：A。

例如军团已经走完一半路线，因为桥梁被摧毁而暂停：

- 保留暂停时最后一个有效位置。
- 军团停留在那里。
- 不回滚到 Command 开始前的位置。
- 不把位置变成未知。
- 恢复后从暂停时的位置和进度继续。

## 8.2 D01-51：单条 Command 遇到执行障碍

阶段性选择：B。

用户强调，必须区分作者明确设计的等待行为与系统擅自补充的等待行为。

情况一：作者明确设计三条 Command：

1. 军团移动到断桥处等待。
2. 军团驻扎，等待桥梁恢复。
3. 军团从驻扎地移动到目标。

系统应按作者明确设计的三条命令执行。

情况二：作者只设计一条从当前位置移动到目标的 Command，但路线遇到断桥。

系统不能擅自解释成：

- 自动停在桥边。
- 自动驻扎。
- 自动等待桥梁恢复。
- 自动继续前进。

正确行为：

- 发现命令无法执行。
- 终止该 Command 的播放。
- 通知用户障碍及原因。
- 等待用户处理。

核心原则：

**系统不能替作者补充没有设计的历史行为。**

## 8.3 D01-52：恢复后原路线失效

阶段性选择：C。

如果等待条件恢复，但原路线已经不可用：

1. 系统重新检查原路线。
2. 原路线失效时，自动计算替代路线作为建议。
3. 向用户展示原路线失效原因和替代路线。
4. 不修改原 Command。
5. 不自动接受替代路线。
6. 用户确认后，才将新路线写入 Command。

允许自动计算建议路线，不允许自动修改用户指定路线或自动恢复执行。

## 8.4 D01-53：撤销原问题

此前曾讨论“路线改变后执行时间如何处理”，但该问题建立在把历史修复误解为现实时间继续推进的前提上。

用户明确纠正：

World View 是设计软件。

用户发现冲突后开始修复，修复完成后，冲突不应继续存在。系统应重新从原历史时间执行新的设计方案。

因此撤销原 D01-53 的 A/B/C 选择题，不保留“105 天确认”这一概念。

正确理解：

- 第 100 天开始执行。
- 第 101 天发现执行冲突。
- 用户修复历史设计。
- 系统从第 100 天重新执行。
- 再次检查整个执行过程。

修复不是追加一个新的历史事件。

## 8.5 D01-54：冲突修复后的后续历史

阶段性选择：A。

用户修复历史冲突后：

- 从最早受影响的历史时间重新执行。
- 自动重新执行所有受影响的后续 Command。
- 根据依赖关系确定执行顺序。
- 无法执行的 Command 产生错误。
- 不擅自修改后续 Command。
- 重新评估受影响的 World State、派生 State Change、警告和 Branch。

## 8.6 D01-55：后续 Command 执行失败后的诊断

阶段性选择：C。

系统提供：

1. 失败信息。
2. 具体失败原因。
3. 相关依赖链。
4. 针对问题的修复建议。
5. 由用户决定是否采用修复建议。

## 8.7 D01-56：修复建议的范围

阶段性选择：A。

修复建议只针对每条失败的 Command 单独提出。

不主动分析整条受影响依赖链并生成一套相互协调的整体修复方案。

但是系统仍需展示依赖链和问题来源。

区分：

- 诊断范围：可以展示完整依赖关系。
- 修复建议范围：只针对当前失败的 Command。

## 8.8 D01-57：修改 Command 后仍然失败

阶段性选择：A。

用户修改 Command 后，即使重新执行仍然失败：

- 保留用户修改后的 Command。
- 标记执行失败。
- 持续显示警告或错误。
- 保留失败原因。
- 允许用户继续编辑其他历史。
- 不自动回滚用户修改。
- 后续修复后重新计算受影响历史。

软件不能擅自撤销作者的创作决定。
