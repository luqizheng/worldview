# 9. 编译器式历史重建

## 9.1 D01-58：执行失败后的时间线处理

阶段性选择：B。

用户明确提出，World View 的历史重建更像编译软件。

基本工作方式：

1. 用户编写历史 Command。
2. 系统按历史时间检查并重建。
3. 发现错误，停止后续重建。
4. 报告错误及原因。
5. 用户修改设计。
6. 系统重新重建。
7. 直到所有 Command 成功执行，得到完整历史结果。

错误之后的历史：

- 不展示为有效的执行结果。
- 即使后续 Command 没有直接依赖失败 Command，也不能将它们的结果作为完整有效历史展示。
- 不删除后续 Command。
- 不代表后续 Command 本身全部有错误。
- 只是当前完整历史重建尚未成功。

## 9.2 D01-59：遇到第一个错误后的检查策略

阶段性选择：B。

一旦遇到第一个无法执行的 Command：

- 立即停止所有后续检查。
- 不继续检查后续 Command。
- 只报告当前第一个错误。
- 用户修复后重新执行。

用户明确表示，不需要建立过于复杂的多错误报告体系。

因此采用简单的 Fail-Fast 方式。

不引入复杂的：

- 并行错误收集。
- 多错误关联。
- 批量错误诊断。
- 整体依赖链自动协调修复。

## 9.3 D01-60：修复后的重建起点

阶段性选择：B。

默认从刚刚修复的错误所在时间开始重建，尽可能复用此前成功的结果。

用户补充：

- 可以拉动播放条选择历史时间点。
- 可以修改某个播放点的内容。
- 修改后重新播放。

需要区分：

**播放起点：** 用户主动选择从哪个历史时间开始观看。

**重建起点：** 系统根据修改影响范围确定必须从哪里重新计算。

用户选择播放起点，不代表系统可以忽略更早的未解决历史错误。

如果更早修改实际影响更早时间，则仍需从实际最早受影响位置重建。

## 9.4 D01-61：播放条遇到历史错误

阶段性选择：A。

播放条只能播放到最近一次成功重建的时间点。

如果第 105 天发生 Command 执行错误：

- 第 105 天之前已成功重建的历史可以播放。
- 第 105 天显示错误。
- 第 105 天之后不能播放未经验证的历史结果。
- 用户修复并重新重建后，播放范围才向后扩展。

播放条展示的是当前已经成功重建的可信历史范围。

## 9.5 D01-62：Command 修改后的重建触发

阶段性选择：B。

用户可以连续修改多条 Command，不立即自动重建。

由用户主动点击“重新播放 / 重建”后，系统统一执行：

1. 确定最早受影响的历史时间。
2. 复用此前仍然有效的结果。
3. 从重建起点开始按顺序执行 Command。
4. 遇到第一个错误立即停止。
5. 展示错误和修复提示。
6. 用户继续修改后，再次主动重建。

## 9.6 D01-63：未重建修改期间的播放

阶段性选择：B。

只要用户修改了 Command，但尚未重新重建：

- 暂停时间线播放。
- 不允许继续播放旧的重建结果。
- 提示用户存在尚未验证的修改。
- 用户主动点击“重新播放 / 重建”后，才恢复播放能力。
- 重建失败则停留在错误位置，等待用户修复。

播放结果必须与当前创作内容保持一致，不能让用户误以为旧结果代表最新设计。

## 9.7 D01-64：重建状态

阶段性选择：A。

界面明确区分三种状态：

| 状态 | 含义 |
|---|---|
| 未重建 | 用户已修改内容，但尚未重新验证 |
| 重建失败 | 已经执行重建，但发现错误并停止 |
| 重建成功 | 当前创作内容已成功完成历史重建 |

三种状态不能混淆：

- 未重建不代表设计有错误。
- 重建失败意味着已经发现具体问题。
- 重建成功意味着当前历史已通过执行检查。
