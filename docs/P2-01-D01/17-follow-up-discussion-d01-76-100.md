## 17.1 D01-76：Shared Object 与 Branch 历史重建关系

阶段性选择：C（分层重建与时间约束结合）。

**后续澄清（用户确认，与选择 C 共同构成本条完整裁决）：**

- 用户一次只激活一条 Branch 时间线。
- Shared Object 不应被理解为一套独立于 Branch Local Command 的权威历史。
- 应按选定 Branch 的继承路径连续执行 Command。
- Shared Object 在该路径重建过程中持续接收 Command 影响。
- 不同 Branch 中同一个 Shared Object 可以具有不同的运行时状态。

**模型修正声明：** 不得继续按"独立 Shared Object History 与 Branch Local History 两套历史交错合成"的模型理解本条——那是错误模型。正确模型为上述继承路径连续重建模型：Shared Object 不是第三套权威历史，共享对象状态在选定 Branch 的继承路径重建过程中形成。D01-70"共享对象身份，不等于跨 Branch 共享运行时修改结果"的原则不变，并由本条澄清进一步具体化。

核心原则：

**按选定 Branch 的继承路径连续重建；同一个 Shared Object 在不同 Branch 中可以具有不同的运行时状态。**

## 17.2 D01-77（重拟）：Checkpoint 继承与复用

**重拟说明：** 本条为重新拟定（重拟）的议题。此前讨论中的旧 D01-77 议题已被撤回，撤回的旧议题内容不构成裁决、不记录于本文档、不得恢复为有效结论。本条以重拟后的议题为准。

阶段性选择：A（逐层复用祖先 Checkpoint）。

以 A→B→C 继承链为例：

1. A 在 1200 年保存 Checkpoint。
2. B 从 A 的 1200 年继承，在 1500 年保存 Checkpoint。
3. C 重建时，先恢复 A@1200。
4. 执行 B 在 1200—1500 年之间的 Command。
5. 恢复 B@1500 Checkpoint。
6. 再执行 C 自己的 Command。

规则：

- Checkpoint 是完整 World State 的派生缓存，不是权威历史。
- Checkpoint 缺失时可以重新构建。

（衔接说明：与 D01-65~69、D01-72 一致——Checkpoint 仍为按 Branch 归属的派生缓存；祖先 Checkpoint 在后代继承路径重建过程中被复用，不改变其归属，也不使其成为权威历史。示例的精确恢复策略见[第 13.7 节](13-known-pending-review-items.md)第 8 项，本文档未自行补充。）

## 17.3 D01-78：活动 Branch 切换

阶段性选择：A。

- 同一时刻只有一条活动 World State。
- 切换 Branch 时，按目标 Branch 的有效 Checkpoint 恢复。
- 从最近有效 Checkpoint 继续执行。
- 其他 Branch 的 Checkpoint 可以保留，但不作为当前活动状态。

## 17.4 D01-79：祖先修改后的 Checkpoint 失效传播

阶段性选择：A。

- 祖先历史修改后，失效所有受影响的祖先及后代 Checkpoint。
- 沿继承路径检查受影响后代。
- 不受影响的历史区间与 Checkpoint 可以保留。
- 后代自己的 Command 不删除、不自动修改。

（衔接说明：与 D01-72"祖先历史修改使受影响 Checkpoint 失效并重新生成"一致；本条补充传播范围与保留边界。失效判定的版本机制见 D01-86~88。）

## 17.5 D01-80：祖先修改导致后代 Command 执行失败

阶段性选择：A。

- 保留后代 Command。
- 重建在失败点停止。
- 报告失败 Command、时间、祖先历史变化及原因。
- 不自动寻找替代路线，不自动补建对象，不修改后代 Command。

（衔接说明：与 D01-71 第 8 条、D01-09 一致，并延续 D01-05"不自动寻找替代方案、不擅自修改 Command"的原则；Fail-Fast 适用。）

## 17.6 D01-81：重建失败与继承阻断的区别

阶段性选择：A。

必须区分：

- **重建失败**：Branch 自己的 Command 执行失败，重建在失败点停止。
- **继承阻断**：Branch 无法取得有效祖先继承状态。

配套规则：

- 祖先修改后，受影响后代标记为待重建。
- 不得使用失效的旧 Checkpoint 作为当前有效状态。
- 祖先修复后沿继承链恢复重建。

## 17.7 D01-82：祖先修复后的自动恢复

阶段性选择：A。

- 先重建发生修改的祖先 Branch。
- 祖先重建成功后自动检查直接后代。
- 后代继承起点有效则启动重建。
- 成功后继续向下传播。
- 后代自身失败则其后代进入继承阻断。

**范围说明（V0.4，衔接 D01-94；V0.4.1 更新交叉引用）：** 本条确立祖先修复后自动恢复沿继承链向下传播的机制；其"立即重建"的执行范围由后续 D01-94 限定为用户当前活动路径，非活动路径切换时按需重建（见 17.19）。两条须合并理解，不得将本条单独解读为"所有后代无论是否活动都立即自动重建"。合并理解的规则关系已经明确（V0.4.1，见[第 13.7 节](13-known-pending-review-items.md)第 7 项）：**自动传播检查机制与实际重建任务的启动范围是两个不同概念**——本条的自动检查与传播沿继承链进行，实际重建任务只对当前活动路径上的后代自动启动，非活动 Branch 保持待重建状态、切换时按需重建；具体任务调度实现仍待技术设计。

## 17.8 D01-83：失败 Branch 对其他 Branch 的影响范围

阶段性选择：A。

- 一个 Branch 失败，只阻断它自己的后代。
- 不影响其他独立 Branch。
- Fail-Fast 约束单条历史重建路径，而不是整个 Branch 树。

## 17.9 D01-84：多 Branch 重建调度

阶段性选择：C。

- 同一继承路径必须按照祖先到后代顺序执行。
- 独立 Branch 可以并行。
- 系统根据资源、任务数量及缓存情况动态选择并行或串行。
- 调度方式不能改变历史语义，串行与并行结果必须一致。

**范围说明（V0.4.1，衔接 D01-94）：** 本条决定**已经具备重建资格的任务如何调度**，不决定重建任务的触发范围：

- 同一继承路径仍必须按照祖先到后代的顺序执行。
- 独立 Branch 在具备重建资格且任务已被触发的前提下，可以并行或串行。
- 系统根据资源、任务数量及缓存情况动态决定调度方式。
- 并行或串行不得改变历史语义，结果必须一致。

**特别强调：本条的并行调度能力，不意味着系统可以绕过 D01-94，主动启动所有已经失效的非活动 Branch。** 重建任务的触发范围由 D01-94 决定（见 17.19）。

## 17.10 D01-85：重建期间祖先 Command 再次修改

阶段性选择：A。

- 旧重建任务立即失效。
- 不允许旧任务发布结果。
- 系统尽快终止不再需要的计算。
- 使用最新历史重新重建。
- 不受影响的独立 Branch 任务可以继续。
- 即使旧任务已经完成计算，只要尚未完成最终版本校验和发布，也必须作废。

## 17.11 D01-86：Branch 继承路径版本

阶段性选择：C。

- 按继承路径维护版本。
- Branch 自己或祖先历史改变，只更新受影响路径版本。
- 不相关独立 Branch 不更新版本。
- 重建任务记录对应路径版本。

## 17.12 D01-87：重建任务版本校验

阶段性选择：C。

- 主动传播版本失效。
- 任务启动时记录完整继承路径版本组合。
- 发布前再次校验完整版本组合。
- 任一相关版本发生变化，旧结果不得发布。
- 最终校验作为主动失效机制的补充防线。

## 17.13 D01-88：Checkpoint 版本有效性

阶段性选择：C。

- Checkpoint 保存生成时完整继承路径版本组合。
- 祖先修改后主动识别并使相关 Checkpoint 失效。
- 读取或使用前再次校验路径版本。
- 不匹配时不得用于恢复当前 World State。
- 不受影响的 Checkpoint 可以继续复用。

## 17.14 D01-89：Checkpoint 数量和保存位置

阶段性选择：A。

- 系统自动管理 Checkpoint 的保存位置与数量。
- 分叉点优先作为候选位置。
- 根据重建成本、访问频率、缓存空间等决定其他保存位置。
- 可以淘汰 Checkpoint。
- 缺失时从有效祖先 Checkpoint 或初始状态重建。

## 17.15 D01-90：祖先 Checkpoint 淘汰策略

阶段性选择：A。

- 允许淘汰祖先 Checkpoint。
- 不因为存在后代就永久保护。
- 多个活跃后代依赖时提高保留优先级。
- 综合后代活跃程度、访问频率、重建成本及缓存空间。
- 淘汰不影响历史权威性。

## 17.16 D01-91：正在使用的 Checkpoint

阶段性选择：A。

- 重建任务读取 Checkpoint 时建立使用引用。
- 有引用期间不能物理淘汰。
- 任务完成、取消或失败后释放引用。
- 所有引用释放后重新评估淘汰。
- 必须处理异常终止，避免引用泄漏。

## 17.17 D01-92：Checkpoint 逻辑失效与物理淘汰

阶段性选择：A。

- 祖先修改后立即逻辑失效。
- 即使仍有任务引用，也不得继续作为有效结果使用。
- 有引用时物理数据暂留。
- 任务取消或停止并释放引用后，再进行物理淘汰。
- 历史有效性与缓存物理生命周期分离。

**衔接说明（V0.4；V0.4.1 更新规则关系表达）：** [第 10 章](10-world-state-cache-and-checkpoint.md) D01-68 规定失效 Checkpoint"立即删除、不保留"，确立于无并发重建任务的场景；本条在存在重建任务引用的场景将物理删除时点延后至引用释放。两条规则的共同不变量完全一致：**失效 Checkpoint 在任何场景下都不得作为有效结果使用。** 两条按 Checkpoint 生命周期不同阶段统一理解，规则关系已经明确（见[第 13.7 节](13-known-pending-review-items.md)第 5 项）：失效即立即逻辑失效，不得用于恢复当前 World State；没有任务引用时立即物理淘汰；仍有任务引用时暂缓物理删除，所有引用释放后物理淘汰；物理数据暂时存在不代表 Checkpoint 仍然有效。具体引用计数、引用释放及异常恢复机制仍待技术设计。本条与 D01-68 原文均未被改写。

## 17.18 D01-93：旧重建任务撤销

阶段性选择：A。

- 旧任务立即失去有效执行资格。
- 不允许发布结果。
- 系统发出取消信号，尽快终止计算。
- 底层无法立即终止时允许短暂清理，但结果必须丢弃。
- 释放 Checkpoint 引用及其他运行资源。

## 17.19 D01-94：全局失效、活动路径优先重建

**条目性质说明：** 本条不是 A/B/C 选择题，而是用户补充并确认的完整机制。

场景：用户当前正在 C Branch，继承路径为 A→B→C，同时存在 A→B→D 或 A→B→C→E 等其他 Branch。

如果 A 的祖先历史发生改变：

1. 立即使所有受影响 Branch 的 Checkpoint 逻辑失效。
2. 只立即重建用户当前活动路径 A→B→C。
3. 非活动 Branch（例如 D、E）不立即重建。
4. 用户切换到 D 或 E 时，才启动目标路径重建。
5. 物理淘汰仍遵守 D01-91、D01-92 的引用保护规则。

核心概括：

**全局失效，活动路径优先重建，非活动路径按需重建。**

**范围说明（V0.4；V0.4.1 更新交叉引用）：** 本条将 D01-82 自动恢复传播的"立即重建"范围限定为当前活动路径。D01-82 与本条按"自动传播检查机制"与"实际重建任务启动范围"两个不同概念合并理解，规则关系已经明确（见 17.7 与[第 13.7 节](13-known-pending-review-items.md)第 7 项）；具体任务调度实现仍待技术设计。

**与 D01-84 的边界（V0.4.1）：** 本条决定重建任务的**触发范围**：

- 祖先历史修改后，所有受影响 Branch 的 Checkpoint 立即逻辑失效。
- 只立即触发当前活动路径的重建。
- 非活动 Branch 不主动启动重建，切换时才按需重建。

已经具备重建资格的任务如何调度由 D01-84 决定（见 17.9）。**D01-84 的并行调度能力，不意味着系统可以绕过本条，主动启动所有已经失效的非活动 Branch。**

## 17.20 D01-95：切换到非活动 Branch

阶段性选择：A。

- 切换后目标 Branch 成为唯一活动 Branch。
- 如果存在有效 Checkpoint，直接恢复。
- 如果不存在有效 Checkpoint，立即启动目标路径重建。
- 按祖先到后代顺序执行。
- 失败时遵守 Fail-Fast 与继承阻断规则。
- 不得将旧 Checkpoint 对应状态作为当前有效状态展示。

## 17.21 D01-96：活动 Branch 重建期间的编辑权限

阶段性选择：A。

- 活动 Branch 正在重建时进入临时重建锁定状态。
- 禁止新增、修改、删除、移动 Command 等历史编辑操作。
- 用户可以查看重建进度和浏览其他页面。
- 重建成功后解除锁定，恢复正常编辑。
- 重建失败后解除计算锁定，进入失败处理阶段。

**阶段区分说明：** 重建执行期间的编辑锁定（本条），与重建失败后的修复权限（D01-97~100）是两个不同阶段，不得混淆。

## 17.22 D01-97：重建失败后的修复模式

阶段性选择：A。

- 允许用户进入修复模式。
- 用户可以查看第一个错误及相关 Command。
- 可以修改、删除、调整自己的 Command。
- 每次修复保存后，根据最新历史触发重建。
- 再次失败时仍按 Fail-Fast 报告第一个错误。
- 不自动修改祖先或其他后代 Branch 的 Command。

（衔接说明：修复模式下"每次修复保存即触发重建"是重建失败状态的确认流程；正常状态下的"连续修改、用户主动触发重建"规则（D01-62）继续适用，状态边界见 17.26.1/17.26.2 与[第 13.7 节](13-known-pending-review-items.md)第 6 项。）

## 17.23 D01-98：失败点之前的 Command 修改范围

阶段性选择：A。

- 允许修改失败 Command 本身。
- 允许修改失败时间点之前的任意 Command。
- 允许删除或调整相关 Command。
- 每次修复保存后重新检查和重建。
- 在历史恢复有效之前，不允许修改失败点之后的 Command。
- 如果修复后错误位置发生变化，以最新重建报告的第一个错误为准。

## 17.24 D01-99：修复期间失败点之后的 Command 编辑权限

阶段性选择：A。

- 严格禁止修改失败点之后的 Command。
- 必须先修复失败点及之前的历史。
- Branch 重建成功、历史恢复有效后，才能继续修改失败点之后的 Command。
- 不采用草稿或待验证 Command 作为绕过限制的方式。

## 17.25 D01-100：继承阻断期间后代 Branch 的修复权限

阶段性选择：A。

场景：

- A 的历史修改导致 B 重建失败。
- C 继承 B，因此无法取得有效继承状态。
- C 自己的 Command 可能没有执行错误。

用户确认：

- C 应保持继承阻断状态。
- C 只允许查看，不允许进入修复模式。
- 不允许修改 C 自己的 Command。
- 必须先修复 B，使 B 恢复有效状态。
- 之后 C 才能恢复正常重建流程。

必须明确区分：

**重建失败**：当前 Branch 自己的 Command 执行失败，可以进入受限修复模式。

**继承阻断**：当前 Branch 无法取得有效祖先状态，只能查看，不能修复自己的 Command。

## 17.26 状态与编辑权限规则总结（D01-64、D01-96~100 确认规则汇总）

本节为已确认规则的汇总，便于后续讨论引用。**本节是已确认规则的汇总，不是新的状态机设计，不得据此擅自推导或补充尚未讨论的其他状态转换、状态名称或权限规则。**

**V0.4.1 整理说明：** 原表将重建结果状态与 Branch 编辑权限混合在同一列中。两者是不同维度——D01-64 明确重建结果状态（未重建 / 重建失败 / 重建成功），D01-96~100 讨论 Branch 当前所处的操作阶段及 Command 编辑权限。现拆分为 17.26.1 与 17.26.2 两个独立部分。本次仅为按维度整理既有规则的表达，不是重新设计状态机，未新增状态转换、状态名称或权限规则。

### 17.26.1 重建结果状态

D01-64 已确认三种重建结果状态，覆盖"当前历史是否完成有效重建"维度：

| 重建结果状态 | 含义 |
|---|---|
| 未重建 | 当前历史尚未完成有效重建 |
| 重建失败 | 重建过程中发生错误，未得到有效完整结果 |
| 重建成功 | 当前历史已完成有效重建 |

（D01-64 原文见 9.7，未改动；本表为其汇总表达，语义一致。不得在这里新增重建状态。）

### 17.26.2 Branch 编辑权限与操作阶段

D01-96 至 D01-100 已确认 Branch 当前所处的操作阶段及对应 Command 编辑权限，覆盖与 17.26.1 不同的维度：

| Branch 操作阶段 | Command 编辑权限 |
|---|---|
| 正常编辑 | 按正常规则编辑 |
| 正在重建 | 暂时禁止历史编辑 |
| 自身重建失败 | 进入受限修复模式，只能修改失败点及之前的 Command |
| 继承阻断 | 只允许查看，不允许修改自己的 Command |
| 修复后重建成功 | 恢复正常编辑权限 |

补充边界（原有，全部保留）：

- 失败点之后的 Command 在重建失败期间禁止修改（D01-99）。
- 继承阻断期间，后代 Branch 连受限修复权限也没有（D01-100）。
- 重建执行期间的编辑锁定与重建失败后的修复权限是两个不同阶段（D01-96）。
- 修复模式下每次保存后触发重新检查和重建（D01-97/98）。
- 不得利用草稿或待验证 Command 绕过失败点之后的编辑限制（D01-99）。

两个维度的关系：17.26.1（D01-64）覆盖重建验证维度，17.26.2（D01-96~100）覆盖 Branch 活动与 Command 编辑权限维度；两表并行使用，不得互相混用，也不得据以推导新状态。
