# 18. Checkpoint 专题（2026-11-19）：继承、有效性、损坏检测、重建调度与应用重启（D01-101 至 D01-143）

本章记录 D01-76~100 落档后的 Checkpoint 专题讨论结论（D01-101~143），编号承接 D01 系列，与既有编号无冲突。

**状态说明：**

- 本章各条均为**用户确认的讨论结论**。本轮讨论未采用 A/B/C 选择题形式，各条以"用户确认"直接记录结论内容，不标注选择字母；这不是记录缺漏，而是本轮议题的记录方式。
- 整体状态为 **Proposed / Discussion**：不是正式架构冻结，不签发 ADR，不构成开发实施授权。
- 本章涉及的完成标记、`md5.txt`、任务持久化等为**已确认的机制方向**；具体文件布局、数据结构与交互细节仍待技术设计（登记于[第 13.8 节](13-known-pending-review-items.md)），不得据此开始代码实施。
- 三个容易混淆的概念职责不同，全程须区分：**原子发布**（D01-114，发布过程要么完整发布、要么不发布）、**完成标记**（D01-141，Checkpoint 写入流程已完成的标志）、**MD5 校验**（D01-142，组成文件的数据完整性检测）。
- 本章只更新本讨论记录，不修改其他项目文件。

## 18.1 D01-101：Checkpoint 基本定位

用户确认：

- Checkpoint 是 World State 的恢复缓存，不是权威历史。
- Command 仍是唯一权威历史数据；Checkpoint 丢失不影响历史数据完整性，可以重新生成。

（衔接说明：与 D01-65/66、D01-72 一致，本轮在 Checkpoint 专题下再次确认该定位；本章全部规则均以该定位为前提。）

## 18.2 D01-102：Checkpoint 唯一性

用户确认：

- 每个 Branch 在每个历史时间点最多有一个 Checkpoint。
- 不存在同一 Branch 同一历史时间点的多份 Checkpoint。

（衔接说明：唯一性是生成任务管理（D01-110）与发布规则（D01-114）的前提约束。）

## 18.3 D01-103：Checkpoint 按 Branch 归属

用户确认：

- Checkpoint 按 Branch 归属。
- 不同 Branch 的 Checkpoint 不得混淆归属。

（衔接说明：与 D01-72 一致。）

## 18.4 D01-104：后代复用祖先分叉点 Checkpoint

用户确认：

- 后代 Branch 可以复用祖先在分叉点的有效 Checkpoint。
- 复用的前提是该 Checkpoint 通过完整继承路径版本校验（D01-106）。

（衔接说明：与 D01-77"逐层复用祖先 Checkpoint"一致，并将其落实为分叉点 Checkpoint 复用规则；不改变 D01-77 原文与示例。）

## 18.5 D01-105：恢复后继续执行自有 Command

用户确认：

- 从 Checkpoint 恢复后，继续执行当前 Branch 自有的 Command。
- Checkpoint 恢复不改变 Command 权威数据，也不改变历史重建语义。

（衔接说明：与 D01-76"按选定 Branch 的继承路径连续执行 Command"、D01-71 动态继承一致。）

## 18.6 D01-106：完整继承路径版本校验

用户确认：

- 使用或恢复 Checkpoint 前，必须检查完整继承路径版本。
- 不能只检查 Checkpoint 自身版本。
- 完整继承路径中任何一环版本不匹配，该 Checkpoint 都不得使用。

（衔接说明：与 D01-88 一致并强化——校验对象是完整继承路径版本组合，不是 Checkpoint 单点版本。）

## 18.7 D01-107：祖先历史变化的失效传播

用户确认：

- 祖先历史变化时，沿继承路径传播失效。
- 受影响路径上的 Checkpoint 逻辑失效，不得再作为有效状态使用。

（衔接说明：与 D01-79/86/87 一致；失效传播针对"历史变化导致的逻辑失效"，与数据损坏（D01-116/117）是两类不同问题。）

## 18.8 D01-108：活动路径优先重建

用户确认：

- 活动路径优先重建。
- 非活动 Branch 按需重建（用户切换到该 Branch 时才启动）。

（衔接说明：与 D01-94"全局失效，活动路径优先重建，非活动路径按需重建"一致；本章后续损坏处理（D01-118/119）沿用同一原则。）

## 18.9 D01-109：创建的唯一性约束

用户确认：

- Checkpoint 的创建受唯一性约束：同一 Branch 同一历史时间点最多生成一个有效 Checkpoint（D01-102）。
- 生成任务的产出不得突破该唯一性约束。

（衔接说明：本条为创建规则的前提，与 D01-102 配套。）

## 18.10 D01-110：同一 Checkpoint 单一有效生成任务

用户确认：

- 同一 Checkpoint 同时只能有一个有效生成任务。
- 不允许两个任务同时生成同一份 Checkpoint。

（衔接说明：与 D01-85"重建期间祖先 Command 再次修改时旧任务立即失效"配套——旧任务失效并释放后，该 Checkpoint 位置才可被新任务使用；任务终止与资源释放见 D01-93。）

## 18.11 D01-111：生成失败不发布

用户确认：

- Checkpoint 生成失败时，不能发布有效 Checkpoint。
- 失败任务不得输出任何可被后续恢复使用的 Checkpoint 数据。

（衔接说明：与 D01-92 的共同不变量一致——未成功生成或已失效的数据都不得作为有效结果使用。）

## 18.12 D01-112：生成中版本变化即失效

用户确认：

- 生成过程中继承路径版本发生变化，旧生成任务立即失效。
- 失效任务不允许发布结果。

（衔接说明：与 D01-85/87/93 一致，将"旧任务立即失效"规则落实到 Checkpoint 生成任务。）

## 18.13 D01-113：发布前完整版本校验

用户确认：

- Checkpoint 发布前，再次检查完整继承路径版本。
- 版本不匹配时不得发布。

（衔接说明：与 D01-87"发布前再次校验完整版本组合"一致，落实到 Checkpoint 发布环节；最终校验是主动失效机制的补充防线（D01-87）。）

## 18.14 D01-114：原子发布与不完整数据

用户确认：

- Checkpoint 发布必须原子完成。
- 不完整数据不能作为有效 Checkpoint 使用。

（衔接说明：原子发布指发布过程的完整性——要么完整发布、要么不发布，不产生"半份"可见 Checkpoint。它与完成标记（D01-141，写入流程完成标志）、MD5 校验（D01-142，数据完整性检测）职责不同，不得混淆。恢复时的数据完整性检查见 D01-115。）

## 18.15 D01-115：恢复前完整性检查

用户确认：

- 恢复 Checkpoint 前，必须检查数据完整性。
- 完整性检查未通过的 Checkpoint 不得用于恢复。

（衔接说明：完整性检查的手段见 D01-140（完成标记检查）与 D01-142（MD5 校验）。）

## 18.16 D01-116：单个损坏只影响自身

用户确认：

- 单个 Checkpoint 损坏只影响自身，不自动连带失效其他 Checkpoint。
- 数据损坏不触发沿继承路径的失效传播。

（衔接说明：必须与历史变化导致的失效传播（D01-79/107）区分：失效传播针对"历史变化使缓存对应版本不再有效"；损坏是单个缓存数据自身的问题，不改变其他 Checkpoint 对应历史区间的有效性。）

## 18.17 D01-117：祖先损坏不连带后代失效

用户确认：

- 祖先 Checkpoint 损坏，不自动导致后代 Checkpoint 失效。
- 后代 Checkpoint 自身数据与版本校验仍然有效时，可继续使用。

（衔接说明：需要祖先状态而祖先 Checkpoint 不可用时，按既有重建规则处理——D01-89：从有效祖先 Checkpoint 或初始状态重建。）

## 18.18 D01-118：活动 Branch 损坏自动恢复

用户确认：

- 活动 Branch 的 Checkpoint 损坏后，系统自动恢复（自动重建该 Checkpoint）。
- 自动恢复不改变 Command 权威数据，也不等同于用户修改历史后的重建流程。

（衔接说明：与 D01-62 不冲突——D01-62 约束"用户修改 Command 后由用户主动触发重建"；损坏自动恢复是缓存自愈，不涉及任何用户修改。活动路径优先原则与 D01-94/108 一致。）

## 18.19 D01-119：非活动 Branch 损坏按需处理

用户确认：

- 非活动 Branch 的 Checkpoint 损坏后，只做逻辑失效，不立即重建。
- 用户切换到该 Branch 时，按需启动重建。

（衔接说明：与 D01-94/95 一致——全局失效、活动路径优先重建、非活动路径按需重建。）

## 18.20 D01-120：不建复杂损坏历史记录

用户确认：

- 不额外建立复杂的损坏历史记录。
- 损坏检测服务于恢复可靠性，不扩展为审计或历史追踪功能。

（衔接说明：与 D01-59"不引入复杂的多错误报告体系"的简化原则精神一致。）

## 18.21 D01-121：通知时机

用户确认：

- 只有当损坏导致恢复失败，或影响用户操作时，才需要通知用户。
- 不为每次损坏检测单独打扰用户。

（衔接说明：与 D01-07 警告规则精神一致——诊断服务于用户需要处理的问题；被自动恢复覆盖的损坏（D01-118）不需通知。）

## 18.22 D01-122：损坏处理小结

用户确认（本条为 D01-115~121 已确认规则的小结性归纳，未引入新机制）：

- Checkpoint 不可用有两类原因：历史失效（逻辑失效，沿继承路径传播，D01-107）与数据损坏（单个发生、不传播，D01-116/117）。
- 两类的处理路径一致：不可用即不得用于恢复；损坏 Checkpoint 的恢复手段是重新创建（活动 Branch 自动恢复，非活动 Branch 按需重建）。
- 损坏与失效都不影响 Command 权威历史，都不改变历史语义。

（衔接说明："需要重新创建"与 D01-141/142 校验失败的处理一致。）

## 18.23 D01-123：不提供单个 Checkpoint 的手动删除

用户确认：

- 用户不能手动删除单个 Checkpoint。
- Checkpoint 的保留与淘汰由系统按既有规则自动管理（D01-89/90），不提供用户手动删除单个 Checkpoint 的操作。

（衔接说明：与 D01-67"由系统自动决定 Checkpoint 位置、不要求用户手动管理"一致。）

## 18.24 D01-124：用户可要求重新创建全部 Checkpoint

用户确认：

- 用户可以要求重新创建全部 Checkpoint。

（衔接说明：与 D01-123 相对——不提供单个删除操作，但提供全部重新创建的入口；批量任务的范围、顺序与锁定见 D01-125~127。）

## 18.25 D01-125：全部重建的覆盖范围

用户确认：

- 全部重新创建覆盖当前 Branch 及完整祖先继承路径。
- 目标范围在任务启动时确定并固定（D01-135）。

（衔接说明：与 D01-77/104 的继承复用结构一致——祖先路径是当前 Branch 重建的依赖基础。）

## 18.26 D01-126：祖先到后代顺序执行

用户确认：

- 批量重建按祖先到后代顺序执行。

（衔接说明：与 D01-84 一致——同一继承路径必须按照祖先到后代顺序执行；本条将其落实到批量重建任务。）

## 18.27 D01-127：批量重建期间的地图级锁定

用户确认：

- 批量重建期间，地图不可操作。
- 该锁定是地图级锁定：批量重建任务执行期间，整个地图进入锁定状态。

（衔接说明：D01-96 的重建锁定针对活动 Branch 的单次重建；本条适用于批量重建场景，锁定范围提升为地图级。两条是不同场景的锁定，互不否定。）

## 18.28 D01-128：批量重建模式一：继续/修复重建

用户确认：

- 支持"继续/修复重建"模式：保留已成功生成的 Checkpoint，从失败或中断位置继续按序重建。

（衔接说明：与 D01-60"尽可能复用此前成功的结果"的原则一致。）

## 18.29 D01-129：批量重建模式二：强制全部重建

用户确认：

- 支持"强制全部重建"模式：对目标范围内全部 Checkpoint 重新生成，不依赖既有 Checkpoint。
- 强制全部重建同样按祖先到后代顺序执行（D01-126），同样受地图级锁定约束（D01-127）。

## 18.30 D01-130：两种模式的边界

用户确认：

- 继续/修复重建与强制全部重建是批量重建任务的两种模式。
- 两种模式都不改变重建的目标范围（D01-125）、祖先到后代顺序（D01-126）与地图级锁定（D01-127），都不改变历史语义。

（衔接说明：模式选择的交互方式未在本轮单独裁决，列入[第 13.8 节](13-known-pending-review-items.md)待技术设计。）

## 18.31 D01-131：批量重建失败的处理

用户确认：

- 批量重建过程中出现失败时，严格沿用已确认裁决：Fail-Fast 停止（D01-58/59）、报告第一个错误及原因（D01-55/58）、失败 Branch 进入受限修复模式、其后代进入继承阻断（D01-81/100）。
- 不因批量场景引入新的失败处理机制。

## 18.32 D01-132：批量任务取消

用户确认：

- 用户可以取消批量重建任务。
- 取消严格沿用 D01-93：任务立即失去有效执行资格、不允许发布结果、发出取消信号尽快终止计算、释放 Checkpoint 引用及其他运行资源。

## 18.33 D01-133：批量任务再次启动

用户确认：

- 批量重建失败或取消后，用户可以再次启动批量重建。
- 再次启动严格沿用已确认裁决：由用户主动触发（D01-62 的主动重建原则），启动时重新确定并固定目标范围（D01-135），按所选模式执行（D01-128~130）。

## 18.34 D01-134：批量重建期间祖先历史再次变化

用户确认：

- 批量重建期间祖先历史再次变化时，严格沿用已确认裁决：旧重建任务立即失效、不允许发布结果（D01-85）；发布前完整版本校验不通过即不得发布（D01-87/113）；失效沿继承路径传播（D01-94/107）。
- 已失效的批量任务不得发布任何结果。

## 18.35 D01-135：批量任务目标范围启动时固定

用户确认：

- 批量重建任务的目标范围在启动时固定。
- 任务执行过程中目标范围不变；祖先历史再次变化按 D01-134 处理（任务失效，而非扩大或改写目标范围）。

## 18.36 D01-136：不得通过切换 Branch 绕过锁定

用户确认：

- 批量重建锁定期间，不允许通过切换到其他 Branch 绕过地图级锁定。
- 该规则不改变正常状态下的 Branch 切换规则（D01-78/95）；锁定解除后，切换规则照常适用。

## 18.37 D01-137：批量任务进度与错误可查看

用户确认：

- 批量重建期间，任务进度、错误信息等可以查看。
- 查看是只读的，不解除地图级锁定（D01-127）。

（衔接说明：与 D01-96"用户可以查看重建进度"一致。）

## 18.38 D01-138：单机应用定位与关闭行为

用户确认：

- World View 是单机应用软件，不是浏览器应用。
- 正常关闭应用或操作系统关机时，安全停止当前重建任务。
- 不要求关机期间继续计算。

（衔接说明："安全停止"的具体行为（终止计算、不发布部分结果、释放引用）与 D01-93 的取消/终止语义一致；细节待技术设计。）

## 18.39 D01-139：轻量级任务持久化与完成标记

用户确认：

- 使用轻量级任务持久化，不引入复杂的恢复日志。
- 每个 Checkpoint 写入完成后，有特定的完成标记。
- 应用启动时检查完成标记。

（衔接说明：完成标记的职责限定见 D01-141；启动时的校验规则见 D01-140。）

## 18.40 D01-140：启动时的校验规则

用户确认：

- 有完成标记的 Checkpoint，仍须通过继承路径版本校验（D01-106）和数据完整性校验（D01-115），才可作为有效 Checkpoint 使用。
- 没有完成标记的 Checkpoint 视为未完成，需要重新创建。

（衔接说明：完成标记只证明"写入流程已完成"，不证明"仍然有效"——有效性由版本校验与完整性校验决定（D01-141）。）

## 18.41 D01-141：完成标记的职责

用户确认：

- 使用完成标记表示 Checkpoint 写入流程已完成。
- 完成标记不能代替继承路径版本校验和数据完整性校验。

（衔接说明：完成标记、原子发布（D01-114）、MD5 校验（D01-142）职责不同：原子发布保证发布过程不产生半份数据；完成标记标志写入流程结束；MD5 检测组成文件是否意外损坏。）

## 18.42 D01-142：MD5 校验

用户确认：

- 使用 `md5.txt` 记录 Checkpoint 所有组成文件的文件名和 MD5 校验值。
- 读取或恢复 Checkpoint 时，重新计算 MD5 并与 `md5.txt` 比较。
- 校验不一致，或校验文件不存在时，该 Checkpoint 不可用，需要重新创建。
- MD5 用于检测意外数据损坏，不作为防恶意篡改机制。

（衔接说明：与 D01-115 恢复前完整性检查、D01-140 启动校验衔接；校验失败的后续处理与损坏处理规则一致（D01-118/119：活动 Branch 自动恢复、非活动 Branch 按需重建）。）

## 18.43 D01-143：Checkpoint 保存内容与边界

用户确认：

**Checkpoint 保存：**

指定 Branch 在指定历史时间点的完整合成 World State。

保存内容必须足以独立恢复该时间点的世界状态，并继续执行后续 Command。

至少包括：

- 地形、地貌等地图状态。
- POI 的身份、位置和当前属性。
- 人物及其他世界对象的当前状态。
- 国境线及区域状态。
- 道路、桥梁等基础设施状态。
- 对象之间的关系，例如所属区域、连接关系。
- Shared Object 在当前 Branch 中的有效状态及局部变化。
- 其他影响后续 Command 执行的世界状态。

特别注意：

**B@1500 不是只保存 B 自己修改的部分，而是保存从 A@1200 继承并执行 B 自有 Command 后形成的完整合成 World State。**

**Checkpoint 不保存：**

- Command。
- State Change。
- Command 执行顺序约束。
- 可重新计算的警告和错误信息。
- 可重新发现的隐式依赖信息。
- UI 状态、面板布局、选中状态等。
- 其他不属于 World State 的数据。

完成标记、MD5 校验信息属于 Checkpoint 完整性管理信息，不属于 World State。

（衔接说明：与 D01-69"保存指定历史时间点的完整 World State"、D01-72"完整合成 World State"一致；B@1500 示例与 D01-71/77 的继承链（A→B）一致。不保存清单与[第 12.1 节](12-unified-architecture-understanding.md)的定位一致：Command 与顺序约束属于创作历史数据而非 World State；警告、错误与隐式依赖是可重建派生信息（D01-11/55）；UI 状态不属于世界状态。完成标记与 MD5 信息是完整性管理信息，同样不属于 World State。）
