# World View — 地图历史与分支模型架构裁决 V1.0

- **文档状态**：Accepted / Frozen
- **版本**：V1.0
- **日期**：2026-11-18
- **适用范围**：地图历史、时间线、State Change、Event、地图分支
- **性质**：架构裁决
- **后续实施依据**：是
- **是否允许实现阶段重新解释本模型**：否；如发现冲突，应提交新的 ADR / 裁决，不得自行改变本模型

---

# 1. 裁决摘要

World View 不采用传统意义上的"世界版本管理系统"，也不采用 Git 式 Merge。

World View 的核心模型是：

> **地图是一条可以随时间持续演进、并允许在任意历史时点产生永久分叉的历史地图。**

地图从一个初始状态开始。

随着时间推进：

- Event 描述发生的事情；
- State Change 描述世界状态发生的变化；
- State Change 改变地图中的地形、国境线、POI、人物、单位等对象状态；
- 用户可以在任意历史时点创建分支；
- 分支继承分叉点之前的完整历史；
- 分叉之后，父地图与分支独立演进；
- 父地图对分叉点以前历史的修改，会被分支继承；
- **分支之间永远不能 Merge**；
- 用户可以自由删除分支，也可以将分支标记为"废弃"。

因此，World View 的历史结构更准确地称为：

> **带分叉能力的历史地图（Branching Historical Map）**

而不是：

> World Version Management / Git-like Version Control。

---

# 2. 核心设计原则

## 2.1 用户是创作者，不是版本管理员

World View 面向：

- 作家；
- 网文作者；
- 游戏制作人员；
- 历史爱好者；
- 世界观创作者。

系统的职责是帮助用户表达和整理世界，而不是要求用户维护复杂的软件工程式版本体系。

因此：

- 不要求用户理解 Git；
- 不要求用户理解 commit / merge / rebase；
- 不要求用户处理版本冲突；
- 不要求用户提交版本；
- 不要求用户管理版本发布流程。

用户只需要理解：

> **世界从这里开始，随着时间变化；如果想走另一条历史，就从这里分叉。**

---

# 3. 初始地图

## 3.1 地图具有一个初始历史状态

例如用户创建：

> **魔法王国 · 公元 1000 年**

并绘制：

- 地形；
- 山脉；
- 河流；
- 国境；
- 城市；
- POI；
- 人物；
- Unit。

这个状态就是该地图的历史起点。

概念结构：

```text
Map
└── Initial State
    ├── Terrain
    ├── Boundaries
    ├── POI
    ├── Characters
    └── Units
```

不要求额外创建一个复杂的 `WorldVersion` 对象。

---

# 4. 世界历史时间

World View 必须区分：

## 4.1 世界历史时间（Valid Time）

表示：

> **这个事情在世界中什么时候发生。**

例如：

```text
1935 年 1 月
红军经过某地
```

或者：

```text
1200 年
王国吞并北方领地
```

这是地图播放和历史演进使用的主要时间。

---

# 5. Event

Event 表示：

> **发生了什么。**

例如：

```text
Event:
魔法大战
```

Event 可以包含：

- 时间；
- 地点；
- 参与者；
- 过程描述；
- 结果；
- 相关 Unit；
- 相关人物；
- 相关地图对象。

Event 的职责是叙事表达。

Event 本身不是地图状态。

---

# 6. State Change

State Change 表示：

> **世界状态发生了什么变化。**

例如：

```text
State Change
1940 年

山脉 → 平地
```

或者：

```text
State Change
1700 年

POI：
「白石城」 → 「圣都」
```

或者：

```text
State Change
1650 年

国境线：
Boundary A → Boundary B
```

或者：

```text
State Change
1200 年

国家：
王国 A → 灭亡
```

---

# 7. Event 与 State Change 的关系

Event 与 State Change 可以关联，但**不是一一对应关系**。

原则：

> **Event = 发生了什么。**

> **State Change = 世界变成什么样。**

## 7.1 Event 可以触发 State Change

例如：

```text
Event
魔法大战

        ↓

State Change
山脉被夷平

        ↓

State Change
国境线发生变化

        ↓

State Change
附近城市名称发生变化
```

一个 Event 可以产生多个 State Change。

---

## 7.2 State Change 不要求必须存在 Event

例如作者只知道：

> 1650 年，这座城市改名。

完全可以只记录：

```text
1650
POI.name = 新名称
```

不要求创建一个：

> "城市改名事件"

如果作者希望描述：

> 国王颁布法令，将城市改名。

再创建 Event 即可。

因此：

**State Change 可以独立存在。**

---

# 8. State Change 的时间模型

State Change 支持两种基本表达。

## 8.1 生效时间

最常见的方式：

```text
1935 → 国境 A
1940 → 国境 B
1950 → 国境 C
```

系统可以推导：

```text
1935–1940 → 国境 A
1940–1950 → 国境 B
1950–∞    → 国境 C
```

用户不需要手动填写每个结束时间。

---

## 8.2 明确有效区间

在需要时，可以直接表达：

```text
1000–1940
山脉
```

```text
1940–∞
平地
```

因此：

> **简单情况使用生效时间；复杂情况允许明确有效区间。**

---

# 9. 地图时间线

地图时间线是地图世界状态随历史时间变化的表达。

例如：

```text
1000
│
├── 王国 A 建立
│
1050
│
├── 北方战争
│
├── 国境线变化
│
1100
│
├── 皇都迁移
│
1200
│
├── 魔法大战
│   ├── 山脉被夷平
│   ├── 国境线改变
│   └── 皇都改名
│
1300
```

地图播放时，系统根据：

> 初始状态 + 时间轴上的 State Change

重建指定历史时点的地图状态。

---

# 10. 地图状态可以发生的变化

State Change 可以影响地图中的各种对象，包括但不限于：

- 地形；
- 山脉；
- 河流；
- 海岸线；
- 国境线；
- 国家；
- POI；
- POI 名称；
- POI 类型；
- 城市状态；
- 人物状态；
- Unit 状态；
- 其他可时间化的世界对象。

因此：

> **地图不是静态图片，而是可以随历史时间演进的世界状态。**

---

# 11. 地图分支

## 11.1 分支的目的

用户可以在任意历史时点停下来：

> "如果从这里开始，历史走另一条路呢？"

例如：

```text
1000 → 1050 → 1100 → 1200
                         │
                         ├── 主线
                         │
                         └── 分支 A
```

分支不是软件工程意义上的开发分支。

它表示：

> **从这个历史时点开始，创作者选择另一条世界历史。**

---

# 12. 分支继承完整历史

分支创建于 1200 年：

```text
主地图：

1000 → 1050 → 1100 → 1200
                         │
                         └── Branch A
```

Branch A 播放时仍然拥有：

```text
1000 → 1050 → 1100 → 1200
```

然后继续：

```text
1200 → 1230 → 1280
```

因此分支的完整历史为：

```text
1000 → 1050 → 1100 → 1200 → 1230 → 1280
```

---

# 13. 分支不复制祖先历史

分支不复制 1200 年以前的所有 Event / State Change。

分支只需要记录：

```yaml
parent_map: map_main
parent_at: 1200
```

概念上：

```text
Branch A
├── parent_map = Main Map
├── parent_at = 1200
└── own history
    ├── 1230
    └── 1280
```

播放 Branch A：

```text
Parent History
1000 → 1200

+

Branch History
1200 → 1230 → 1280
```

---

# 14. 父地图历史修改会传播到分支

这是本模型的明确规则。

例如：

```text
主地图

1000 → 1100 → 1200
                  \
                   Branch A
```

之后用户回到主地图修改 1100 年：

```text
1100
国王 A
↓
国王 B
```

那么 Branch A 播放：

```text
1000 → 1100 → 1200 → 1230
```

时，也看到：

> 1100 年 = 国王 B。

原因：

> **Branch A 的分叉点以前的历史属于父地图。**

分支只从分叉点以后开始拥有自己的独立历史。

---

# 15. 分叉之后完全独立

例如：

```text
                    ┌── 主线
1000 → 1100 → 1200 ┤
                    └── Branch A
```

1200 年之后：

```text
主线：
1200 → 1250 → 1300 → 1350

Branch A：
1200 → 1230 → 1280 → 1400
```

两条历史互不影响。

主线发生什么，不改变 Branch A 的 1200 年以后历史。

Branch A 发生什么，也不改变主线。

---

# 16. 明确禁止 Merge

这是本模型最重要的边界之一。

World View：

> **允许 Branch。**

> **禁止 Merge。**

例如：

```text
1000 → 1100 → 1200
                  │
                  ├── Main → 1250 → 1300
                  │
                  └── Branch → 1230 → 1280
```

不允许：

```text
Main + Branch → Merge
```

因此系统不需要实现：

- Merge；
- Merge Request；
- 冲突检测；
- 冲突解决；
- 三方合并；
- Rebase；
- Cherry-pick；
- Branch reconciliation；
- 合并审批。

---

# 17. 为什么禁止 Merge

World View 的分支代表：

> **不同的创作历史。**

而不是：

> 不同开发人员修改同一个代码库。

例如：

```text
历史 A：
1200 年之后王国统一。

历史 B：
1200 年之后王国灭亡。
```

这两种历史没有"正确合并方式"。

它们本身就是两个不同的故事。

因此：

> **分支的意义就是允许不同历史并存，而不是最终把它们合并。**

---

# 18. 分支的用户管理

用户完全控制自己的分支。

系统不替用户做版本治理。

用户可以：

### 18.1 继续发展

```text
Branch A
1200 → 1230 → 1280 → 1350
```

### 18.2 删除分支

删除：

```text
Branch A
```

其分支独有历史随之删除。

分叉点以前的父历史不受影响。

其他分支不受影响。

---

### 18.3 废弃分支

用户可以标记：

> **废弃**

例如：

```text
Branch A
王国覆灭路线
状态：废弃
```

废弃不是删除。

废弃分支：

- 保留历史；
- 可以查看；
- 可以作为创作参考；
- 默认不作为当前主要历史方向；
- 后续可以恢复继续创作。

---

# 19. Copy Map 与 Branch Map 的区别

必须明确区分两种用户行为。

## 19.1 Copy Map

用户说：

> "复制一张地图。"

目的可能是：

- 备份；
- 尝试新想法；
- 完全独立创作。

Copy 后得到独立地图。

---

## 19.2 Branch Map

用户说：

> "从这个历史点发展另一条历史。"

例如：

```text
1200 年
      ↓
Create Branch
      ↓
另一条历史
```

Branch 继承父地图此前完整历史。

---

# 20. 不建立复杂的"版本管理"概念

World View 不要求用户面对：

- Version 1；
- Version 2；
- Version 3；
- Release；
- Merge；
- Conflict；
- Revision Branch；
- Version Approval。

虽然底层实现可以存在历史节点、变更记录等技术结构，但这些不应成为用户必须理解的产品概念。

用户看到的是：

> **历史**

> **时间**

> **分支**

> **废弃**

> **删除**

---

# 21. 与地图复制 / POI 共享模型的关系

地图之间可以共享 POI 等对象。

例如：

```text
地图 A：王国之乱
地图 B：王国统一
```

两张地图可以引用同一个 POI。

如果用户修改共享 POI：

> 两张地图都看到修改。

如果用户希望其中一张地图独立演进：

> 复制 POI → 得到新的 POI → 原引用删除/替换。

因此不需要复杂的对象版本系统。

---

# 22. 地图局部历史

地图可以对共享对象建立自己的局部历史。

例如共享 POI：

```text
共享历史：
1600 → 白石城
1700 → 圣都
```

地图 B：

```text
地图局部历史：
1650 → 魔法帝都
```

地图 B 可以拥有自己的创作设定，而不会修改共享对象。

地图局部历史：

- 只属于当前地图；
- 不跨地图引用；
- 不建立复杂的同步机制；
- 不参与 Merge。

如果另一张地图也需要相同设定，用户自行复制相关对象/内容。

---

# 23. 地图局部历史与共享历史

最终地图状态可以理解为：

```text
共享对象历史
        ↓
地图局部 State Change
        ↓
指定历史时间
        ↓
最终地图状态
```

地图局部创作可以覆盖共享历史。

系统允许：

> **创作者有意创造与共享历史不同的世界。**

这种差异可以被系统提示或展示，但不能阻止保存。

---

# 24. 设计哲学

World View 的核心原则不是：

> "帮助用户管理版本。"

而是：

> **"帮助用户构建一个随时间变化的世界，并允许他们探索不同的历史。"**

因此：

```text
地图
 ↓
历史
 ↓
变化
 ↓
分叉
 ↓
不同故事
```

比：

```text
版本
 ↓
版本控制
 ↓
合并
 ↓
冲突解决
```

更符合产品定位。

# 25. 示例：四渡赤水

假设作者要复现"四渡赤水"。

单位：

> 中央红军

通过 Unit 的 Track 表达移动。

Event：

> 一渡赤水

> 二渡赤水

> 三渡赤水

> 四渡赤水

Event 描述发生的事情。

Unit 的 Track 描述：

> 红军实际从哪里走到哪里。

地图时间线中的 State Change 描述：

> 在特定历史时间点，地图状态发生了什么变化。

地图播放时：

```text
历史时间
1935-01
     ↓
1935-02
     ↓
1935-03
     ↓
1935-04
```

用户可以看到完整历史过程。

---

# 26. 示例：架空历史分支

作者播放到：

> 1935 年 2 月。

然后产生一个新的历史分支：

```text
真实历史
1935-02
   │
   ├── 原路线
   │     ↓
   │   四渡赤水
   │
   └── 架空路线
         ↓
       红军向另一方向移动
```

架空路线继承此前完整历史。

但从 1935 年 2 月开始：

> Unit、Event、State Change 可以完全不同。

不需要 Merge。

# 31. 最终一句话

> **World View 不是 Git，也不是版本管理器。它是一张可以随时间演进、可以从任意历史时点分叉、并允许不同历史永久并存的创作地图。**

**分支是为了创造另一条历史，不是为了最终合并历史。**
