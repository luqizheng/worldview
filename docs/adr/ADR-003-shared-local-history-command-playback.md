# 1. 裁决摘要

共享对象（例如 Shared POI）拥有自己的历史，同时某张 Map 也可能对该对象进行局部修改。两类历史共同影响地图播放时的对象状态。

用户选择 **C** 作为基本方向：

> **共享对象历史与地图局部历史，按照世界历史时间共同演进。**

经进一步讨论，决定：

> **不采用**复杂的状态覆盖、固定优先级或多结果合成机制。
>
> **采用命令驱动的历史播放模型。**

# 2. 已确认的裁决（A10-01 ~ A10-09）

## A10-01 统一命令执行模型

共享对象历史与 Map-local History 中适用于当前地图的修改，最终组织成**一条连续的命令执行序列**。

播放时，从初始状态开始，按照确定的顺序逐条执行命令，得到**唯一的当前状态**。

不支持同时播放多个分叉结果，也不需要在播放时展示多个互相竞争的最终状态。

## A10-02 共享命令与局部命令的作用范围

1. 对共享 POI 的修改，属于**共享对象历史**。
2. 共享 POI 的修改会**影响所有引用该 POI 的地图**。
3. Map-local 修改属于**当前地图的局部历史**。
4. Map-local 修改**只影响当前地图**，不修改共享 POI 本身，也不传播到其他地图。
5. 播放某张地图时，使用共享历史中适用于该地图的命令，以及该地图自己的局部命令。

## A10-03 命令驱动的播放

用户修改 POI 时，表达为一条命令，例如：

```text
cmd(poiId, nameOfProperty, newName)
```

命令描述**一次具体修改**，而不是直接保存一份新的完整 POI 状态。

播放时按照命令序列逐步执行。

> 注意：命令的实际数据结构、持久化结构及是否需要其他字段，留给后续技术设计（见 §3）。

## A10-04 App 负责默认排序

1. App 应**主动为命令组织默认执行顺序**。
2. **不要求**用户逐条手动指定顺序。
3. App 应依据**历史时间**及**可识别的命令关系**组织执行顺序。
4. 用户可以**自行调整** App 生成的顺序。
5. 用户明确调整的顺序**必须保存为正式数据**，后续播放应遵循该顺序。
6. 新增命令时，App 应重新检查并组织相关命令，但**不得擅自覆盖**用户已经明确指定的顺序。

具体排序算法、用户指定顺序的表达方式及新增命令与既有人工顺序之间的细节，留待后续设计（见 §3）。

## A10-05 异常检测与警告

App 应主动检查可能存在问题的历史命令关系，例如：

- 同一个对象、同一个属性在同一历史时间被重复修改。
- 修改一个尚未创建的对象。
- 修改一个已经删除的对象。
- 删除对象后仍有依赖该对象的命令。
- 其他可能存在逻辑依赖或执行顺序问题的命令组合。

> 以上仅为检查场景示例，**不构成完整检查规则清单**。

## A10-06 警告不阻止播放

1. App 检测到异常时，应产生**警告**。
2. App 可以自动选择一个默认执行顺序。
3. **即使存在警告，也允许继续播放**。
4. 不因异常而强制阻止用户播放历史。
5. **不允许 App 擅自修改、删除或修正用户原始命令**。

## A10-07 警告具有独立生命周期

本次讨论中特别确认的原则：

1. App 发出的警告**不会因为自动排序而消失**。
2. 用户调整命令执行顺序，**也不会自动消除警告**。
3. **播放历史不会消除警告**。
4. 用户调整顺序，只解决执行顺序问题，**不代表原始历史事实已经得到修正**。
5. **只有原始异常条件确实不再成立**，App 才能重新评估相应警告。
6. 警告应**保留其产生原因及历史记录**，不能简单地随排序操作删除。

> **特别表述（2026-11-18 补充确认）**：警告是**对历史数据问题的记录**，不是临时弹窗，也不是执行顺序调整后的自动清除标记。

警告的具体数据结构、状态机、审计机制和重新评估机制留待后续设计（见 §3）。

## A10-08 单线播放（2026-11-18 补充确认）

1. 一次播放只针对**一个** Map 或一个 Branch。
2. 适用的历史命令组织成**一条连续执行序列**。
3. 播放时只有**一个当前状态**。
4. **不支持**同时播放多个 Branch 或多个分叉结果。
5. **Branch 必须先被选定**，之后才重建和播放它自己的历史。

## A10-09 删除后修改：命令执行、对象存在与警告三维独立（2026-11-18 补充确认）

### 场景示例（正式裁决场景）

```text
1100 年：共享 POI 在共享历史中被删除。
1150 年：Map A 的局部历史中存在一条针对该 POI 的名称修改命令。
```

### 裁决一：命令仍然允许执行

- 1150 年的 Map-local 修改命令**不得因为目标对象已经删除而被自动丢弃**。
- 历史播放仍然按照**统一命令执行序列**进行。
- App **不得擅自删除、修改或跳过**这条原始命令。

### 裁决二：不得自动复活对象

- 执行名称修改命令，**不代表重新创建 POI**。
- 已经删除的 POI **不得因为后续属性修改而自动恢复为存在状态**。
- **对象是否存在，必须由创建、删除等明确的状态变化决定**。
- 名称修改与对象重新创建是**两种不同语义**，不能混淆。

### 裁决三：必须产生持续警告

App 应识别以下异常：

```text
对象已删除，却又出现针对该对象的后续修改命令。
```

要求：

- 产生**可追踪的历史质量警告**。
- 警告**不阻断**历史播放。
- **命令排序、命令执行、用户手动调整执行顺序，都不能自动清除**该警告。
- 只有**原始异常条件确实不再成立**时，才能重新评估警告。
- **不得将"命令已经执行"解释为"异常已经解决"**。

### 领域原则：三个维度相互独立

| 维度 | 负责回答的问题 |
| --- | --- |
| **命令执行** | 该命令是否进入并执行于历史播放序列？ |
| **对象存在状态** | 该对象在当前历史时间是否存在？ |
| **历史质量警告** | 历史命令之间是否存在可疑或不一致关系？ |

三者相互独立，**不得将其中一个维度的结果直接推导为另一个维度的结果**：

- 命令允许执行，**不代表**对象自动复活。
- 对象仍然处于删除状态，**不代表**后续命令必须被自动丢弃。
- 警告存在，**不代表**播放必须停止。
- 命令已经执行，**不代表**警告自动消失。

> **边界**：本裁决只规定产品语义。删除后修改命令在重建算法中的具体实现、已删除对象属性数据的保存与呈现、删除/恢复/重新创建的完整状态机，均留待技术设计（§3-11~13）。

## 5.2 发现的张力（只报告，不自行修改）

### T1：A10-05/06/07 与 P2-01 提案默认项 A11/A12 存在语义冲突

- **提案默认（A11/A12，非冻结裁决）**：写入时强制校验——"修改尚未创建/已销毁对象"被**拒绝**（提案 §4.3），destroy 后再变更判为**错误**（A12）。
- **ADR-003 裁决**：同一类关系是**警告级**异常——命令允许存在、允许播放，App 不得修改或删除用户命令（A10-05/06），只有原始异常条件消失才重新评估警告（A10-07）。
- **分析**：若写入时硬拒绝，A10-05 列举的异常命令根本无法存在，警告机制将失去作用对象。因此 A11/A12 需按本裁决调整为：**结构校验**（时间窗、payload 模式）保留写入级；**对象存在性 / 生命周期引用**降级为**警告级检查**。
- **处置**：该调整涉及提案已确认的默认项，**待人工裁定后另行更新**；本次任务未改动 A11/A12 的原文，仅在提案中标注张力（见提案 §4.3、§7-A11/A12）。
- **✅ 解除（V1.2，2026-11-18）**：A10-09 正式裁决"删除后修改"语义——命令允许执行、**不自动复活对象**、持续警告，**命令执行 / 对象存在 / 质量警告三维独立**。据此 A11/A12 已按裁决同步为警告级（提案 §4.3、§7-A11/A12 已更新，修订痕迹保留）。

# 6. 冻结结论

> **共享历史与地图局部历史的修改最终组织成一条命令执行序列，按确定顺序播放出唯一状态。**
>
> **共享命令影响所有引用地图；局部命令只影响当前地图。**
>
> **App 负责默认排序，用户可以调整，用户指定顺序是正式数据；异常只警告、不阻止播放、不自动修正用户命令；警告独立于排序与播放存在，只有原始异常条件消失才能解除。**
>
> **一次播放只针对一个选定的 Map 或 Branch：适用命令组成一条连续序列，只有一个当前状态；不支持同时播放多个分叉结果（A10-08）。**
>
> **命令执行、对象存在状态、历史质量警告三个维度相互独立：命令允许执行不代表对象复活；对象已删除不代表命令被丢弃；警告存在不阻止播放；命令已执行不等于警告消失（A10-09）。**
