# 1. 裁决摘要

> **批量修复支持 Undo / Redo；普通单项修复不提供专门的 Undo；本规则严格限定于批量修复操作层，未经授权不得扩大为通用 Undo / Redo 机制。**

Undo / Redo 栈记录的是**批量修复操作**，不是世界状态版本；本裁决不是版本管理，也不是 Branch Merge（见 §6）。

---

# 2. 适用范围（已确认）

1. **批量修复**支持 Undo / Redo。
2. **普通单项修复**不提供专门的 Undo。
3. **不得**将本规则未经授权扩大为所有 Command、State Change 或普通编辑操作的通用 Undo / Redo 机制。

> 注："批量修复"本身的完整定义不在本裁决范围内（作为既有用户操作概念被引用，见 §8 待设计第 2 项）。

---

# 3. Undo 规则（已确认）

1. 用户可以撤销**最近执行的**批量修复。
2. **不设置时间期限**。
3. 只要没有发生导致撤销冲突的后续修改，用户就可以**随时撤销**。
4. Undo 必须**整体原子执行**：全部成功，或者全部拒绝。
5. 执行前必须**检查后续修改**是否造成冲突。
6. 存在冲突时，**整体拒绝 Undo**，不得覆盖后续修改，并提示用户处理。
7. Undo 成功后，必须**重新验证并重建**受影响的历史。

---

# 4. Redo 规则（已确认）

1. Redo 是对 Undo 的**反向操作**，即恢复原批量修复执行后的状态。
2. Redo **不是创建一次新的修复**。
3. Redo 必须**严格恢复**原批量修复的**操作范围和内容**。
4. Redo 同样必须**整体原子执行**。
5. 执行前必须**检查后续修改**是否造成冲突。
6. 存在冲突时，**整体拒绝 Redo**，不得覆盖后续修改，并提示用户处理。

---

# 5. Undo / Redo 栈规则（已确认）

1. 严格遵循**栈顺序**。
2. 仅允许操作**当前栈顶**记录。
3. **不允许跳过**中间记录，任意选择较早的记录撤销或重做。
4. 用户执行**新的批量修复**后，**清空 Redo 路径**。
5. Undo 与 Redo **共用记录及数量机制**：Undo 有多少，Redo 就有多少。
6. **不得设计两套互不关联的数量和记录体系**。

---

# 6. 本裁决不是什么

| 不是 | 说明 |
| --- | --- |
| 不是 Git 式版本管理 | 不引入 WorldStateVersion / Revision / Commit；栈是操作记录，不是世界状态历史 |
| 不是 Branch Merge | Undo 不合并任何两条历史（ADR-001 §16 禁令不变） |
| 不是通用 Undo / Redo | 仅限批量修复；扩大到 Command / State Change / 普通编辑需另行授权裁决 |
| 不是 App 自动修正 | Undo / Redo 均由**用户主动发起**；ADR-003 A10-06"App 不得擅自修改、删除用户命令"不受影响 |

# 7. 与现有模型的一致性检查结果

## 7.1 一致项

| 对照对象 | 分析 | 结果 |
| --- | --- | --- |
| Baseline §2 / §5 / §39（World State 是计算结果，无版本实体） | Undo 通过修改历史数据集合并重算实现（机制待设计，§8-1），不引入 Version / Revision / Commit 实体 | ✅ 一致（附边界：栈不得演变为世界状态版本体系） |
| ADR-001 §20（底层可有技术结构，不成为用户版本概念） | Undo / Redo 是用户熟悉的编辑操作隐喻；用户不需要理解版本 / 分支 / 合并 | ✅ 一致 |
| ADR-001 §14 / INV-09（父历史修改传播到 Branch） | 对父历史的批量修复 Undo 与任何父历史编辑同语义：分支自然反映变化 | ✅ 一致；"分支存在是否构成 Undo 冲突因素"列入 §8-4（倾向：沿用传播语义，待确认） |
| ADR-001 §16（禁 Merge） | Undo / Redo 不合并任何历史 | ✅ 一致 |
| ADR-002（统一 History）/ HSE-01（确定性） | 被撤销变更的 History 归属不变；重建是纯函数，Undo 后可确定性重算，满足 Undo 规则 7"重建受影响历史" | ✅ 一致 |
| ADR-003 A10-06-5（App 不得擅自修改 / 删除用户命令） | Undo / Redo 是用户主动发起的修正，不是 App 擅自行为；App 不得自动触发 Undo / Redo | ✅ 一致（附边界） |
| ADR-003 A10-07（警告独立生命周期） | Undo / Redo 改变命令集合 → 原始异常条件**真实变化** → 可触发警告重新评估；这不违反 A10-07（其禁止的是排序 / 播放**自动消除**警告，不是条件真实变化后的重评） | ✅ 一致（分析性结论，联动细节见 §8-7） |
| ADR-003 A10-06（警告不阻止播放）vs 本裁决冲突时"整体拒绝" | 两者对象不同：前者是**播放**不被警告阻止；后者是**操作级数据保护**（不得覆盖后续修改），不是播放阻止 | ✅ 无冲突（UI 语义中须区分这两类提示） |
| Baseline §28 / ADR-001 §23（差异不阻止创作与保存） | 拒绝 Undo 保护的是**既有数据不被覆盖**，与"创作不被系统阻止"对象不同 | ✅ 一致 |

## 7.2 报告项（只报告，不改变已确认规则）

**R1 — Undo / Redo 底层机制未裁决。**
从 History 中移除该批变更、追加补偿变更、或其他机制，均未确定。Undo 规则 4（原子）与 Redo 规则 2/3（"不是创建一次新的修复""严格恢复原范围和内容"）**暗示**机制需保留原批量修复记录以便恢复，但这是暗示，不是机制裁决。已列入 §8-1。

**R2 — 领域模型缺少"批量修复"分组概念。**
P2-01 现有模型中没有表达"一次批量修复包含哪些变更"的结构；要识别"最近执行的批量修复"，需要批次标识或等价机制。这是**缺失项，不是冲突项**。已列入 §8-2。

**结论：无与已冻结裁决（ADR-001/002/003）及 Baseline 不变量的直接冲突。**

Baseline 为冻结文档，以下修订建议**待人工批准后**由人工或另行任务并入：

- **建议二**：在 §33（最小核心闭环）/ §34（第一阶段不实现的内容）澄清：批量修复及其 Undo / Redo **不在**最小核心闭环与 Phase 2 引擎范围内，属后续功能层；Historical State Engine 的正确性不依赖它。
- **建议三**：在 §39（明确废弃的旧方向）补充澄清：Undo / Redo **操作栈**不属于被废弃的 World Version / Object Version 方向——操作记录 ≠ 世界状态版本。

实施顺序不变：Domain → Historical Engine → Storage → API → UI；Undo / Redo 属功能层，晚于引擎与测试矩阵。

# 10. 规则摘要（速查表）

| 维度 | 裁决 |
| --- | --- |
| 适用对象 | 仅批量修复；单项修复无专门 Undo；不得扩大为通用机制 |
| Undo 对象 | 最近一次批量修复（栈顶） |
| 时间限制 | 无 |
| 冲突处理 | 原子执行；有冲突整体拒绝、不覆盖后续修改、提示用户 |
| Undo 后动作 | 重新验证并重建受影响历史 |
| Redo 语义 | Undo 的反向操作；严格恢复原修复的范围和内容；不是新的修复 |
| 栈规则 | 严格栈序；仅栈顶；不可跳过；新批量修复清空 Redo 路径；Undo/Redo 共用记录与数量 |
| 本质边界 | 操作记录机制；不是版本管理、不是 Merge、不是通用 Undo、不是 App 自动修正 |

---

# 11. 冻结结论

> **批量修复可以撤销和重做：撤销没有期限，冲突则整体拒绝；重做严格恢复原修复，不是新修复；栈只有栈顶可操作，新修复清空重做路径。Undo / Redo 记录的是操作，不是世界版本——不是版本管理，不是 Merge。**
