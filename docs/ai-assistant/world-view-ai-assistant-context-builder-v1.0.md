# World View — AI Assistant Context Builder

- 文档版本：V1.0
- 日期：2026-11-20
- 状态：产品与技术设计推荐基线；具体检索算法、索引结构、token 预算及供应商差异待工程验证
- 适用范围：World View 单用户、单机桌面软件；用户自行配置 LLM 供应商
- 上位文档：`world-view-ai-assistant-product-architecture-v1.0.md`、`world-view-ai-assistant-single-user-local-first-architecture-v1.1.md`、`world-view-provider-adapter-contract-and-tool-calling-protocol-v1.0.md`、`world-view-internal-tool-catalog-v1.0.md`

## 1. 目的

本文定义 AI Assistant 在调用用户配置的 LLM 之前，如何从本机 World View 数据中选取、整理、标注并交付当前任务所需上下文。

Context Builder 的目标不是把整张地图、全部对象、全部历史或整个世界设定发送给模型，而是为当前任务构建一个范围明确、来源可追溯、状态有效、信息量受控的上下文包（Context Package）。

必须同时满足：

1. **相关性**：提供完成当前任务所需的信息，不以数据量代替相关性。
2. **权威性**：明确区分正式地图数据、正式世界设定、用户当前输入、候选内容、历史资料、外部证据和模型推断。
3. **时效性**：模型使用的地图修订、Branch、时间点、对象状态和设定版本必须明确。
4. **完整性**：不因裁剪而隐藏会改变结论的重要约束、冲突或依赖。
5. **最小化**：仅发送任务必要的数据；默认不上传完整地图或整个本机项目目录。
6. **可追溯**：本机能够记录上下文来源、版本、裁剪决策和实际发送范围，而不必在日志中保存完整敏感正文。
7. **可控性**：用户能够了解和控制哪些本机数据会发送给所配置的模型服务。

## 2. 架构位置与职责边界

```text
User Request + Editor State
          │
          ▼
    AI Assistant
          │ task intent / scope
          ▼
    Context Builder
      ├─ Scope Resolver
      ├─ Local Data Retriever
      ├─ Authority & Freshness Resolver
      ├─ Relevance Ranker
      ├─ Context Assembler
      ├─ Budget Manager
      └─ Provenance Recorder
          │ Context Package
          ▼
       Model Gateway
          │
          ▼
   User-configured LLM
          │
          ▼
 AI Assistant → Tool Gateway → Domain Services
```

### 2.1 Context Builder 负责

- 根据任务意图识别所需上下文类别和范围。
- 从本机领域服务读取地图、对象、图层、几何摘要、世界设定、历史和当前编辑状态。
- 检查对象状态、正式性、Branch 继承路径和版本时效。
- 进行相关性排序、去重、摘要、分块和预算控制。
- 为每段信息附加来源、状态、版本和可信度标签。
- 生成本机 Context Manifest，记录实际纳入和排除的信息范围。
- 在发送前执行数据最小化和用户隐私策略。

### 2.2 Context Builder 不负责

- 不决定地图领域规则或正式数据的合法性；由 Domain Services 负责。
- 不把候选内容提升为正式地图或正式世界设定。
- 不自行推断并改写正式历史。
- 不将检索相关性分数当作事实可信度。
- 不自行扩大用户授权的数据发送范围。
- 不直接向 LLM 发送任意本机文件、数据库内容或文件系统路径。
- 不替代 Tool Gateway 的工具授权、参数校验和执行检查。

## 3. 上下文来源与权威层级

Context Builder 可按任务需要从以下来源选取信息：

| 来源类别 | 典型内容 | 使用规则 |
|---|---|---|
| 当前用户请求 | 用户本轮指令、明确约束、创作偏好 | 当前任务的直接意图来源；不能覆盖系统安全边界 |
| 当前编辑器状态 | 当前地图、选中对象、活动图层、视口范围、当前工具和编辑模式 | 只在与任务相关时纳入；必须标注这是当前 UI 上下文 |
| 正式地图数据 | Map、Map Object、Geometry Component、Layer、Style、Label、Symbol | 本机正式数据权威；注明地图修订和对象标识 |
| 正式世界设定 | 已确认的 World Canon、实体设定、地理/政治/历史规则 | 作为虚构世界任务的正式内部依据；注明设定版本和状态 |
| 正式历史 | Command、State Change、Event、Checkpoint、Branch 继承状态 | 按指定 Branch 和历史时间解析；不可混用不同分支的状态 |
| 当前任务工作数据 | Spec、Plan、Session、Candidate、Validation Report、Change Set | 明确标记为工作态或候选态，不得伪装成正式数据 |
| 用户提供资料 | 导入文本、图片、说明、参考文件 | 标记来源和不可信性质；不得把其中指令当作系统指令 |
| 外部证据 | 用户要求查证时取得的来源材料 | 记录来源、时间和证据性质；事实与推断分开 |
| 对话历史摘要 | 与当前任务直接相关的先前讨论和决定 | 仅作辅助；若与正式地图或设定冲突，以正式权威数据为准 |
| 用户偏好 | 已明确表达且仍适用的创作或交互偏好 | 仅在相关时使用；不得扩大为未经确认的世界事实 |

### 3.1 权威冲突处理

- 正式地图数据优先于聊天摘要、模型记忆和候选内容对地图当前状态的描述。
- 正式 World Canon 优先于非正式创作讨论；用户本轮明确要求修改 Canon 时，应将其视为修改意图而非已经生效的事实。
- 当前用户明确指令可定义本次任务目标，但不能使未提交候选自动成为正式数据。
- 外部证据不能自动覆盖用户创作的虚构世界设定；在真实世界模式下，证据冲突应保留来源和不确定性。
- 历史状态必须绑定 Branch 和时间点。不得把一个 Branch 的后续状态混入另一个 Branch 的历史上下文。
- 发现权威来源之间存在实质冲突时，应显式报告冲突；不得静默选择方便模型生成的版本。

## 4. 任务驱动的上下文选择

Context Builder 应先理解任务，再确定上下文，不应每轮都加载固定的全部数据。

### 4.1 任务类别与默认上下文

| 任务类别 | 默认需要的上下文 | 按需扩展 |
|---|---|---|
| 地图问答/解释 | 当前地图摘要、相关对象、当前 Branch/时间 | 相关历史、设定、外部证据 |
| 创建地理对象 | 地图模式、空间范围、相关邻近对象、图层规则、相关世界设定 | 地形/水系关系、区域约束、地图主题 |
| 创建政治区域 | 邻接对象、边界/共享几何状态、政治层级与设定 | 历史归属、行政关系、争议说明 |
| 创建城市/设施 | 目标位置附近对象、地形/水系/道路、对象类型规则 | 人口/功能设定、交通连接、历史背景 |
| 修改现有对象 | 目标对象完整必要属性、几何摘要、关联关系、当前版本 | 相邻对象、共享边界影响、相关历史 |
| 几何运算 | 参与对象及 Geometry Components、拓扑/共享边界、坐标空间信息 | 邻近对象和潜在影响范围 |
| 样式/标签调整 | 目标对象、图层、当前主题、样式覆盖规则 | 图例和 Layout 使用情况 |
| 地图质量检查 | 指定范围内对象、几何/语义约束、验收标准 | 全图统计或相关历史 |
| Layout/导出 | Layout、Map Frame、导出范围、装饰元素、当前地图状态 | 主题、图例、比例尺和 CRS 能力 |
| 历史查询/分支工作 | Branch、分叉点、适用 Checkpoint、Command/State Change 摘要 | 相关对象在指定时间的状态变化 |
| 世界设定创作 | 正式 Canon 相关条目、用户目标、相关地图对象 | 相关历史、证据、待确认冲突 |

以上是默认检索策略，不是固定字段清单。实际范围由任务意图、用户明确范围和领域依赖共同决定。

### 4.2 范围解析

范围可由以下信息确定，按任务语义组合：

- 用户明确指定的对象、图层、区域、地图或时间段；
- 当前选中的对象和活动图层；
- 当前视口范围；
- 目标对象的父子、邻接、引用和其他语义关系；
- 几何运算涉及的对象及共享边界依赖；
- 当前地图的 Branch、历史时间和修订号；
- 任务验收条件所要求的全局约束。

当前视口只是一个上下文信号，不应默认等于任务的全部空间范围。用户明确要求全图检查时，不得仅检索当前视口。

### 4.3 渐进式检索

采用渐进式检索：

1. 先读取轻量地图/任务摘要和明确目标对象。
2. 判断是否存在关键缺失信息或不确定性。
3. 仅针对缺失部分扩展检索，例如邻近对象、关系、历史或设定。
4. 若仍不足以可靠完成任务，向用户询问关键歧义，或说明无法确认的部分。
5. 不通过无边界扩大检索来掩盖任务定义不清。

## 5. 空间上下文与地图表达

地图是空间数据，不能只靠文本名称检索。

### 5.1 空间检索能力

本机空间检索可使用：

- 对象几何包围范围（Bounding Box / Envelope）；
- 点、线、面及多部件几何类型；
- 相交、包含、邻接、距离和空间连接关系；
- 当前地图逻辑坐标空间及 CRS/单位信息（如适用）；
- 图层和对象类型过滤；
- 共享边界和拓扑引用关系。

具体空间关系判断由本机几何/空间服务执行，不要求 LLM 自行计算或猜测精确拓扑。

### 5.2 几何内容的上下文表示

优先按任务需要选择以下表示，不默认传输全部高精度坐标：

1. **语义摘要**：对象类型、名称、主要属性、所在区域和关系。
2. **空间摘要**：位置范围、面积/长度（仅在单位与参考系统允许时）、方向、邻接对象。
3. **简化几何**：经受控简化的轮廓或路径，用于理解大致形状。
4. **精确几何数据**：仅当任务确实需要精确节点、控制柄或坐标计算，且供应商能力和数据发送策略允许时使用。
5. **局部图像/地图预览**：当视觉空间关系比文本更适合表达时，发送裁剪后的必要区域；标明比例、方向、坐标参考和裁剪范围。

几何简化必须保留任务相关拓扑和关键形状特征；不得把简化结果作为正式几何写回。真实距离、面积和方向只有在坐标参考系统和单位支持时才可作为真实量值表达；虚构地图逻辑单位不得伪装成真实地理测量。

### 5.3 空间上下文完整性

若目标对象依赖共享边界、邻接关系或跨区域拓扑，检索不能只取目标对象本身。必须按操作依赖纳入所有可能受影响的对象或其影响摘要，并在上下文中标注依赖范围。

## 6. 历史、Branch 与时间一致性

所有可能依赖历史的上下文必须带有明确的时间语义。

- 当前地图任务默认使用当前活动 Branch 的当前有效状态。
- 历史查询必须指定目标 Branch 和目标时间；未指定时应依据用户问题澄清，不能猜测。
- 后代 Branch 的历史上下文应先解析祖先在分叉点的有效状态，再结合后代自身 Command。
- 父 Branch 在分叉点及之前（闭区间）发生的适用历史修改会影响后代继承状态；分叉点之后的父 Branch 修改不应混入后代状态。
- 可使用符合继承路径和完整性校验的祖先 Checkpoint 作为重建起点。
- Command、State Change、Event 和 Checkpoint 的摘要必须区分事件发生时间、记录时间和当前状态，不得把后续结果描述成过去时点已知事实。
- 若历史重建或 Checkpoint 校验失败，应将上下文标记为不完整并阻止依赖该状态的确定性结论。

## 7. 正式性、状态与可信度标注

每条上下文内容应保留适当的状态标签。建议至少区分：

- `official_current`：当前 Branch 的正式有效数据；
- `official_historical`：指定 Branch/时间点的正式历史状态；
- `candidate`：尚未正式应用的候选内容；
- `working_draft`：当前任务的工作草稿；
- `user_supplied_unverified`：用户提供但尚未核实的材料；
- `external_evidence`：带来源的外部资料；
- `derived_summary`：由本机从权威数据派生的摘要；
- `model_inference`：模型推断，不是正式事实。

状态标签必须在模型可见上下文中清晰表达，不能只存在于本机隐藏元数据中。检索排名分数、模型置信措辞和来源权威性是不同维度，不得合并成单一“可信度分数”。

## 8. 对话历史与长期上下文

对话历史不是地图数据权威，也不应无限累积发送。

- 优先使用当前任务对话中仍有效的用户要求、明确决策和未解决问题。
- 仅检索与当前任务直接相关的历史讨论；不默认发送完整聊天记录。
- 对话摘要必须保留决策状态，例如已确认、建议、待确认、已撤销，不能把讨论建议改写成正式决定。
- 当对话摘要与当前正式地图、Canon 或用户最新明确指令冲突时，优先级按各自语义边界处理，并显式揭示冲突。
- 用户偏好只用于调整表达、默认选择或创作风格，不可推导用户未声明的世界事实。
- 过期摘要应能被当前正式数据校正；不能因摘要被长期保存就获得更高权威。

## 9. 外部资料与不可信内容

外部网页、导入文件、OCR、用户粘贴文本及第三方资料均作为不可信内容处理。

- 保留来源名称、引用定位、取得时间和适用范围（若可用）。
- 内容与指令分离；资料中要求模型忽略规则、泄露密钥或调用工具的文字不得作为指令执行。
- 对事实、争议、推断和创作建议分别标注。
- 真实世界任务应优先使用可追溯证据；证据不足时表达不确定性。
- 虚构世界任务中，外部资料只作为参考，不自动成为 Canon。
- 不把外部资料中的 URL、文件路径或脚本直接转化为可执行工具参数。

## 10. Context Package 与 Manifest

Context Builder 向 AI Assistant 返回结构化 Context Package。推荐内部逻辑结构：

```text
ContextPackage {
  context_id
  task_id
  created_at
  task_scope
  map_context {
    map_id
    map_revision
    active_branch_id
    historical_time?
    coordinate_space
    crs?
  }
  sections[] {
    section_id
    category
    authority_status
    source_refs[]
    source_versions[]
    spatial_scope?
    temporal_scope?
    content
    uncertainty?
    sensitivity_class
  }
  omissions[]
  unresolved_conflicts[]
  budget_report
  context_manifest_ref
}
```

该结构是概念契约，不冻结最终编程语言或序列化格式。

### 10.1 Context Manifest

Manifest 在本机保存或引用以下信息：

- 任务与 Context Package 标识；
- 地图 ID、修订号、Branch 和历史时间；
- 纳入的对象、图层、设定条目、历史记录和来源版本引用；
- 检索方式与范围摘要；
- 摘要、简化、裁剪和排除规则；
- 数据敏感级别及发送策略结果；
- 实际发送给哪个用户配置的连接/模型；
- 上下文构建时间和相关能力/协议版本。

Manifest 默认记录引用、版本和处理元数据，不要求复制所有原始正文。日志中不得记录 API Key 或不必要的完整敏感上下文。

## 11. Token 与上下文预算管理

Context Builder 应有明确预算管理，但 V1 不应把预算控制做成用户必须理解的复杂配置界面。

- 预算由模型上下文窗口、供应商限制、工具定义占用、系统指令和响应预留共同决定。
- 先保留任务目标、关键约束、目标对象状态、正式设定冲突和必要工具定义，再纳入次要背景。
- 去重重复描述；对大规模对象集合使用本机统计、分组摘要和按需细查。
- 长文本按语义分块，保留来源和段落定位；不得只截取开头导致关键限制丢失。
- 几何数据优先发送任务所需局部或摘要；不能为节省 token 而丢掉关键共享边界依赖。
- 若预算不足，按优先级缩减并记录被省略内容；如果省略内容会影响正确性，应暂停并进一步检索或询问用户。
- 不应把模型供应商的 token 估算当作精确计量；实际用量以供应商返回值为准（若可用）。
- V1 可使用固定的内部预算策略与安全余量，具体数值通过工程测试确定。

## 12. 数据最小化、隐私与用户控制

World View 是单机应用，正式地图数据保存在本机。向用户配置的远端 LLM 发送上下文属于明确的数据出站行为。

1. 默认只发送当前任务必要的数据，不发送完整地图、整个项目目录或无关历史。
2. 不发送本机绝对路径、系统用户名、凭据、API Key、无关个人信息或内部安全日志。
3. 对敏感内容按本机策略过滤、脱敏或要求用户确认；不能仅依赖模型自行忽略。
4. 用户应能够在产品设置中了解当前连接供应商、模型以及上下文发送的基本范围。
5. 对大范围地图、批量对象或含敏感资料的上下文，提供清晰提示，并按风险策略要求确认。
6. 不得为了改善模型效果而暗中扩大数据范围或后台上传地图。
7. 连接配置变化、用户切换模型或供应商时，仍遵循同一最小化策略；不得假设不同供应商具有相同数据处理承诺。
8. 未配置模型或网络不可用时，Context Builder 不应妨碍手工编辑和本机数据操作。

## 13. 上下文时效与地图状态变化

上下文构建后，地图仍可能被用户编辑或被其他本机任务修改。因此 Context Package 必须绑定构建时的地图修订和相关对象版本。

- 只读问答可在必要时标注回答基于的地图修订。
- 任何准备产生正式写入的任务，必须在 Tool Gateway/Domain Services 应用前重新验证地图基准状态。
- 若目标对象、依赖对象、共享边界、Branch 或相关设定版本发生变化，相关候选应标记为 stale，并重新检索、重新验证或请求用户决策。
- 不允许模型依据旧上下文直接覆盖新状态。
- 仅当变化与任务依赖无关且本机校验能够证明安全时，才可继续使用既有候选。
- Context Builder 负责提供基准引用；最终并发和写入正确性由 Tool Gateway 与 Domain Services 保证。

## 14. 失败、降级与恢复

| 情况 | 处理原则 |
|---|---|
| 目标对象不存在 | 告知未找到；可询问是否扩大范围，不猜测对象 ID |
| 检索结果过多 | 缩小范围、分组摘要或要求用户指定区域 |
| 权威来源冲突 | 保留冲突并暂停依赖该冲突的确定性操作 |
| 历史状态无法重建 | 标记上下文不完整，不生成确定性历史结论 |
| 空间参考信息不足 | 不提供虚假的距离/面积/方向，必要时询问或降级为定性描述 |
| 上下文预算不足 | 按优先级裁剪；若关键约束会丢失则停止并说明 |
| 数据脱敏或发送策略拒绝 | 不发送被禁止内容，解释限制并提供本机操作路径 |
| 地图在模型响应期间发生变化 | 写入前复核；过期则 stale，重新构建上下文 |
| 外部资料不可用 | 明确证据缺口，不把推测伪装成查证结果 |
| 模型不支持图片/结构化输入 | 使用已验证的文本/摘要降级；无法保持正确性时停止该任务 |

## 15. V1 实施范围与建议顺序

### 15.1 V1 必须具备

- 当前用户请求、地图、Branch、修订号和编辑器状态的基础上下文；
- 按任务类别选择地图、图层、对象和相关关系；
- 正式数据、候选数据、用户资料和外部证据的明确区分；
- 基础空间范围检索及必要的邻接/关联对象扩展；
- 对象/设定/历史来源引用与版本标注；
- 上下文摘要、去重和基本预算控制；
- Context Manifest 和最小化发送策略；
- 写入前地图状态复核及 stale 处理；
- 无模型时不影响本机手工地图工作。

### 15.2 推荐实施顺序

1. 定义 Context Package、Context Manifest 和 Authority/Status 标签。
2. 实现当前地图、Branch、修订号、选中对象和活动图层上下文。
3. 实现对象/图层/关系的按需检索。
4. 实现空间范围和共享边界依赖检索。
5. 接入 World Canon 与历史状态解析。
6. 实现摘要、分块、去重和预算控制。
7. 实现数据最小化、脱敏和发送前提示策略。
8. 接入 AI Assistant 与 Model Gateway，进行真实供应商兼容测试。
9. 完成 stale、冲突、超预算、权限拒绝和模型降级测试。

## 16. 验收标准

1. 简单任务只携带必要上下文，不默认发送整张地图。
2. 对象修改任务包含目标对象必要属性、几何/关系依赖和版本信息。
3. 共享边界或拓扑相关任务能检索并标明受影响对象。
4. 当前视口不会错误地限制用户明确要求的全图任务。
5. 不同 Branch 和历史时间的状态不会混淆。
6. 候选、草稿、外部资料和正式数据在模型可见内容中有明确标签。
7. 正式世界设定与聊天摘要冲突时，不会将摘要误当作权威 Canon。
8. 用户提供资料和外部资料中的恶意指令不会提升为系统指令或工具授权。
9. 几何简化或文本摘要不会被误当作正式精确几何。
10. 缺少 CRS/单位依据时，不输出虚假的真实距离、面积或方向。
11. Context Manifest 能追溯上下文来源、版本、范围和裁剪结果。
12. 不必要的本机路径、凭据和敏感数据不会发送给模型。
13. 地图状态变化后，旧上下文生成的写操作会被重新验证或标记 stale。
14. 预算不足时不会静默丢弃关键约束并继续执行高影响操作。
15. 模型连接失败时，手工编辑、保存、导入和导出仍正常工作。

## 17. 尚待工程验证

- 本机空间检索引擎及几何简化算法；
- Context Package 的具体类型、序列化和版本兼容方式；
- 各供应商 token 估算、图片输入、上下文窗口和结构化输入能力；
- 上下文预算、摘要粒度和分块策略的具体数值；
- 本地全文/语义检索是否需要独立索引，以及索引重建策略；
- 敏感数据分类、脱敏规则和发送前确认的 UX 细节；
- Context Manifest 的持久化、保留期限和日志策略；
- 历史状态、Checkpoint 与 Branch 解析的性能边界；
- 大地图、超多对象和复杂共享拓扑场景下的性能测试指标。

本文不提前冻结上述工程参数，也不要求 V1 引入独立向量数据库或云端检索服务。优先复用本机权威数据和确定性领域查询能力。

## 18. 与相关文档的关系

- Product Architecture：定义 AI Assistant、本机 Domain Services 和用户交互边界。
- Single-user Local-first Architecture：定义本机数据权威、用户自带 LLM 和隐私边界。
- Provider Integration Architecture：定义模型连接、数据传输和供应商适配。
- Provider Adapter Contract：定义模型请求、响应和工具调用协议。
- Internal Tool Catalog：定义模型可请求的本机地图领域工具。
- Map Generation Specification：定义复杂地图任务的意图、约束和验收条件。
- Map Generation Workflow：定义任务规划、执行、验证和应用流程。
- Generation Session Lifecycle：定义复杂任务工作态生命周期。

**文档结论**：Context Builder 是 AI Assistant 连接本机地图权威数据与用户配置 LLM 的受控上下文边界。V1 应采用任务驱动、渐进检索、来源标注、版本绑定和最小必要发送；不以整图上传、无边界聊天记忆或云端数据副本换取模型便利。
