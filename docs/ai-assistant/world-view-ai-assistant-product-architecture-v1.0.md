## 1. 文档目的与产品定位

World View 的地图制作是产品核心能力。内置 AI Assistant
不是独立于地图编辑器的聊天机器人，也不是仅生成地图图片的图像生成入口，而是用户通过自然语言使用
World View 地图制作能力的主要智能交互入口。

**产品定位：World View 内置 AI Assistant
是能够理解用户意图、规划并执行地图制作任务、检查结果、解释依据，并在必要时请求用户决策的地图创作助手。**

AI Assistant
应支持真实地理、真实历史、架空历史、奇幻世界、科幻世界和原创虚构世界。统一使用
World View
的地图对象、几何、图层、样式、标签、历史和布局能力；不同内容类型采用适合其自身的事实或设定检查依据。

### 1.1 核心产品原则

1.  用户以自然语言描述目标，不必学习专业 GIS、Agent 或地图数据模型术语。
2.  以用户任务为工作单位，不把单次工具调用暴露为主要交互。
3.  AI
    能自主规划和执行明确、低风险的工作；重要歧义、正式设定冲突和高影响变更才请求用户决策。
4.  AI 的结果必须落到 World View
    正式地图领域模型中，而不是只生成一张不可编辑的图片。
5.  LLM 不直接读写数据库；所有正式地图操作通过 World View 内部受控接口和
    Domain Services。
6.  地图数据、正式世界设定和历史状态是权威依据；聊天记录、摘要和检索索引不能取代它们。
7.  真实事实、资料支持、推断、争议和创作内容必须区分。
8.  先保证普通用户体验清晰，再逐步开放复杂专业能力；底层复杂性尽可能由系统承担。

## 2. 架构方向与边界

### 2.1 已确认的总体架构

World View 采用**内置 LLM 的 AI 地图制作应用**。World View 内置 AI
Assistant
是用户主要智能入口，负责理解意图、制定计划、组织执行、检查结果、汇总反馈以及在必要时询问用户。

World View Domain Services
负责确定性的地图业务操作、正式数据管理、业务约束、权限和历史规则。

LLM 不直接访问或修改数据库。AI Assistant 通过 World View 内部工具/API
调用 Domain
Services。生成结果应先经过必要的校验与预览；重要设定或高影响正式变更按规则需要用户确认后应用。

### 2.2 逻辑结构

``` text
User
  |
  v
World View Map Editor + AI Assistant
  |
  +-- Intent Understanding
  +-- Context Assembly
  +-- Task Planning and Execution Control
  +-- Knowledge / Evidence Retrieval
  +-- Result Explanation
  |
  v
World View Internal Tools / APIs
  |
  v
World View Domain Services
  |
  +-- Map Object and Geometry Services
  +-- Layer / Style / Label / Symbol Services
  +-- Topology and Geometry Operations
  +-- World Settings / Canon Services
  +-- History / Branch / State Change Services
  +-- Layout / Export Services
  +-- Validation and Quality Services
  |
  v
Authoritative World View Data
```

以上为逻辑职责关系，不要求每个方框在部署上成为独立服务。

### 2.3 非目标与明确排除项

-   不依赖 Codex、Claude Code、外部 Agent 或 MCP 才能运行地图制作。
-   不把外部 Agent 调度、外部 HTTP/MCP 接入作为核心运行架构。
-   不要求用户理解 Agent、Coordinator、Orchestrator 或多 Agent
    等内部术语。
-   不允许 LLM 绕过 Domain Services 直接修改数据库。
-   不以不可编辑的栅格图片作为唯一地图生成结果。
-   不重新引入已取消的复杂场景模拟领域。

未来可以通过统一模型接口接入云端或本地 LLM。外部 Agent、MCP
或开发者工具若未来支持，只能作为可选扩展，不是产品运行前提。

## 3. 用户交互模式

### 3.1 对话驱动、任务执行、地图结果预览

主要交互由三个相互配合的区域构成：

1.  **对话区域**：用户描述目标、补充条件、提出修改、询问地图内容。
2.  **任务进度区域**：展示 AI
    正在做什么、完成了什么、后续步骤、异常和需要用户处理的事项。
3.  **地图结果区域**：在现有地图画布中直接呈现创建或修改结果，支持检查和继续编辑。

AI 不应只回复"已经完成"，而应让用户能够看到地图实际发生的变化。

AI Assistant 应融入现有地图编辑器，不另建一个要求用户学习的复杂 AI
工作台。

### 3.2 是否先展示计划

采用以下默认规则：

-   普通、明确的小任务：直接执行，不必先展示计划。
-   中大型、多步骤任务：先简要展示计划，但不要求用户逐项批准，随后自动开始。
-   存在重大歧义、重要设定冲突或高影响决策：先询问用户，明确后再执行。
-   执行中发现问题：按影响程度自动处理、局部暂停或停止相关操作。

计划用于提高透明度，不应把用户变成任务调度员。

### 3.3 任务进度呈现

任务进度至少展示：

-   任务目标和当前状态；
-   主要步骤及其状态（待执行、执行中、已完成、受阻、跳过、失败）；
-   当前正在处理的工作；
-   重要结果和异常；
-   是否需要用户参与。

进度百分比只能在系统拥有可信工作量信息时显示。不能仅按步骤数量计算并将估算值伪装成精确完成度。第一版优先展示步骤状态。

### 3.4 用户干预

支持：

-   暂停；
-   继续；
-   修改要求；
-   取消；
-   查看当前已完成结果。

暂停应在当前安全操作完成后阻止启动新的制作步骤。取消任务不等于撤销已正式应用的成果；已完成的安全成果默认保留。需要撤销已应用内容时，使用地图编辑器
Undo/Redo 或相应批量撤销能力。

### 3.5 执行中修改要求

用户可以在任务执行过程中补充或修改要求。AI 应：

1.  接收新要求并判断其意图；
2.  识别受影响的后续步骤；
3.  判断是否影响已完成内容；
4.  更新后续计划；
5.  若会覆盖重要成果或改变正式设定，先请求确认；
6.  在安全范围内继续执行。

不得因为用户修改了要求就擅自大规模重做已完成内容。

### 3.6 异常处理

按影响程度处理三类情况：

-   **可自主修复**：例如普通标签重叠、样式不协调、可确定的几何小错误。AI
    修复并重新检查。
-   **需要用户决定**：例如正式世界设定冲突、重要历史资料存在不同说法、目标对象存在歧义。暂停受影响步骤，解释冲突并提供选项。
-   **必须停止相关操作**：例如数据损坏、影响范围无法确认、无法保证操作安全。停止受影响步骤，保留安全成果并说明原因。

异常应尽量局部化。一个步骤受阻，不应自动导致整个任务失败；其他独立且安全的步骤可以继续。

### 3.7 任务完成摘要

任务完成后展示：

-   已创建的内容；
-   已修改的内容；
-   对既有对象的影响；
-   资料支持、推断、争议和创作内容的区分；
-   质量检查结果；
-   未解决问题和待用户处理事项。

用户可以直接在当前对话中继续修改当前地图，不必重新描述整个世界或地图。

## 4. 意图理解与地图语义识别

### 4.1 统一自然语言意图理解

后台至少识别以下意图类别：

1.  **创建内容**：创建地理、政治、人类活动、军事、注释等地图对象。
2.  **修改内容**：修改几何、属性、关系、样式、标签和图层。
3.  **改变历史状态**：创建历史事件、State
    Change，调整对象在特定时期的状态。
4.  **补充世界设定**：新增或修改世界规则、背景、地理特征等正式设定。
5.  **查询与分析**：查询地图内容、解释空间关系、检查历史变化和设定一致性。
6.  **地图表现与排版**：调整主题、符号、标签、图例、比例尺、Layout
    和导出。

一个任务可以包含多种意图和多个地图操作。例如创建山脉、商路和沿线城镇，并建立适当的空间关系，应作为一个连贯任务处理。

### 4.2 当前编辑器上下文

AI 应能够在权限允许的范围内读取当前任务相关的编辑器上下文：

-   当前地图；
-   当前时间和 Branch；
-   当前选中的对象；
-   当前图层；
-   当前选中的 Geometry Component；
-   当前视口范围；
-   最近相关操作；
-   当前 AI 任务。

用户说"把它向东延伸"时，如果当前明确选中一条河流，应理解为修改该河流几何，而不是要求用户重复对象名称。

### 4.3 对象指代解析优先级

建议按以下顺序解析用户指向的对象：

1.  用户明确指定的对象 ID 或名称；
2.  当前选中的对象；
3.  当前地图上下文中明确指向的对象；
4.  最近对话中已经讨论的对象；
5.  根据名称、位置、类型和语义关系检索的候选对象。

若存在多个同名或无法区分的候选对象，必须展示候选并请求用户确认，不得任意选择。

### 4.4 地图内容与世界设定分离

地图对象和世界设定是不同的正式领域数据，但 AI 可以协同处理。

默认规则：

-   用户明确要求绘制、添加或修改地图：执行地图操作。
-   用户明确要求记录、确立或修改设定：进入世界设定变更流程。
-   用户仅描述背景事实：结合上下文理解，不自动将其转成大规模地图修改或正式设定。
-   用户同时要求建立设定并绘制：协同处理两类操作。
-   AI 提出的新设定默认是候选，不得冒充用户已确认的正式设定。

### 4.5 内容性质标识

至少区分：

-   有资料支持的事实；
-   多来源支持或交叉核验的信息；
-   存在争议的信息；
-   AI 推断；
-   AI 创作；
-   用户已确认的内容。

这些标识用于后台追溯和结果解释。不能把 AI 推断或创作静默提升为事实。

## 5. 地图制作能力范围

### 5.1 总体原则

AI Assistant 的目标能力范围覆盖 World View
地图编辑器向用户开放的地图制作能力。AI
不应只会生成轮廓图片，还应能持续编辑真实的地图对象和数据。

能力范围不等于第一版必须一次实现所有高级功能。应依据 Domain Services
的成熟度分阶段开放。

### 5.2 能力领域

1.  **地图对象创建**：地理对象、政治对象、人类活动与基础设施对象、军事对象、注释对象。
2.  **几何创建与编辑**：点、线、区域、多部件几何、孔洞、直线段、贝塞尔曲线、节点和控制柄编辑。
3.  **几何运算**：Union、Difference、Intersection、Split
    等；遵循非破坏性预览、验证和明确应用规则。
4.  **对象属性和关系**：名称、语义属性、对象间关系、行政归属、政治关系、军事信息等。
5.  **图层管理**：创建、删除、重命名、分组、排序、显隐、锁定、透明度和对象移动。
6.  **样式管理**：系统默认样式、地图主题、对象样式覆盖；样式与语义身份分离。
7.  **标签和符号**：自动标签、手动标签、位置和优先级调整、符号库使用及冲突处理。
8.  **历史与 Branch**：查询历史状态、创建历史事件和 State
    Change、按既定规则创建 Branch；复杂历史重建交由历史服务。
9.  **Layout
    与导出**：创建布局、添加地图制图元素、调整页面和地图范围、预览和导出。
10. **质量检查**：几何、空间、拓扑、语义、制图表现和内容一致性检查。

### 5.3 第一版优先范围

第一版优先打通可实际完成地图制作的闭环：

-   自然语言创建地图对象；
-   自然语言修改对象几何和属性；
-   图层、样式和标签管理；
-   多步骤地图制作任务；
-   地图上下文理解；
-   基础质量检查和可确定问题的自动修复；
-   用户暂停、继续、修改要求、取消和确认；
-   基础历史时间与 Branch 操作；
-   结果预览和摘要。

复杂共享拓扑编辑、复杂历史重建、专业军事符号标准、高级 Layout
自动排版等，可在基础能力成熟后逐步开放。

## 6. 操作权限、确认与安全

### 6.1 风险驱动的确认原则

是否询问用户，取决于操作影响范围、可逆性、语义重要程度和用户授权范围，而不是操作数量。

默认处理建议：

  操作                          默认规则
  ----------------------------- --------------------------------------------------------
  创建普通地图对象              信息充分且权限允许时自动执行
  修改普通属性和样式            自动执行
  修改几何                      可自动执行；影响共享边界或重要对象时先检查并按风险确认
  批量修改                      执行前说明影响范围；高影响变更请求确认
  删除对象                      检查关联关系；重要关联或不可恢复风险时询问
  修改共享边界                  检查全部引用对象；重大影响时询问
  改变正式世界设定              需要用户确认
  创建历史事件和 State Change   遵循正式历史规则及确认策略
  修改既有历史记录              必须经过专门的历史变更保护机制
  导出地图                      用户明确提出导出要求后执行

用户对某类操作的明确授权可以降低重复询问，但不能绕过系统权限、数据校验和正式历史规则。

### 6.2 正式操作边界

AI 可以提出操作计划，但 Domain Services 必须负责：

-   身份和权限校验；
-   目标对象当前状态检查；
-   几何和拓扑有效性检查；
-   共享资源影响分析；
-   语义关系和领域约束检查；
-   历史 Command、State Change、Branch 规则；
-   正式数据写入和审计。

AI 不能自行假设操作成功；应依据服务返回结果更新任务状态和向用户报告。

### 6.3 几何操作与对象操作区分

必须遵循既定地图领域规则：

-   几何操作改变 Geometry Components 的形状，不自动改变 Map Object
    身份。
-   对象操作负责对象身份、数量和语义关系变化。
-   几何拆分不自动创建新语义对象。
-   几何合并不自动合并语义对象。
-   将一个国家拆为两个国家属于对象身份和政治关系变化，不能仅执行几何
    Split 代替。

## 7. 知识来源与资料依据

### 7.1 两类主要依据

-   **外部资料依据**：用于真实地理、历史、现实政治和其他现实世界事实。
-   **世界内部设定依据**：用于奇幻、科幻、架空历史和原创虚构世界。

同一地图允许混合现实与虚构内容。内容模式不是封闭类型，检查策略应按对象和内容分别适用。

### 7.2 支持的知识来源

1.  World View
    内置模型知识：用于辅助理解和提出检索线索，不应单独作为重要事实的充分依据。
2.  外部公开资料：地理、历史、政治、文化和专业资料。
3.  用户导入资料：文献、图片、扫描地图、结构化清单、GIS 数据和设定文档。
4.  当前地图数据：现有对象、属性、空间关系和历史状态。
5.  World Canon：用户正式确立的虚构世界设定。

### 7.3 资料适用性评估

不建议用单一数字评分代替判断。AI 应至少考虑：

-   来源可靠性：机构、作者、数据集及其专业性；
-   时间适用性：资料对应的时期是否匹配当前地图时间；
-   空间适用性：覆盖范围、精度和空间参考是否合适；
-   内容一致性：与其他可信资料和现有正式设定是否冲突。

资料可信不代表它适用于所有问题。例如，现代行政边界数据不能直接作为古代政治边界依据。

### 7.4 冲突处理

当资料或设定相互矛盾时：

1.  识别冲突的具体内容；
2.  比较来源、时间和空间适用性；
3.  尝试通过进一步检索或用户资料解决；
4.  仍有争议时明确展示不同说法；
5.  请求用户选择，或将内容保留为未确定状态。

AI 不得静默掩盖重要争议，也不得为了完成地图而编造确定结论。

### 7.5 来源追溯

地图对象及重要属性应能关联其来源依据，包括：

-   来源资料或数据集；
-   使用的具体信息；
-   资料支持、推断、争议或创作性质；
-   用户是否确认；
-   适用时间或历史时期。

来源关联应与 Map Object
身份分离。对象几何或名称变化不应自动丢失来源记录。

普通用户不必在创建每个对象时手工填写来源；系统应尽可能由 AI
和领域服务维护。

### 7.6 用户导入资料

用户可以直接导入文档、图片、扫描地图、结构化数据和支持的 GIS 文件。AI
负责识别类型、提取信息、识别时间与空间范围、发现冲突，并建立来源关联。

扫描地图的地名和边界识别结果不能自动视为精确空间数据。坐标配准、比例、投影和原图绘制误差应纳入质量检查。

### 7.7 幻想与原创世界

虚构世界不需要符合现实自然规律，但应符合用户正式确立的内部规则。漂浮大陆、地下海洋、魔法河流和人工山脉均可成为有效内容。

AI 检查依据：

  内容类型       主要依据
  -------------- ----------------------------------
  真实地理       现实地理资料
  真实历史       历史资料及当时地理环境
  架空历史       真实历史背景与用户确立的架空变化
  奇幻世界       用户正式设定与内部规则
  科幻世界       用户确立的科技和世界规则
  原创虚构世界   用户正式设定及内部一致性

## 8. 长期上下文与记忆

### 8.1 四类上下文

1.  **当前地图上下文**：地图对象、图层、几何、属性、样式、时间和
    Branch。
2.  **世界知识上下文**：正式世界设定、地理规则、历史背景、政治关系等。
3.  **创作对话上下文**：近期对话、当前任务、补充要求和未确认讨论。
4.  **用户创作偏好**：地图风格、详细程度、命名习惯、事实准确性要求和工作偏好。

当前任务的明确要求优先于一般用户偏好。

### 8.2 权威依据优先级

AI 需要结合对象、时间和 Branch 的有效性判断。总体原则：

1.  当前有效的正式地图数据和历史状态；
2.  当前有效的正式世界设定；
3.  用户在当前任务中明确提出的新要求（作为待执行意图，不自动绕过正式变更流程）；
4.  已确认的用户长期创作偏好；
5.  近期对话和未确认讨论；
6.  AI 根据现有信息作出的推断。

聊天记录不能覆盖正式数据；摘要和索引不能成为新的权威来源。

### 8.3 记忆内容范围

长期保留对后续创作有持续影响的信息：

-   正式世界设定；
-   已确认的地图地理规则；
-   用户明确要求长期遵循的创作偏好；
-   当前未完成任务的必要状态；
-   正式地图对象和关系由地图领域数据保存，不复制成另一套事实记忆。

近期对话可暂时保留。普通闲聊不必永久保存。未确认的 AI
创作建议应保持候选状态。

### 8.4 按需读取

不应每次对话都把整个世界加载进 LLM
上下文。根据任务读取相关地图对象、关系、设定和来源。

例如修改某王国边境时，读取该王国、相邻对象、边界资源、相关设定和适用历史状态即可；全世界一致性检查才扩大读取范围。

### 8.5 摘要和索引

正式数据变化后，系统应更新相关摘要、检索索引和上下文缓存。它们是可重建的辅助数据，不是正式地图或世界设定的替代品，也不得反向覆盖正式数据。

### 8.6 地图和 Branch 隔离

-   地图上下文默认限定在当前地图。
-   Branch 上下文遵循既定历史继承规则。
-   不同世界默认隔离。
-   跨地图引用或导入必须由用户明确要求或通过明确的产品关系建立。
-   用户偏好可跨地图使用，但不能替代当前地图正式设定。
-   后代 Branch
    应取得祖先在分叉点的有效状态，再应用自身历史变化；不能错误使用祖先
    Branch 当前最新状态。
-   不采用 Git 式 Branch Merge。

### 8.7 用户纠正和查看

用户可通过自然语言表达：

-   某项设定以后都要遵守；
-   某项旧设定已经废弃；
-   某个内容只是想法，不是正式设定；
-   某类地图创作应长期遵循某种偏好。

AI 应将其路由到对应的偏好或正式设定流程。用户询问当前正式设定时，AI
应能汇总并提供查看入口。正式设定修改仍遵循正式变更机制。

## 9. 质量保证与结果验证

AI 生成结果必须经过适用的质量检查。至少包括：

1.  **Geometry**：几何有效性、闭合、自相交、孔洞和曲线数据完整性。
2.  **Spatial**：空间位置、包含、相交、邻接和范围关系。
3.  **Topology**：共享边界、拓扑约束和引用对象影响。
4.  **Semantic**：对象类型、必要属性和语义关系。
5.  **Cartographic**：符号、标签、视觉层级、遮挡和可读性。
6.  **Specification Compliance**：是否符合用户任务要求。
7.  **Content
    Consistency**：现实地理事实、历史事实或虚构世界内部规则的一致性。
8.  **Evidence Traceability**：重要事实和推断是否有可追溯依据。

AI
可以自动修复确定性、低风险问题。对于存在多种合理解释或涉及正式设定的事项，应请求用户决策。

质量检查不能把幻想世界强制套用现实自然规律；检查规则必须依据当前内容模式和正式设定。

## 10. 任务生命周期与状态建议

任务生命周期的产品状态建议如下（具体状态机可在技术设计阶段细化）：

``` text
Received
  -> Understanding
  -> Planning
  -> AwaitingUserDecision (when necessary)
  -> Executing
  -> Validating
  -> Applying (when formal application is required)
  -> Completed

Executing / Validating may also lead to:
  -> Paused
  -> Blocked
  -> PartiallyCompleted
  -> Failed
  -> Cancelled
```

需要区分：

-   AI 计划中的步骤；
-   已执行但尚未正式应用的候选结果；
-   已经正式应用的地图变更；
-   任务本身的完成状态。

任务取消不能隐式撤销已经正式应用的地图变更。任务、地图编辑器 Undo/Redo
和正式历史 Command / State Change 是不同层次，应协调但不能混为一谈。

## 11. 技术实现建议与待细化项

以下是建议的实现方向，不代表所有细节已冻结：

### 11.1 任务规划和执行

由一个对用户统一呈现的内置 AI Assistant
负责分阶段处理复杂任务。后台可以按需要并行请求模型或执行独立步骤，但不要求多
Agent 成为产品前提，也不向用户暴露多个 Agent。

### 11.2 内部工具接口

为地图对象、几何、图层、样式、标签、世界设定、历史、Layout、导出和质量检查提供类型明确、权限受控、可验证的内部工具/API。

每项写操作应具备明确输入约束、前置状态检查、结果结构和错误语义。需要时支持幂等键、操作关联
ID、审计信息和任务取消检查。

### 11.3 变更预览与应用

对重要或高影响变更，支持候选结果、影响范围预览、验证报告和用户确认。普通低风险操作可按授权直接执行。预览或取消不得意外写入正式数据。

### 11.4 可靠性

建议支持任务步骤记录、失败重试策略、幂等执行、局部恢复、进度事件和操作审计。重试不能造成重复创建对象或重复应用历史变化。

### 11.5 模型接口

通过统一模型适配层支持云端或本地
LLM。模型本身不是正式数据权威；模型输出必须经过工具参数校验、领域服务校验和结果验证。

### 11.6 待后续专项设计

-   内部工具/API 的具体清单、参数和错误契约；
-   任务持久化模型与完整状态机；
-   任务并发、锁定和冲突处理；
-   模型路由、上下文预算和成本控制；
-   外部资料检索、导入解析和来源数据模型；
-   用户授权策略的具体配置和审计；
-   AI 候选变更、预览、正式应用的事务边界；
-   任务级撤销与地图编辑器 Undo/Redo 的协调；
-   失败恢复、幂等和长任务恢复机制。

## 12. 第一版范围与演进路线

### 12.1 第一版必须形成的闭环

1.  用户自然语言提出地图制作任务；
2.  AI 识别意图和当前地图上下文；
3.  对多步骤任务生成简明计划；
4.  调用内部工具和 Domain Services 创建或修改地图对象；
5.  执行必要的几何、语义和制图检查；
6.  展示地图变化和任务摘要；
7.  支持用户暂停、继续、修改要求和取消；
8.  对重要歧义、正式设定和高影响操作请求确认；
9.  保留必要的资料来源与推断标识；
10. 能在后续对话中继续当前地图工作。

### 12.2 后续增强

-   更复杂的共享拓扑和几何操作；
-   更完整的历史事件与 Branch 创作辅助；
-   高级 Layout 自动排版；
-   专业军事符号与专题地图能力；
-   更丰富的资料导入、地理配准和证据交叉核验；
-   跨地图引用和更成熟的长期创作上下文；
-   可配置的用户授权和自动化策略。

    和历史领域的专项规范。
