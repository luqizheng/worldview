# World View AI Assistant — Unified Logical Database Schema V1.16

- Version: 1.16
- Date: 2026-11-21
- Status: Integrated logical schema baseline — Core Domain P2-09 key/ownership integration aligned; physical DDL and provider proof still pending
- Storage target: SQLite, single-user, local-first desktop application
- Supersedes for design purposes: V1.14 integrated SQLite prototype
- Does not supersede: V1.14 historical test artifact or source schema drafts

## 1. Purpose and status

V1.16 reconciles the AI Assistant logical schema with the Core Domain P2-09 ownership, key, History, Calendar, Object Reservation, Asset and transaction contracts.

The redesign is driven by these conclusions:
1. The Core Domain is the only authority for formal Map, Branch, History, Command, Object identity, World State and Checkpoint data.
2. The formal application model is Command-oriented, not CRUD-oriented.
3. Human authorization applies to one exact immutable proposal version and target context.
4. Command submission, later author edits, history reconstruction and playback are separate lifecycle concerns.

This document defines the AI Assistant's logical tables and their responsibilities. It intentionally does not provide executable SQL or guessed Core Domain foreign keys. Core Domain P2-09 V0.7 now provides the detailed relational proposal; it is not yet executable DDL, and the shared-provider transaction boundary still requires the P2-09-12 proof tests.

V1.14 remains a historical SQLite prototype. It must not be used unchanged as an implementation baseline.

## 2. Global persistence principles

### 2.1 Ownership

AI Assistant owns:
- Task, Plan, Step, Tool Call, Operation and Task Log;
- Candidate Sets, Candidates and Candidate Versions;
- Validation Reports and immutable validation evidence;
- Selection Snapshots and Selection Items;
- Command Proposal/Change Set versions;
- human authorization evidence for AI-generated proposals;
- submission attempts, reconciliation evidence and submission reports.

Core Domain exclusively owns:
- Project, Map, Calendar and Calendar Configuration; Object identity and Object ID reservation;
- Branch, History and formal Commands;
- Events, deterministic runtime State Change generation and dependency/ordering semantics;
- Initial State and formal map data;
- World State reconstruction and playback boundary;
- Checkpoints.

### 2.2 No shadow domain entities

Do not create AI-owned tables for:
- `maps`, `branches`, `histories`, `commands`, `events`, `state_changes`;
- `object_versions`, `branch_revisions`, `branch_object_states`;
- `world_states`, `checkpoints`;
- authoritative command dependencies or ordering graphs.

AI tables may store stable Core Domain references, enforced FKs only for permanent Core identities, and immutable context evidence; they never own or duplicate the referenced Core facts.

### 2.3 ID and time conventions

- AI-owned primary keys: UUID text, generated by a maintained library.
- Core Domain entity references use canonical UUID text where a stable entity key is required. Reference lifecycle determines whether a reference is an enforced FK or immutable opaque evidence; do not force FKs to deletable Core entities.
- Transaction timestamps: UTC integer milliseconds.
- Historical Time: AI proposals carry the canonical Core Domain precision interval (Map-relative integer day/offset boundaries). Do not encode it as a UTC timestamp or independently recalculate Calendar dates.
- JSON: use only for variable payloads, immutable snapshots and manifests. Relational links remain relational within the AI-owned schema.
- Foreign keys: enforce AI-owned relationships. Add Core FKs only for permanent Core identities (Object identity, Object Reservation and retained published Asset); keep deletable target Map/Branch/History and returned Command references as opaque UUID evidence.
- Deletion: preserve immutable evidence; use lifecycle state and retention rules rather than cascading deletion of completed work.

### 2.4 Core Domain reference and asset lifecycle policy

| Reference | Representation | Persistence rule |
|---|---|---|
| Map / Branch / History target | UUID text | Opaque immutable target evidence; Core Domain validates current existence/lifecycle at preflight. No restrictive FK that blocks Core lifecycle. |
| Object identity | UUID text | FK to retained `core_object`; draft/active/abandoned/retired identity rows are retained, not physically deleted. |
| Object ID reservation | UUID text | FK to permanent `core_object_id_reservation`; reservation evidence is never deleted or recycled. |
| Published Core Asset | UUID text | FK to `core_asset`; Core Asset metadata/bytes are not garbage-collected while referenced. |
| Candidate staging Asset | hash + AI-owned staging locator/manifest | AI-owned staging evidence, not a Core Asset FK until published. |
| Submitted Core Command | UUID text | Opaque immutable evidence, not an FK; Commands may later be edited/deleted. |
| History context / effective Object context / lineage | opaque token/hash | Preconditions only; never Object Version, Branch Revision or World State Version entities. |

Never cascade-delete AI evidence from a Core lifecycle operation. AI repositories do not write Core tables; Core Domain services do not write AI tables.

## 3. Logical table inventory

V1.16 retains the Task, Candidate, Validation and Selection foundations and integrates the post-Selection submission group with Core Domain P2-09.

### 3.1 Task execution — retain

| Table | Responsibility | Key rules |
|---|---|---|
| `tasks` | One user-requested AI task | Owns task lifecycle and current contract/plan pointers |
| `task_contract_versions` | Immutable task goal/scope/acceptance/authorization/budget snapshots | New semantic contract means new version; baseline-changing updates require human approval |
| `task_plan_versions` | Versioned execution plan | Activated plan versions and their steps are immutable |
| `task_steps` | Ordered sequential execution steps | No DAG; step order is explicit and simple |
| `tool_calls` | Invocation records against static Tool Contracts | Tool identity/version and input/output evidence are retained |
| `task_operations` | Durable side-effect records and Undo/recovery state | Stable operation identity; persist recovery data before side effects |
| `task_logs` | Operational and diagnostic history | Append-only |
| `human_intervention_requests` | User decisions required to continue | Captures question, context, options and response |
| `task_delivery_records` | Immutable delivery manifest for Candidate outputs | Completion means candidate delivery, not formal map submission |

The Task Execution group remains subject to the existing Task Undo, cancellation write barrier, crash recovery and Recovery Required rules.

### 3.2 Candidate and validation — retain with reference correction

| Table | Responsibility | V1.16 treatment |
|---|---|---|
| `candidate_sets` | Alternative generated result sets | Retain |
| `object_candidates` | Stable candidate identity within a set | Retain; `object_id` is an opaque Core Domain identity reference when bound |
| `object_candidate_versions` | Immutable candidate payload snapshots | Retain; bind each version to exact payload/assets and source provenance |
| `candidate_edit_records` | Source-to-result candidate edit evidence | Retain, immutable |
| `validation_reports` | One validation execution and result summary | Retain, immutable after finalization |
| `validation_report_items` | Exact Candidate Versions covered by a report | Retain, immutable |
| `validation_issues` | Error/Warning/Info findings | Retain, immutable |

**Reference correction:** V1.14's `base_object_version_ref` must not imply a Core Domain Object Version entity. Replace it with `base_effective_object_context_ref`, an opaque precondition reference supplied by Core Domain for the Object's effective context in the selected target Branch, if that check is needed.

Candidate Version is an AI-owned immutable candidate snapshot. It is not a formal Object Version, Branch state or Checkpoint.

### 3.3 Selection — retain

| Table | Responsibility | Key rules |
|---|---|---|
| `selection_snapshots` | Immutable decision snapshot over Candidate Versions | New decision creates a new snapshot |
| `selection_items` | Exact selected Candidate Version and intended disposition | Must reference exact versions and same Task; selection does not authorize formal writes |

Selection means “these Candidate Versions are proposal inputs.” It does not mean “apply these changes to the map.”

## 4. Redesigned Command Proposal and submission group

The post-Selection model changes from CRUD Change Items to typed Command Proposals.

### 4.1 `change_sets`

One logical package of proposed formal history authoring operations.

Suggested fields:
- `change_set_id`;
- `source_task_id`;
- `selection_snapshot_id`;
- `current_version_number`;
- lifecycle status;
- created/updated timestamps.

Suggested lifecycle:
- `draft`;
- `ready`;
- `submitted`;
- `submission_rejected`;
- `reconciliation_required`;
- `cancelled`.

Do not use `applied` to imply that World State reconstruction succeeded. A `submitted` Change Set means the formal Commands were persisted.

### 4.2 `change_set_versions`

One immutable content version of a Change Set.

Suggested fields:
- `change_set_version_id` (stable AI-owned primary key);
- `change_set_id`;
- `version_number`;
- `target_map_id` (opaque Core UUID evidence; Core Domain validates lifecycle at preflight);
- `target_branch_id` (opaque Core UUID evidence, when applicable);
- `target_history_id` (opaque Core UUID evidence resolved by Core Domain as the writable History target);
- `target_history_context_ref` (opaque freshness/precondition reference);
- `target_context_snapshot` (immutable explanatory snapshot, not authority);
- `content_hash`;
- `hash_algorithm`;
- `manifest_schema_version`;
- `status` (`draft` / `sealed`);
- `change_summary`;
- timestamps.

Rules:
- all semantic fields and ordered proposal items are covered by the canonical hash;
- display-only fields are excluded;
- a sealed version is immutable;
- any semantic edit creates a new version;
- the target Map/Branch/History and target-context references must come from Core Domain, never AI inference;
- target Map/Branch/History references remain opaque UUID evidence rather than restrictive FKs, so old AI evidence cannot block Core Domain lifecycle operations;
- child proposal/authorization/submission rows reference the exact `change_set_version_id`, not duplicated `(change_set_id,version_number)` pairs; enforce unique `(change_set_id,version_number)` and a unique stable `change_set_version_id`;
- do not add `base_branch_revision_id` as an assumed Branch Revision foreign key.

### 4.3 `command_proposal_items` — replaces `change_items`

Each row is one typed proposal to create a formal Core Domain Command.

Suggested fields:
- `proposal_item_id`;
- `change_set_version_id` (FK to the exact AI-owned sealed/draft version);
- `item_number`;
- `command_type_id` (supplied by Core Domain);
- `descriptor_version` (supplied by Core Domain);
- `payload_json` (exact Core Domain-defined payload shape);
- `historical_time_payload` (canonical representation defined by Core Domain);
- `candidate_id` and `candidate_version_id` where applicable;
- `object_identity_id` where applicable (FK to retained Core Object identity);
- `reservation_id` where applicable (FK to permanent Core Object ID Reservation);
- `asset_manifest` with immutable hashes and AI-owned staging locators; published Core Asset IDs are recorded separately after submission;
- `preflight_snapshot` and diagnostics;
- created timestamp.

Rules:
- `item_number` defines the order of items in the immutable manifest, not necessarily the final semantic execution order;
- the payload must validate against the Core Domain descriptor/version;
- AI must not invent Command types or payload schemas;
- one proposal may reference multiple Candidate Versions only when the Core Domain descriptor permits it;
- a Candidate CRUD label is not a formal Command type;
- geometry operations and Object operations remain distinct;
- no direct Object state overwrite is permitted.

### 4.4 `proposal_ordering_relations` — AI-proposed relations only

Stores only new ordering relations proposed as part of a Change Set version.

Suggested fields:
- `ordering_proposal_id`;
- `change_set_version_id` (FK to exact proposal version);
- `before_proposal_item_id`;
- `after_proposal_item_id`;
- `relation_type`;
- `provenance`;
- `human_acceptance_evidence`;
- created timestamp.

Rules:
- this table is not an authoritative dependency graph;
- it must not contain copied or editable versions of existing Core Domain ordering constraints;
- existing constraints are queried read-only and captured only as exact context/precondition evidence in the sealed manifest;
- accepted proposed relations are submitted through a Core Domain-supported authoring operation;
- if a relation is semantically ambiguous, require user decision before sealing.

### 4.5 `change_authorizations`

One immutable human authorization decision for an exact sealed proposal version.

Suggested fields:
- `authorization_id`;
- `change_set_version_id` (unique FK to the exact AI-owned sealed version);
- `content_hash`;
- `target_history_id` (opaque Core UUID evidence);
- `target_history_context_ref`;
- `decision` (`authorized` / `rejected`);
- `authorized_by`;
- `decision_evidence`;
- `decided_at_utc_ms`.

Rules:
- only a human can authorize or reject;
- authorization binds to exact version, hash, History target and target context;
- any semantic change or stale context makes it unusable for submission;
- a rejected version cannot later be authorized; the user must create a new sealed version;
- the authorization row is immutable; it has no `revoked_at` or mutable revocation fields;
- AI and background workers cannot create authorization or revocation evidence.

### 4.5.1 `authorization_revocations`

Append-only record that a human withdrew an unconsumed authorization.

Suggested fields:
- `authorization_revocation_id`;
- `authorization_id` (unique FK to `change_authorizations`);
- `revoked_by_actor_id` (optional local human actor reference);
- `reason`;
- `revoked_at_utc_ms`.

Rules:
- only a human may create a revocation row;
- one authorization may be revoked at most once; only an `authorized` decision may be revoked;
- revocation is allowed only before a submission attempt enters `submitting`;
- if a submission outcome is `outcome_unknown`, reconcile first because the commit may already have succeeded;
- revocation and submission-start are serialized through the single Application Commit Coordinator and checked in one short transaction;
- a revoked authorization can never be reused; reauthorization requires a new sealed proposal version and a new human decision;
- successful submission is not retroactively revocable.

### 4.6 `submission_attempts`

One row for each attempt to submit an authorized sealed Change Set.

Suggested fields:
- `submission_attempt_id`;
- `change_set_version_id`;
- `authorization_id`;
- `idempotency_key`;
- `request_hash`;
- `status` (`prepared`, `submitting`, `persisted`, `rejected`, `outcome_unknown`, `reconciled_persisted`, `reconciled_not_persisted`);
- `started_at_utc_ms`;
- `finished_at_utc_ms`;
- `error_code`;
- `error_message`;
- `reconciled_at_utc_ms`.

Rules:
- the idempotency key is stable for the same exact submission attempt;
- a retry after a known rejection may be a new attempt only after the proposal/context is revalidated as required;
- an uncertain outcome must be reconciled against authoritative Core Domain History;
- `outcome_unknown` blocks retry and authorization revocation until reconciliation;
- revocation and submission-start are serialized through the single Application Commit Coordinator;
- never blindly replay;
- prevent duplicate submission while an outcome remains unknown.

### 4.7 `submission_command_refs`

Maps successfully persisted proposal items to exact Core Domain Command references returned by Domain Services.

Suggested fields:
- `submission_command_ref_id`;
- `submission_attempt_id`;
- `proposal_item_id`;
- `core_command_ref`;
- `accepted_order` if returned by Core Domain;
- created timestamp.

`core_command_ref` is opaque Core UUID evidence, not a local Command copy and deliberately not a restrictive FK because Core Commands may later be edited/deleted while AI evidence must remain.

### 4.7.1 `submission_asset_refs`

Maps proposal asset content to the exact immutable Core Asset published/returned during formal submission.

Suggested fields:
- `submission_asset_ref_id`;
- `submission_attempt_id`;
- `proposal_item_id`;
- `asset_role`;
- `content_hash`;
- `core_asset_id` (FK to retained Core `core_asset`);
- `created_at_utc_ms`.

Rules:
- one proposal item may reference multiple assets; one Core Asset may be reused by multiple proposal items;
- the Core Asset ID is recorded only after Core Domain has validated/published the immutable Asset;
- the Core Asset hash must match the sealed proposal asset manifest;
- the AI row is immutable submission evidence, not an AI-owned Asset metadata copy;
- the Core Asset cannot be garbage-collected while a `submission_asset_refs` row references it;
- failed submission transactions do not commit this row. A file published before a failed DB commit remains an unreferenced orphan until safe cleanup.

### 4.8 `application_reports`

One immutable final report per submission attempt, written only once the attempt has a known terminal outcome.

Suggested fields:
- `application_report_id`;
- `submission_attempt_id`;
- `outcome`;
- `persisted_command_count`;
- `rejected_command_count`;
- `core_diagnostic_code`;
- `core_diagnostic_summary`;
- `report_payload`;
- `created_at`.

The report describes submission/persistence only. It must not claim that reconstruction or playback succeeded.

Do not store `result_branch_revision_id` as an assumed FK. Do not update this historical report when a user later edits or deletes a submitted Command.

## 5. Reconstruction and playback are not AI-owned schema entities

The AI Assistant must not create a formal `rebuild_jobs`, `world_states` or `checkpoints` authority table.

Core Domain owns:
- rebuild trigger rules;
- rebuild job/lock lifecycle;
- Fail-Fast result and first error;
- valid playback boundary;
- Branch invalidation propagation;
- Checkpoint validity and recovery.

AI Assistant may display current Core Domain status through a read-only integration query.

If a local cache is later required for UX/performance, it must be:
- explicitly marked as a non-authoritative read model;
- keyed by Core Domain context/lineage references;
- safely refreshable;
- invalidated when the Core Domain context changes;
- never used to authorize a formal write or prove current reconstruction success.

Normal Command edits pause playback until the user triggers rebuild. Failed-history repair follows the Core Domain's restricted repair mode. Checkpoint corruption recovery is a separate Core Domain cache-recovery operation.

## 7. Transaction and migration design constraints

### 7.1 Desired transaction boundary

The final submission should use one short local database transaction:
1. recheck exact human authorization and canonical content hash;
2. recheck target History context and reservations;
3. validate descriptors/payloads and accepted ordering data;
4. persist the entire formal Command batch through Core Domain Domain Services;
5. persist exact submission outcome evidence;
6. commit all or none.

No LLM inference, network operation, large geometry generation, long validation or asset staging runs inside this transaction. Candidate assets are validated and immutably published before the final DB transaction; Core Domain owns formal Asset metadata and references. Unreferenced files after a failed DB commit are cleaned only after proving no committed reference exists.

### 7.2 Transaction proof is still mandatory

The one-file SQLite topology is the recommended target, not a proven current implementation. Before executable DDL:
- confirm the Core Domain persistence provider;
- confirm the same SQLite connection/transaction can be passed through Domain Services and AI submission services;
- confirm transaction rollback covers both Core Commands and minimum AI submission evidence;
- test process termination immediately before and after commit;
- test uncertain response reconciliation.

If the same transaction cannot be shared, stop and redesign. Do not simulate atomicity with two commits. The required provider/transaction proof scenarios are specified in P2-09-12; they must be executed by the development team on packaged Windows/macOS runtimes.

### 7.3 Migration policy

V1.14 SQL is an initial prototype bootstrap, not an upgrade migration.

Recommended final sequence:
- Core Domain P2-09 migrations create Core tables and stable keys first;
- AI tables are added in the same SQLite file with AI-owned migration scripts under `module_id='ai-assistant'`;
- one shared `schema_migration` ledger records `module_id`, migration ID, checksum and applied time; Application Bootstrap owns orchestration only;
- the integrated bootstrap creates both bounded contexts in dependency order;
- any supported V1.14 user database requires an explicit tested migration; otherwise V1.14 is documented as a disposable prototype and a fresh integrated database is created;
- unknown or partially initialized databases are rejected rather than silently repaired.

## 8. Required verification tests

### Proposal and authorization
1. Sealed proposal versions are immutable.
2. Semantic edits create a new version and new content hash.
3. Display-only edits do not alter the semantic hash.
4. Authorization binds to exact version/hash/History target/context.
5. A stale target context rejects submission and requires new authorization.
6. AI/system actors cannot authorize.

### Command submission
7. Unsupported Command descriptors are rejected.
8. Payloads validate against Core Domain descriptors.
9. Accepted ordering relations are included in the hash and submitted through Core Domain.
10. Existing authoritative constraints cannot be mutated by AI.
11. Entire batch persists or none does.
12. Unknown commit outcome is reconciled without duplicate Commands.
13. Exact Core Domain Command references are retained.

### Later authoring and reconstruction
14. Later manual Command edits do not mutate old proposal or authorization evidence.
15. Later AI-requested changes require a new proposal and authorization.
16. Command deletion does not auto-delete dependent Commands.
17. Insertion at an earlier Historical Time retains later Commands.
18. Normal edits pause playback until user-triggered rebuild.
19. Fail-Fast preserves later Commands and stops at the first error.
20. Playback boundary never exceeds successfully rebuilt history.
21. Branch inheritance and Checkpoint invalidation are delegated to Core Domain.

### Database and recovery
22. No AI table shadows Core Domain identity/history/state/checkpoint entities.
23. Foreign keys enforce all AI-owned relationships.
24. Core/AI atomic transaction rollback is proven.
25. Crash recovery and submission reconciliation are tested against the production .NET SQLite provider.

## 9. Open gates before executable V2.0 schema

- Concrete V1 Core Domain Command descriptor catalog, payload schemas and deterministic handler compatibility policy.
- Final Calendar conversion/interval validation against complete D01 examples; D01 remains Proposed / Discussion.
- Final integrated DDL, SQL migration scripts and schema constraints based on P2-09-11 V0.7.
- Verify the exact Object Type display grammar; retain Object identity and published Asset metadata while AI evidence references them.
- Execution of P2-09-12 provider transaction proof tests on packaged Windows/macOS runtimes.
- Final WAL/PRAGMA policy and Project database + Asset Store backup/restore evidence.

The following are already represented in the current design baseline and are not open architecture questions: Shared Object retroactive definition semantics, Project + Object Type allocation namespace recommendation, stable internal Object identity key, in-memory State Change generation, half-open Historical Time precision intervals, Map/Branch History ownership, Calendar Configuration persistence and the one shared migration ledger.

## 10. Current recommendation

Adopt V1.16 as the AI Assistant logical schema integration baseline. It supersedes V1.15 for design purposes but does not provide executable SQL.

The next step is to finish the Command descriptor catalog and bounded schema validation, then produce the integrated executable SQLite Schema V2.0 and migrations only after P2-09-12 passes. Keep the database local and understandable; do not add enterprise persistence infrastructure.
