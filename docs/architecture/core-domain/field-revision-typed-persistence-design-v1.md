# Field Revision Typed Persistence Design V1

- Status: Implemented in PR #11: Map Space / Spatial Reference ownership and typed Field Revision scalar/child persistence; Field Payload storage remains pending
- Date: 2026-11-22
- Scope: Core Domain Field Revision metadata persistence and its spatial-reference boundary
- Parent: [Field Payload Storage Implementation Plan V1](field-payload-storage-implementation-plan-v1.md)

## 1. Purpose

Define the next safe persistence step after the typed Field Revision projection. The design must remove the transitional JSON manifest from the long-term internal authority path without inventing spatial ownership relationships, losing exact numeric meaning, or bypassing the accepted EF Core migration workflow.

This document records the accepted typed-persistence contract and the implementation state. Typed SQLite metadata persistence and its EF migration are implemented; payload BLOB/file storage remains pending.

## 2. Verified current implementation

At the current PR head:

- `core_map_field_dataset` is Map-owned and uniquely identifies one registered field key per Map.
- `core_map_field_revision` stores immutable revision identity, lineage, generic Asset reference, content fingerprint, canonical `manifest_json`, provenance, creation time and typed semantic scalar columns.\n- `core_map_field_revision_plane`, `core_map_field_revision_category_code` and `core_map_field_revision_codec` store ordered/repeatable semantic child rows.
- `FieldRevisionMetadata` is built from the validated manifest at publication and is persisted as typed scalar/child rows. Reads reconstruct it from those relational rows and do not parse `manifest_json`.
- The projection carries descriptor pins, Map Space and spatial-reference IDs, grid, coverage, edge, no-data, value profile, planes, category codes, codecs and tile-hash metadata.
- SQLite retains `manifest_json` as a canonical interchange/diagnostic copy; it is no longer the source for typed metadata reads.
- `core_map` now owns a stable `map_space_id` and an initial nullable `spatial_reference_id` binding; unconfigured Maps cannot publish Field Revisions.\n- `core_spatial_reference` stores immutable project-scoped definitions, including typed coordinate precision profile values and a canonical definition fingerprint.\n- Migration `20261122140144_MapSpatialReferenceOwnership` was generated by the real EF CLI; the generated Designer and model snapshot are committed.\n- Domain publication validation and the SQLite publication transaction both compare Map Space, Spatial Reference, coordinate precision profile and vertical-reference identities.
- The current schema has no dedicated Field Payload row; the revision still references `core_asset`.

The typed projection is now backed by authoritative relational persistence. `manifest_json` remains only as a canonical interchange/diagnostic copy while package consumers are migrated.

## 3. Spatial ownership boundary

### 3.1 Keep the concepts distinct

The following identities must not be collapsed:

- **Map ID**: the owner of the Map Source Field Baseline and its Field Datasets.
- **Map Space ID**: identifies the spatial domain/frame in which the field grid is defined. It is not a viewport, working scope, zoom level, tile set, or Map Extent.
- **Spatial Reference ID**: identifies the immutable coordinate-reference definition used to interpret coordinate values. The accepted ME-05-04 / P2-09-25 contract describes this definition as project-scoped, locally available and immutable once referenced.
- **Grid metadata**: describes one Field Revision's sampling lattice within that declared spatial context. It is revision data, not the definition of the spatial reference itself.

A Map Space and a Spatial Reference are not interchangeable. Two fields may refer to the same spatial reference while having different grids. A coordinate-reference conversion must create a new immutable reference identity and new converted payload/revision evidence; it must not reinterpret existing coordinate strings in place.

### 3.2 What can be enforced now

The codebase now contains authoritative Map Space ownership on `core_map` and immutable Spatial Reference definitions in `core_spatial_reference`. The following rules still apply:

- inventing a foreign key from `map_space_id` to `core_map.map_id`;
- treating `spatial_reference_id` as an EPSG code or assuming it is globally resolvable;
- creating placeholder rows from IDs found in manifests;
- inferring a Map's spatial reference from its current Field Revision;
- silently changing or normalizing either identifier during persistence.

For typed Field Revision persistence, preserve both IDs exactly on the immutable revision snapshot. `spatial_reference_id` is also constrained by the project-scoped `core_spatial_reference` owner record at Map binding and publication; `map_space_id` remains a stable Map-owned identity on `core_map`, not a separate catalog. Validate both IDs against the submitted manifest and current Map owner context.

### 3.3 Owner contract

The ownership boundary is now specified in [Map Space and Spatial Reference Ownership Contract V1](map-spatial-reference-ownership-contract-v1.md):

- One Map owns exactly one stable Map Space ID in V1. It is a typed property on `core_map`, not a separate Map Space aggregate/table.
- A Map may remain unconfigured during initial setup; before Field publication it must have one active Spatial Reference binding. Definitions are project-scoped and the Domain persistence port exposes insert/read only; multiple Maps in one Project may reuse a definition.
- The Spatial Reference definition owns the selected coordinate precision profile and optional vertical-reference identity. The canonical manifest snapshots those IDs and owner-context validation must match them.
- Elevation's `unit` is a sample-value unit, distinct from both coordinate units and vertical-reference identity.
- Map Space and Spatial Reference IDs remain separate identities; neither is inferred from the other or from EPSG aliases.
- The initial release has no historical user data; no legacy read, compatibility dispatcher or backfill path is implemented. Missing definitions/precision/unit/vertical values are rejected for every new publication.

The owner contract is implemented in Domain and EF. `core_map.spatial_reference_id` is constrained to the same-Project `core_spatial_reference` record; owner context is revalidated in the publication transaction.

## 4. Typed relational persistence shape

### 4.1 Revision scalar metadata

The following values are immutable and belong directly to the Field Revision row because they describe the exact interpretation of that revision and are read together. They are now mapped to typed SQLite columns:

- field key, descriptor schema version and semantics ID;
- Map Space ID and Spatial Reference ID;
- grid width/height and tile width/height;
- origin X/Y and spacing X/Y as canonical decimal **TEXT**, not SQLite REAL;
- axis orientation and cell registration;
- coverage mode and optional mask-plane name;
- Map edge semantics;
- no-data policy, mask-plane name, valid value and invalid value;
- value profile ID and profile scope;
- tile hash algorithm and version.

The existing Dataset descriptor pin remains authoritative for Dataset compatibility. The Revision also stores its descriptor snapshot so that an old immutable revision remains independently interpretable and auditable.

### 4.2 Ordered and repeatable metadata

Use child tables rather than opaque JSON arrays for repeatable semantic records. These tables are now implemented:

- `core_map_field_revision_plane`: one row per plane, keyed by revision + ordinal; stores name, sample format and bytes per cell.
- `core_map_field_revision_category_code`: one row per category key; stores category key and integer code.
- `core_map_field_revision_codec`: one row per codec, keyed by revision + ordinal; stores codec ID, name and version.

Codec `parameters` may remain a bounded, validated JSON extension value in V1 because its internal parameter vocabulary is codec-specific and not currently queryable by Core Domain. It must not be used to hide core Field semantics. Its schema/version and canonicalization requirements must be explicit.

Every child row has a restrictive foreign key to its owning revision. Ordinals are stable and unique within a revision. Category keys are unique within a revision. The write transaction inserts the revision and all child rows together.

### 4.3 Values that do not belong in this relational model

- Package envelope values such as manifest format major/minor, manifest schema identifier, byte order and JCS canonicalization are interchange/package concerns, not additional Field Dataset authority columns.
- `ProvenanceJson` remains a separate provenance/audit value; it is not a substitute for typed Field metadata.
- Payload bytes and payload storage location belong to the dedicated Field Payload model in the parent implementation plan, not to these metadata child tables.
- Renderer indexes, decoded tiles and other disposable caches do not belong in Core Domain tables.

## 5. Canonical manifest semantic contract

The initial World View release has one canonical Field Package manifest contract. There is no V1/V2 compatibility split and no historical data requiring a legacy-read path.

The current schema is [P2-09-34 Field Package Canonical Manifest Schema](p2-09-34-field-package-canonical-manifest-schema-v0.1.json), with executable Domain validation and validation vectors in [P2-09-35](p2-09-35-field-package-canonical-manifest-validation-vectors-v0.1.json).

The single contract requires:

- `field.unit`: required for elevation (`m` or `ft`); forbidden for categorical `land_water`.
- `spatial.vertical_reference_id`: required for elevation; forbidden for `land_water`.
- `spatial.coordinate_precision_profile_id`: required for all fields and selected by the immutable Spatial Reference definition.
- `value_encoding.profile_id` remains the sample representation/encoding profile. It is not the coordinate precision profile.
- Resolution is represented by `grid.spacing_x`, `grid.spacing_y`, `grid.width` and `grid.height`. Tile dimensions describe package tiling, not semantic resolution.
- Grid alignment is represented by `grid.origin_x`, `grid.origin_y`, `grid.axis_orientation` and `grid.cell_registration`; no duplicate alignment object is introduced.

The WVFLDPK binary envelope remains format 1.0. The manifest schema identity/version remains the initial contract identity; there is no second manifest format or compatibility dispatcher.

The Domain publication validator enforces the required properties, and both Domain and the SQLite publication transaction verify that Map Space, Spatial Reference, coordinate precision profile and vertical-reference identities match the owning Map and its immutable definition.

## 6. Typed projection and persistence transition

1. The application has no historical user data; new records are created under the complete canonical manifest contract.
2. Verify Dataset descriptor pins match the Revision snapshot.
3. Project every value without lossy numeric conversion. Decimal grid values remain exact strings.
4. Insert revision scalar fields and all child rows in the same publication transaction.
5. Reject malformed, inconsistent, duplicate or unsupported values. Do not repair silently.
6. Preserve the canonical manifest temporarily for diagnostics and package interchange while all consumers migrate.
7. Verify a typed read produces the same semantic projection as the validated manifest.
8. Retire internal manifest persistence only after every production reader/writer has moved to the typed model and the interchange contract is independently preserved.

## 7. Payload relationship

The accepted storage baseline supersedes the older assumption that every Field Revision payload must be a generic Core Asset:

- one immutable Field Revision owns one logical immutable Field Payload;
- the payload may be raw SQLite BLOB bytes or a managed external file;
- payload metadata and the owner relationship are stored in the dedicated Field Payload model;
- the payload storage choice does not change Field Dataset or Revision identity;
- the generic `core_asset` model remains for generic project assets and existing typed Asset consumers.

There is no historical user data to backfill. New Field Revisions should move directly to the dedicated Field Payload authority once its publication, integrity and recovery path is implemented. Do not create both a generic Asset payload and a Field Payload as two competing authorities for new revisions.

## 8. EF Core migration requirements

The Map Space / Spatial Reference ownership schema change was generated using the real EF Core CLI as migration `20261122140144_MapSpatialReferenceOwnership`. The typed Field Revision metadata schema change was generated using the same CLI workflow as migration `20261122141903_FieldRevisionTypedMetadata`.

The command used from the `WorldView` solution directory was `dotnet ef migrations add FieldRevisionTypedMetadata --project src/WorldView.Infrastructure --startup-project src/WorldView.Infrastructure --context CoreDomainDbContext`.

- Do not edit the generated migration or `CoreDomainDbContextModelSnapshot` by hand.
- Do not add a second migration ledger.
- Do not alter the initial migration.
- Do not use `EnsureCreated`, suppress pending-model warnings, or skip migration checks.
- Update runtime model configuration, generated migration and generated snapshot as one schema change.
- Include migration-chain and typed round-trip tests against fresh temporary SQLite databases; no historical backfill test is required.
- Both ownership and typed metadata migrations were generated on GitHub Actions runners using the pinned .NET 11 / EF Core 11 CLI. Their generated migration files and model snapshot were committed unchanged.

## 9. Required acceptance tests

- Typed metadata write/read round trip without consulting `manifest_json`.
- Exact preservation of decimal origin/spacing strings, including lexical precision.
- Plane and codec ordering survives persistence.
- Category-code key/value uniqueness and descriptor-specific validation.
- Invalid enum, range, required-field and cross-field combinations are rejected.
- Map Space and Spatial Reference IDs are preserved exactly and are not accidentally joined to Map ID or EPSG aliases.
- Cross-Project or wrong-Map Dataset ownership is rejected.
- Initial schema creation and typed persistence require no historical-data backfill.
- Malformed or semantically inconsistent manifest input fails with an actionable diagnostic and does not partially publish.
- New Field Revisions cannot be published unless all descriptor-required unit/vertical/precision values are present.
- Revision metadata and its payload reference publish atomically with the Dataset current-revision compare-and-swap.
- Windows and macOS produce equivalent typed values and hashes for the same canonical source.

## 10. Next implementation order

1. **Completed:** Map Space and immutable Spatial Reference Domain records, project-scoped persistence, initial binding and owner-context validation.
2. **Completed:** typed Field Revision scalar columns and ordered plane/category-code/codec child tables; reads reconstruct metadata without parsing `manifest_json`.
3. **Next:** implement the dedicated BLOB / managed-file Field Payload adapter and its publication, verification, recovery, path-confinement and orphan-cleanup protocol.
4. Complete the package writer and regenerate canonical binary golden fixtures.

No historical user-data backfill or dual-read compatibility layer is required for the initial release. No universal BLOB/file threshold is introduced here. The application remains a single-user desktop application on Windows and macOS; no distributed storage or multi-node coordination is implied.
