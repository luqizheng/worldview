# World View Core Domain — P2-09-03 Command / Event / State Change Persistence Contract V0.2

- Date: 2026-11-21
- Status: Recommended V1 persistence decision — Command/Event persisted; State Change is a runtime-derived result and is not persisted as a separate table
- Supersedes: P2-09-03 V0.1 for the V1 persistence choice; prior authority/cardinality semantics are retained unless explicitly revised below
- Depends on: ADR-001/002/003/005; P2-01 Domain Model Proposal; D01-01~143; P2-08 V0.3; P2-09-01/02/05/08

## 1. Purpose

Settle the V1 physical persistence choice for Command, Event and State Change while preserving their distinct domain meanings. This contract deliberately favors the simplest model that can deterministically reconstruct history and support Checkpoints.

## 2. Authority model

- **Command** is the authoritative, author-editable record of an action that adds or changes formal History.
- **Event** is an optional narrative/historical occurrence associated with a History. It does not directly mutate World State.
- **State Change** is the typed executable state-change result generated by interpreting a Command through its registered deterministic handler. It is not a separate authoring record.
- **World State** is the reconstructed result of applying applicable State Changes along one selected History inheritance path.
- **Checkpoint** is the persisted derived acceleration cache for a reconstructed World State; it is not a replacement for Commands or Events.

## 3. V1 persistence decision

**Do not persist State Changes in a dedicated SQLite table in V1.** Generate them in memory when Core Domain interprets/replays the source Command.

Reasons:

1. Commands are already the sole authoring authority. Persisting a second derived ledger would introduce invalidation, materialization generations, publication pointers and cleanup rules without a demonstrated need.
2. Checkpoints already provide the durable acceleration mechanism for large reconstructed states.
3. Deterministic Command descriptors and execution-semantics identifiers preserve reproducibility without a second persisted representation.
4. An in-memory State Change retains its source Command identity, effective Historical Time, type, payload and optional Event association for validation, diagnostics and application.
5. If profiling later proves repeated Command interpretation is a material bottleneck, a rebuildable State Change cache can be introduced through a forward migration. It must remain explicitly derived and must not become history authority.

The absence of a State Change table does not remove State Change from the Domain Model or from runtime execution APIs.

## 4. Cardinality and runtime provenance

- One Command may generate zero, one or many State Changes.
- A narrative-only Command may generate zero State Changes.
- A complex semantic Command may generate multiple State Changes.
- Every runtime State Change is attributable to exactly one source Command in V1.
- A State Change may have zero or one explanatory Event association in the runtime result.
- An Event may explain zero or many runtime State Changes.
- A State Change is never independently authored or persisted as a second history ledger.

The runtime State Change object must retain at least the source Command identity and its effective History context for diagnostics and deterministic application. These are execution values, not persisted entity identities.

## 5. Command / Event association persistence

Persist Commands and Events independently, and use one optional relation table `core_command_event` to associate them:

- one Command may be associated with zero or more Events;
- one Event may be associated with zero or more Commands;
- an Event with no associated Command is valid narrative history;
- a Command with no associated Event is valid;
- a Command may create an Event without generating any State Change;
- the relation is explanatory/grouping metadata and never determines execution order.

When a Command handler generates State Changes, it may attach the relevant Event association to each runtime State Change according to its descriptor. For V1, the persisted Command/Event relation is the durable grouping context. If a future concrete Command requires independently persisted Event mapping for individual generated State Changes, that use case must be demonstrated before adding a more granular relation model.

## 6. Replay and deterministic compatibility

- Persist stable Command Type ID, descriptor schema version and execution-semantics/handler compatibility identifier on each Command.
- Reconstruct State Changes by invoking the compatible deterministic handler for that exact Command semantics identifier.
- Never silently execute old Commands with a newer handler if semantics differ.
- Retain old handlers while persisted Commands require them, or perform an explicit controlled history migration with validation.
- All deterministic inputs needed to generate State Changes must be in the Command payload or in stable, explicitly referenced Core Domain data.
- Visual interpolation and animation frames are not State Changes unless they represent genuine domain transitions.

## 7. Editing and reconstruction lifecycle

- Commands may be edited, deleted and inserted under Core Domain authoring rules; no Command Revision Chain is introduced.
- Any Command edit/delete/insert invalidates the affected Checkpoints and causes the normal reconstruction lifecycle to re-evaluate the selected History path.
- Since State Changes are generated in memory, there is no persisted State Change materialization to mark stale, replace or clean up.
- Failed reconstruction preserves authoritative Commands and Events; it does not silently delete later history.
- Full reconstruction remains Fail-Fast at the first unexecutable boundary; later Commands remain persisted but are not treated as successfully reconstructed.
- Normal Command edits pause playback until the user triggers rebuild, under the established Core Domain lifecycle rules.

## 8. Branch and Shared Object semantics

- Commands and Events belong to one History.
- Branches reference parent History + `parent_at`; ancestor Commands and Events are inherited under the closed fork boundary and are not copied.
- Branch-owned State Changes are generated only from Branch-owned Commands and must satisfy `effective_time > parent_at`.
- Shared Object definition/base data is one current project-level value and is used by all historical reconstructions, including past Historical Time points.
- Post-zero Event-driven runtime changes remain local to the active Map/Branch History. No separate Shared Object History stream is introduced.

## 9. Consequences for physical schema

Persist:
- `core_command`;
- `core_event`;
- `core_command_event`;
- `core_command_order_constraint`;
- Command descriptor/semantics identifiers and required typed payload references.

Do not create in V1:
- `core_state_change`;
- `core_history_materialization`;
- `core_history_materialization_pointer`;
- any AI-owned State Change mirror.

Checkpoint fingerprints must cover the selected History lineage, authoritative Command/Event/ordering inputs, descriptor semantics required for replay, Map Initial State and the current Shared Object definitions used by the reconstruction.

## 10. Verification scenarios

1. One Command generates zero State Changes and persists successfully.
2. One Command generates multiple runtime State Changes deterministically.
3. Repeated reconstruction with the same Commands and handler semantics produces identical State Changes and World State.
4. An Event with no State Changes remains a valid narrative Event.
5. One Event may explain runtime State Changes generated by multiple Commands.
6. A Command may create an Event without generating State Changes.
7. State Changes retain exact source Command identity during execution/diagnostics.
8. Editing/deleting/inserting a Command invalidates affected Checkpoints and regenerates runtime State Changes without a State Change table.
9. A handler upgrade does not silently change an old Command's output.
10. A Branch inherits ancestor history without copying it and rejects Branch-owned effects at or before `parent_at`.
11. A post-zero Event in Map A does not change the runtime state of the same Shared Object in Map B.
12. AI Assistant cannot persist or mutate formal Commands, Events or State Changes directly.

## 11. Status

This V0.2 contract recommends the simplest V1 choice: **persist Commands and Events; generate State Changes deterministically in memory; persist only Checkpoints as reconstruction acceleration artifacts.** It does not authorize implementation or final DDL. A future persisted State Change cache requires measured justification and must remain rebuildable and non-authoritative.
