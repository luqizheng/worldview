# P2-09-12 V0.8 — Single-Connection Read Isolation Amendment

- Date: 2026-11-22
- Status: Adopted V1 architecture reconciliation; test-spec amendment
- Supersedes: Only the separate-reader-connection clauses of P2-09-12 V0.7 TX-04 and TX-31
- Retains: All other P2-09-12 V0.7 requirements and acceptance criteria
- Authority: CD-01-F1 Verification Report V0.1, especially §§5, 7–10 and 15

## 1. Decision

World View V1 retains the CD-01-F1 single-connection-per-ProjectSession access model. A ProjectSession owns one SqlitePackageDatabase; its physical SQLite connection has exactly one SqliteConnectionAccess coordinator. Package operations and Core Domain adapters use that same coordinator. Reads and writes are serialized through the same connection gate. Multi-step reads that require a coherent view use InSnapshotScope.

The V0.7 requirement that independent application reads must use separate physical connections is therefore **not a V1 acceptance requirement**. It is superseded for the current single-user, local-first V1 architecture.

This is not a claim that multiple connections are unsafe in SQLite. It is a deliberate product/architecture choice already implemented and verified in CD-01-F1:
- one application instance owns a Project database at a time;
- V1 has low concurrency and no demonstrated read-throughput bottleneck;
- serial access avoids sharing non-thread-safe connection/command/reader objects;
- a small re-entrant coordinator plus snapshot scope is simpler than introducing reader pools, WAL and cross-connection lifecycle rules;
- separate SqlitePackageDatabase instances for the same file remain distinct physical connections and are coordinated by SQLite file locks plus migration-ledger constraints.

The earlier P2-09-09 design says independent reads *may* use short-lived connections. That was a recommended option, not a mandatory architecture invariant. CD-01-F1 later selected and verified the single-connection model for V1.

## 2. Revised TX-04 — Connection ownership and threading

### Required behavior

1. Every operation using the ProjectSession connection enters its one SqliteConnectionAccess coordinator.
2. The critical section covers command creation, execution, reader materialization/disposal, transaction begin/commit/rollback and all connection use.
3. No SqliteConnection, SqliteCommand, SqliteDataReader or active transaction escapes the coordinator callback or is concurrently used by another execution flow.
4. Multi-step reads requiring a consistent cross-query view execute within InSnapshotScope (or an equivalent single coordinator scope).
5. A separate SqlitePackageDatabase instance opened against the same file owns a separate physical connection/coordinator; SQLite file-level locking and migration-ledger uniqueness must fail closed under cross-instance contention.
6. No dedicated read pool, shared-cache mode or WAL is introduced solely to satisfy the former separate-reader clause.

### Pass criteria

- Concurrent application calls through the same ProjectSession connection are serialized; no overlapping connection/command/reader use occurs.
- A read cannot enter the connection while another operation owns the coordinator for an active transaction.
- Snapshot-scoped multi-query reads observe a coherent state.
- Cross-instance same-file initialization/migration tests prove no duplicate migration application and a valid final database.

## 3. Revised TX-31 — Reader isolation under the V1 single-connection model

### Required behavior

1. Keep ordinary UI/query reads active while a short write transaction commits or rolls back.
2. Reads use the ProjectSession's shared coordinator and wait until the active write transaction leaves its critical section.
3. After commit, a reader sees the complete committed state; after rollback, a reader sees the pre-transaction state.
4. No reader can observe uncommitted rows or a partial multi-table aggregate.
5. Any multi-query read whose correctness depends on a single logical snapshot uses InSnapshotScope.

### Pass criteria

- No dirty or partial state is observable.
- Readers are serialized, not independently concurrent, with the active writer.
- A successful transaction becomes visible as one complete unit; a rolled-back transaction remains invisible.
- No additional read connection is required for V1 compliance.

### Required test evidence

The existing real-SQLite tests provide broad evidence:
- `Concurrent_ReadersAndWriters_NeverObservePartialMapStructure`
- `Transaction_InProgress_BranchOwnedHistoriesAlwaysPairedWithBranch`
- `Concurrent_PackageDbOperationsAndCoreAccess_ShareSingleCoordinator`
- `Migration_PendingApplied_ConcurrentlyWithCoreReads_BothSucceed`

Before closing the amended TX-31 gate, add or identify a deterministic test that holds an explicit write transaction open, starts a competing read through the same coordinator, proves the read does not complete while the write owns the gate, then verifies the committed or rolled-back terminal state. Existing broad concurrency tests do not by themselves replace this explicit blocking assertion.

## 4. Scope and revisit conditions

This amendment applies only to the V1 single-user ProjectSession model. Revisit it only if measured evidence demonstrates that serialized read/write access materially harms UI responsiveness or background workload throughput, or if the product adopts concurrent Project sessions/processes.

Any future multi-connection read model must be a separate architecture revision that specifies:
- connection ownership and disposal;
- read-only/query-only policy;
- snapshot consistency and transaction boundaries;
- journal/WAL and busy-timeout behavior;
- backup/restore implications;
- per-connection foreign-key and native SQLite feature verification;
- deterministic concurrency and crash tests on packaged Windows/macOS runtimes.

Do not add these mechanisms speculatively.

## 5. Non-claims

This amendment does not close TX-01/TX-02 or any Core Domain + AI Assistant atomicity requirement. The Application Commit Coordinator and real AI submission persistence participant remain absent. It does not close WAL durability, process-crash recovery, backup/restore, packaged-runtime verification or Field Dataset publication tests.

It only reconciles TX-04/TX-31 with the already-selected CD-01-F1 V1 connection ownership model.
