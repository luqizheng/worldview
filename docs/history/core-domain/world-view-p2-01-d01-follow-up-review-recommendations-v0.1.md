## 2. 本轮已确认的 D01-77 精确恢复策略

### 2.1 用户选择

用户选择方案 A：

**后代 Branch 可以直接使用继承路径中祖先 Branch 的有效 Checkpoint
作为重建起点，不必强制回到更早祖先 Checkpoint 或基线重新回放。**

例如：

`A@1200 → B@1500 → C@1600`

如果 `B@1500` Checkpoint 有效，C 可以直接从 `B@1500` 恢复，然后执行 C
自己的 Command。

### 2.2 适用条件

直接恢复必须同时满足：

-   Checkpoint 保存的是指定 Branch、指定历史时间点的完整合成 World
    State；
-   Checkpoint 完整性校验通过；
-   Checkpoint 记录的继承路径版本与目标恢复路径完全匹配；
-   Checkpoint 的历史时间点不晚于目标重建位置，且适用于该目标；
-   从该 Checkpoint 到目标位置之间需要执行的 Command，严格属于目标
    Branch 的有效继承路径及其自有历史；
-   不把祖先 Branch 在分叉点之后的 Command 带入后代 Branch。

Checkpoint 的复用只是复用完整状态快照，不改变 Checkpoint
的归属，也不意味着后代 Branch 继承祖先 Branch 的身份或分叉点之后的历史。

### 2.3 对资料库的影响

这解决了 `13.7` 第 8 项所登记的 D01-77
精确恢复策略问题。现有资料存在一处记录不一致：README 将 D01-77
标记为"重拟条目"，而 `13-known-pending-review-items.md`
仍保留该项为未决。后续正式整理时应以本次用户明确选择为准，更新待审查索引与正文说明；不能把它误写成对旧版
D01-77 撤回议题的恢复。

## 3. 批量重建与 Checkpoint 管理（13.8 / 18.45）

### 3.1 两种模式的交互推荐（D01-128～130）

**推荐：默认提供"继续/修复重建"，将"强制全部重建"作为明确的高级操作。**

-   默认模式：继续/修复重建。保留仍有效的
    Checkpoint，从失败或中断位置继续。
-   高级模式：强制全部重建。明确提示会重新生成目标范围内全部
    Checkpoint，不依赖已有 Checkpoint。
-   用户启动前必须能看到模式说明、目标范围、预计影响和地图级锁定提示。
-   不设置隐式自动切换：继续/修复模式遇到错误时，严格
    Fail-Fast；不得自动改成强制全部模式。
-   两种模式共用 D01-125～137
    已确认的目标范围、祖先到后代顺序、地图级锁定、任务取消、任务失效与结果发布规则。

理由：继续/修复模式更符合日常维护成本；强制全部重建具有更大资源和等待成本，应由用户明确选择。

### 3.2 Checkpoint 文件格式与存储布局

**推荐：采用"每个 Checkpoint 独立目录 + 明确元数据 + 状态载荷 +
完成标记 + 校验文件"的逻辑结构。**

建议至少区分：

-   身份信息：地图、Branch、历史时间点、Checkpoint ID；
-   版本信息：继承路径版本组合、重建器/序列化格式版本；
-   World State 载荷：完整合成状态；
-   完整性信息：文件清单、MD5 校验值；
-   发布状态：特定完成标记。

完成标记只能在所有载荷写入、校验信息生成、发布前版本复核成功后写入。读取时必须先检查完成标记、版本适用性和完整性。具体二进制格式、压缩方式、字段布局留给
Storage/Serialization 技术设计确定。

### 3.3 完成标记与 MD5

**推荐：完成标记与 MD5 分工，不互相替代。**

-   完成标记用于识别一次 Checkpoint 生成是否完整发布。
-   `md5.txt` 用于发现载荷文件与记录校验值不一致。
-   MD5
    不承担抗恶意篡改的安全职责；若未来存在安全威胁模型，再另行评估更强摘要算法。
-   校验清单应明确覆盖哪些文件，避免把完成标记本身纳入循环校验。
-   校验失败时，该 Checkpoint 不得用于恢复；按 D01-116～122
    的单点损坏处理原则重建，不把文件损坏误判为祖先历史变化。

### 3.4 轻量级任务持久化与启动恢复

**推荐：持久化任务意图和必要进度，不持久化可恢复的执行现场。**

任务记录至少包含任务
ID、任务类型、启动时固定的目标范围、所选模式、已完成项、当前项、任务状态和必要的版本快照。

应用正常关闭或系统关机时，按 D01-138 安全停止任务。再次启动时：

1.  检查任务记录与完成标记；
2.  对已发布 Checkpoint 执行完整性及版本检查；
3.  清理或标记未完成的临时产物；
4.  不自动恢复旧任务继续计算；
5.  用户重新启动批量任务时，重新固定目标范围并按用户选择的模式执行。

这与"不要求关机期间继续计算"一致，也避免引入复杂恢复日志。

### 3.5 进度与错误呈现

**推荐：任务进度只读展示，错误以第一个阻断错误为主，另列已完成与未执行范围。**

展示内容至少包括：总体进度、当前
Branch/Checkpoint、已完成数量、待处理数量、失败位置、失败原因、受影响后代和下一步允许操作。查看任务信息不得解除地图级锁定。

### 3.6 批量任务与日常重建衔接

**推荐：共用同一重建内核与版本校验规则，使用不同任务编排层。**

-   单 Branch 日常重建仍遵循 D01-62、D01-96 等既有规则。
-   批量重建只负责固定范围、祖先到后代排序、地图级锁定和任务进度。
-   两种入口不能形成两套历史解释或两套 Checkpoint 发布规则。
-   批量任务取消、失败或祖先版本变化时，严格沿用
    D01-131～136，不发布失效结果。

## 4. Branch 继承、失效传播与调度（13.1 / 13.7 / 16.9）

### 4.1 Shared Object 在继承路径中的执行

**推荐：不建立 Shared Object 独立历史队列；沿选定 Branch 继承路径的统一
Command 序列执行。**

Shared Object 的运行时状态由该路径上实际执行的 Command 逐步形成。Command
执行时通过对象身份解析访问 Shared Object，并将状态变化写入当前路径的合成
World State。不同 Branch 可因路径不同而得到同一 Shared Object
的不同运行时状态。

隐式依赖发现应由执行器在 Command
解释/执行过程中生成可追溯的依赖记录；依赖记录是派生数据，历史重建时可重新计算，不成为第二套权威历史。

### 4.2 继承路径版本与失效范围

**推荐：路径版本由祖先链各段的有效历史版本组合构成，而不是一个全地图全局版本号。**

-   每个 Branch 维护自身历史版本。
-   后代路径版本由从根到目标 Branch 的各继承段版本组成。
-   祖先在分叉点以内的修改，只使包含该历史区间的后代路径版本失效。
-   祖先在分叉点之后的修改，不应使不继承该区间的后代路径失效。
-   版本比较必须能定位到路径段，避免无关 Branch 被全量失效。
-   版本值可采用单调递增修订号或不可变内容摘要；最终算法由技术设计选择，但必须满足无碰撞误判、可比较、可追溯和发布前复核。

### 4.3 多 Branch 调度

**推荐：先满足依赖顺序，再在独立路径之间有限并行。**

-   同一继承链必须祖先到后代串行推进。
-   不存在继承依赖的独立 Branch 可以并行。
-   并行度由 CPU、内存、磁盘吞吐和 Checkpoint 缓存压力动态限制。
-   调度优化不得改变 Command 顺序、State Change 结果或最终 World State。
-   D01-94
    的"只立即重建活动路径、非活动路径按需重建"是任务启动范围约束，不能被并行调度策略绕过。

### 4.4 Checkpoint 保存位置、淘汰与引用

**推荐：系统自动管理，不提供用户单个 Checkpoint 删除入口。**

-   优先保留分叉点及常用恢复点。
-   对有效性、重建成本、引用状态和存储压力综合评估淘汰候选。
-   被任务引用的 Checkpoint 可立即逻辑失效，但在引用释放前不得物理删除。
-   任务结束、取消、崩溃恢复时必须释放引用；启动时应能识别并清理孤立引用。
-   失效 Checkpoint 永远不能作为有效状态恢复，即使其物理文件暂时存在。

### 4.5 祖先修改导致后代失败的诊断

**推荐：诊断报告分离"触发变更""失败 Command""执行上下文"和"修复范围"。**

报告至少说明： - 哪个祖先 Branch 的哪段历史发生变化； -
变化是否处于当前后代的继承边界内； - 后代第一个失败的
Command、历史时间和错误类型； - 失败时使用的继承路径版本； -
哪些后代因此继承阻断； - 当前 Branch 允许的修复操作。

不得自动修改 Command、补建对象或寻找替代路线。诊断信息应能追溯到源
Command 和路径版本。

### 4.6 修复模式与正常编辑边界

沿用 D01-62、D01-96～100：

-   正常编辑阶段允许连续修改，用户主动触发重建；
-   自身重建失败后进入受限修复模式，每次修复保存后重新检查和重建；
-   失败点之后的 Command 禁止修改；
-   继承阻断的后代只读，必须先修复祖先 Branch。

不建议增加草稿 Command、绕过失败点的暂存执行或自动修复机制。

## 5. 地图整合技术细节（13.5 / 16.9）

### 5.1 时间轴映射

**推荐：整合时建立明确、可审计的来源时间映射表，不隐式重写历史时间。**

每条来源 Command 都应保留来源地图、来源 Branch、来源 Command
ID、来源历史时间和目标地图新
ID。若整合需要映射到统一时间轴，应显式记录映射关系，并在整合预览中展示。

### 5.2 同一内部时间的顺序处理

**推荐：优先保留来源路径内部顺序；跨来源的同刻 Command
不自动猜测语义顺序。**

-   同一来源历史中的顺序约束继续保留并重映射。
-   跨来源同刻操作只有在存在明确依赖或用户确认的排序规则时才确定先后。
-   无法确定且顺序会影响结果时，作为整合冲突阻断完成发布，不自动按 ID
    或文件顺序决定。

### 5.3 冲突呈现与失败历史

**推荐：先生成整合预览与冲突清单，再创建独立地图 C。**

创建 C 不等于历史验证成功。若 C 的完整历史验证
Fail-Fast，应保留整合任务报告和失败诊断；不得把失败点之后的状态标记为有效。源地图
A/B 不受影响。

### 5.4 独立完整性验证

C 创建后必须独立验证完整继承历史，确认新
ID、显式依赖、顺序约束映射和执行依据均有效。来源追溯只用于审计，不构成 C
对 A/B 的运行时依赖。

## 6. 13.2～13.6 其他遗留领域的推荐方向

### 6.1 持续 Command 精确执行模型（13.2）

**推荐：将持续 Command 建模为带明确执行进度的单条权威
Command；暂停只冻结行动进度，不消耗行动时间。**

持久化用户指定的开始条件、目标、总持续量/总行动量、已完成进度、暂停状态及必要执行依据。暂停时保存进度，不推进行动时钟；恢复时从剩余进度继续。阶段性
State Change 由重建器根据 Command
与进度确定性地产生，不作为独立权威命令。

预计结束时间是派生展示值；用户明确指定的结束约束属于 Command
执行依据。二者冲突时应报告并由作者处理，不自动改变用户输入。

### 6.2 执行依据与算法版本（13.3）

**推荐：区分用户确认依据、系统算法版本和可重建派生结果。**

-   用户明确指定或确认的路线、参数和约束必须持久化。
-   系统建议但未被确认的路线不应被当成作者决定。
-   会影响历史结果的算法必须带版本标识。
-   历史重建默认使用原执行依据和兼容算法语义；算法升级不得静默改变历史。
-   若旧算法不可用，报告兼容性问题，不自动用新算法覆盖旧结果。
-   Checkpoint
    元数据必须包含足以判断序列化格式与重建器兼容性的版本信息。

### 6.3 Checkpoint 生成策略（13.4）

**推荐：采用可配置但由系统管理的混合策略。**

在分叉点、历史重建成本较高的位置和常用时间点优先建立
Checkpoint；不要求每条 Command 后都建立。策略评估必须服从 D01-102
唯一性、D01-109～114 原子发布、D01-106 路径版本校验及 D01-143
完整状态保存边界。

内存缓存只作为进程级性能缓存；磁盘 Checkpoint
是可恢复的派生缓存。二者都不是历史权威，丢失后均可由 Command 重建。

### 6.4 发布作品格式（13.6）

**推荐：暂不把发布格式绑定到创作工程的内部存储格式。**

先定义发布目标与使用场景，再选择静态地图、可交互时间轴、视频或其他交付形式。发布产物应是独立导出物，不反向成为
Command 或 World State 的权威来源。此项不宜在当前 D01 Domain Model
阶段定死具体格式。
