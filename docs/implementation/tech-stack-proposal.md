# 1. 选型约束（来自已冻结架构，栈中立）

| 约束 | 来源 |
| --- | --- |
| 单机应用、单用户、localhost、无认证 | 架构基线 |
| 无分布式队列 / Worker 集群 / 多实例 | Task Engine V1.0 约束 |
| 顺序执行为默认 | Task Engine V1.0 约束 |
| AI 不直改数据库，必须经 Domain Services + Candidate Set + Change Set | 架构基线 |
| 保留 Branch / 版本检查 / 冲突检测 / 历史完整性 | 架构基线 |

结论：**对栈的核心要求是"简单、可靠、可维护的单机工程"，不是并发/分布式能力。**

# 2. 候选方案对比

## 方案 A：Python（标准库起步，按需引入依赖）

| 维度 | 评价 |
| --- | --- |
| 上手/运行成本 | 最低：`python -m unittest` 即可验证，零依赖可起步 |
| 历史引擎/领域建模 | dataclass + 纯函数，表达力足够 |
| 存储 | sqlite3 标准库内建；后续可换 SQLAlchemy（可选） |
| HTTP API | 标准库 http.server 可起步；正式期建议 FastAPI + Pydantic |
| MCP | 官方 Python SDK（`mcp`）成熟 |
| AI 生成链路 | Python 生态最强（后续接生成模型/LLM 最顺） |
| 与未来地图编辑器 UI 的关系 | 引擎与 UI 分离，无直接影响；但若 UI 走 Web/Electron，则前后端异语言 |
| 风险 | 桌面 GUI 生态一般；几何计算库（Shapely 等）为第三方依赖 |
| 已有资产 | 领域层草稿已存在（`server/`，未 commit，可直接续用） |

## 方案 B：TypeScript + Node.js

| 维度 | 评价 |
| --- | --- |
| 上手/运行成本 | 低：Node 单运行时，npm 生态成熟 |
| 历史引擎/领域建模 | TS 类型系统对 StateChange payload 模式校验有利 |
| 存储 | better-sqlite3 / Drizzle / Prisma 均可 |
| HTTP API | Express/Fastify/Hono 均可 |
| MCP | 官方 TS SDK（`@modelcontextprotocol/sdk`）最成熟 |
| AI 生成链路 | 可用（SDK 齐全），弱于 Python |
| 与未来地图编辑器 UI 的关系 | **最强**：若 UI 是 Web Canvas / Electron（地图编辑器基线的方向），前后端同语言、几何类型可共享 |
| 风险 | 数值/几何算法生态弱于 Python；运行时版本管理（nvm）小成本 |
| 已有资产 | Python 草稿作废（作为逻辑参考翻译，约 15 文件 / 30+ 测试用例，机械劳动） |

## 方案 C：C#/.NET（或 Java/Kotlin）

| 维度 | 评价 |
| --- | --- |
| 上手/运行成本 | 中：.NET SDK 安装即用，工程化程度最高 |
| 历史引擎/领域建模 | 强类型 + 成熟 DDD 惯例 |
| 存储 | SQLite（Microsoft.Data.Sqlite）/ EF Core |
| HTTP API | ASP.NET Core（内置，无需第三方） |
| MCP | 官方 C# SDK 已发布 |
| AI 生成链路 | 可通过 HTTP 调用外部模型服务 |
| 与未来地图编辑器 UI 的关系 | 若走 Windows 桌面（WPF/WinUI/Avalonia + Skia/自绘 Canvas），**最强**；地图编辑器基线的画布中心交互与几何编辑是重桌面交互场景 |
| 风险 | 跨平台桌面打包体积大；AI 生态最弱 |
| 已有资产 | Python 草稿作废（同上翻译） |

## 方案 D：Rust / Go

单机创作工具场景下工程性价比低（迭代速度、GUI/生态），**不建议**，仅登记完整性。如未来几何内核需要性能，可用独立原生模块解决，不必以它为主栈。

# 3. 决策的关键问题（供裁决时权衡）

1. **未来地图编辑器的形态**：Web/Electron Canvas → 方案 B 有长期复利；Windows 桌面 → 方案 C；UI 形态本身也是待定项（Baseline §40 未冻结渲染技术）。
2. **AI 生成链路的实现位置**：生成能力（地图生成、历史剧本生成）预期较重 → 方案 A 有生态优势；只做"AI 通过 MCP/HTTP 写入 Candidate"的轻接入 → 三案无差别。
3. **团队维护者的技术背景**：以长期维护者的顺手程度为准（此项只有用户能回答）。
4. **几何能力落点**：布尔运算/曲线/共享边界（地图编辑器基线 §10~15）无论哪个栈都需要几何库或自研内核；A=B(highest 生态) > C。此项可延迟到几何阶段再定。

---

# 4. 实施方建议（供参考，非决定）

- **若 2~3 年内以"引擎 + 数据 correctness"为重心、UI 形态未定**：选 A（Python）。理由：启动成本最低、领域测试最快落地、AI 链路生态最好；UI 定型后引擎可经 HTTP API 解耦，不必迁移。
- **若已倾向 Web/Electron 编辑器**：选 B（TypeScript），一步到位同语言。
- **若已倾向原生 Windows 桌面**：选 C（.NET）。
- 三案下，存储均建议 **SQLite 单文件库**（单机、零运维、事务完整），配版本化迁移脚本；该子决定可随主栈一并裁决。
