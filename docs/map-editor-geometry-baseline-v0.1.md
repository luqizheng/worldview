# World View — 地图制作与几何编辑系统设计基线

**版本：V0.1**  
**日期：2026-11-19**  
**状态：阶段性设计基线，部分扩展能力待后续讨论**

## 1. 产品目标

World View 的首要目标是提供专业、灵活且易于使用的地图制作能力。

地图画布是用户进行地图制作的核心工作空间。用户可以在画布上创建、绘制、编辑和组织地图内容，并通过时间、历史事件和地图分支表达地图随历史进程发生的变化。

产品需要同时满足两类需求：

1. 地图制作：创建地理环境、政治区域、基础设施、POI、标注及装饰内容。
2. 历史剧本制作：通过时间、事件、人物行动、路线和地图状态变化，展示一段历史进程。

两者使用统一的地图对象、几何、图层和历史管理体系。

## 2. 地图编辑器整体交互模式

采用 Canvas-centric（画布中心）交互模式。

建议桌面编辑器布局：

- 顶部：地图名称、保存状态、编辑操作、当前时间、Branch、视图设置。
- 左侧：绘制工具、图层树、地图对象列表。
- 中央：地图画布。
- 右侧：当前选中对象的上下文属性面板。
- 底部：可折叠时间轴、历史操作及相关信息。

设计原则：

- 画布优先。
- 工具按照用户的工作目的组织。
- 属性面板随选中对象变化。
- 编辑操作提供即时视觉反馈。
- 历史管理透明，但不干扰普通地图制作。

## 3. 地图创建方式

正式支持三种创建入口：

1. 空白画布。
2. 地图模板。
3. 导入已有地图，包括图片及支持的地图数据。

三种方式最终进入统一地图编辑器，不产生不同的数据模型。

## 4. Map Space 与画布

采用可扩展 Map Space。

Map Space 使用独立于屏幕像素的逻辑坐标，地图内容可以超出当前视口。

需要区分：

- Map Space：地图内容使用的逻辑坐标空间。
- Canvas View：用户当前看到的视口。
- Map Extent：正式地图范围。
- Export Area：导出时使用的独立范围。

Map Extent 不等于对象有效范围。边界外的对象不能因此自动删除、裁切或失效。

Vector Geometry 使用 Map Space 坐标。

Raster Layer 使用自身分辨率和空间定位，与矢量内容保持空间对齐。

虚构世界不强制使用地球经纬度；真实地理地图需要提供地理参考定位能力，具体坐标参考系统和投影能力需要进一步设计。

## 5. 地图编辑模式

采用矢量对象为核心、栅格绘制为补充的混合编辑模式。

### 5.1 Vector

用于承载具有语义身份的地图内容，例如：

- 大陆、岛屿、海洋。
- 国家、王国、行政区域。
- 河流、湖泊、山脉。
- 道路、桥梁、港口。
- 城市、村庄、建筑、遗迹。
- 历史行动路线、事件位置及其他需要独立管理的对象。

语义对象不能因为视觉绘制而丢失身份。

### 5.2 Raster

用于纹理、阴影、笔触、植被表现、艺术效果等。

Raster 内容可以独立存在于栅格图层，也可以在需要时关联地图对象。

## 6. 图层系统

采用统一图层树，提供类型筛选。

支持：

- Vector Layer。
- Raster Layer。
- Group Layer。

图层支持创建、删除、重命名、排序、嵌套分组、显隐、锁定、透明度、适用的混合模式、复制、批量选择及对象移动。

必须区分图层组织和地图对象语义归属：

- Layer 管理组织、显示和编辑管理。
- Map Object 管理语义身份、属性及业务关系。
- 隐藏图层不改变对象身份。
- Raster 内容可以独立存在，也可以关联对象。

## 7. 地图对象领域

初步分为四个产品领域：

1. Geographic Objects：大陆、岛屿、海洋、山脉、山峰、丘陵、河流、湖泊、森林、沙漠、沼泽、海岸线、地形区域。
2. Political Objects：国家、王国、帝国、省份、州、郡、行政区、领土、边境、政治势力控制区域。
3. Human & Infrastructure Objects：城市、村庄、城堡、建筑、港口、道路、桥梁、遗迹、矿场等。
4. Annotation & Decorative Objects：地名标签、文字说明、地图符号、指北针、比例尺、装饰图案等。

这些是产品领域分类，不要求对应四种数据库实体。

## 8. 地图对象创建方式

同时支持两种方式：

### 8.1 直接创建语义对象

用户选择国家、河流、城市、山脉等语义工具，直接在画布绘制。

### 8.2 先绘制通用几何，再转换

用户先创建点、线、多边形、曲线或自由形状，再赋予语义类型。

转换时需要检查几何类型、必要属性和业务约束，并尽可能保留原始几何。

两种方式最终进入统一地图对象体系。

## 9. Geometry Components

一个 Map Object 可以拥有多个 Geometry Components。

例如：

- 一个国家可以由多个岛屿多边形组成。
- 一个河流系统可以由多个河段组成。

Geometry Component 默认不具有独立语义身份。

如果某个组成部分需要独立名称、属性、历史或业务关系，应建立独立 Map Object。

编辑一个 Component 不自动修改其他 Components。

对象整体属性和组成部分局部几何属性分别管理。

## 10. 几何表达能力

第一版同时支持直线段和原生贝塞尔曲线。

初步几何类型：

- Point
- LineString
- Polygon
- MultiPoint
- MultiLineString
- MultiPolygon

Polygon 支持内部孔洞。

同一条几何路径允许混合直线段与贝塞尔曲线段。

贝塞尔曲线控制点和控制柄作为原生几何数据保留。渲染细分不能替代或丢失原始曲线表达。

## 11. 共享几何边界

采用选择性共享几何边界。

共享边界是独立几何资源，可以被多个地图对象引用。

规则：

- 共享的是边界几何，不是地图对象。
- 对象仍然拥有独立 ID、属性、历史及语义关系。
- 修改共享边界会影响所有引用对象。
- 允许用户通过明确操作解除共享。
- 解除后，各对象拥有独立边界几何。
- 不要求所有几何都共享。

共享边界生命周期、历史版本、冲突处理、拓扑约束及删除规则仍需进一步设计。

## 12. 几何吸附系统

采用默认开启、按类型配置的智能吸附系统。

支持：

- Grid Snapping：网格吸附。
- Vertex Snapping：节点吸附。
- Edge Snapping：边界吸附。
- Intersection Snapping：交点吸附。
- Smart Guides：智能辅助线。

支持按类型配置、临时关闭及显示当前吸附目标。

贝塞尔曲线需要支持原生曲线连接，不能只吸附到渲染近似线段。

重要规则：

吸附到同一位置不等于建立拓扑关系。只有通过明确操作和规则，才建立共享边界或其他拓扑关联。

## 13. Geometry Operations 与 Object Operations

采用两套独立但可以协同的操作体系。

### 13.1 Geometry Operations

负责 Geometry Components 的形状变化，不自动改变 Map Object 身份。

包括：

- Union：几何并集。
- Difference：几何差集。
- Intersection：几何交集。
- Split：几何拆分。
- Merge：几何组成部分合并。

### 13.2 Object Operations

负责地图对象身份、数量及语义关系变化。

例如：

- 将一个地图对象拆分为多个独立对象。
- 将多个对象合并为一个新对象。
- 对象身份变更及其关联关系处理。

几何操作不能擅自替代对象操作。

几何拆分不自动创建新的语义对象；几何合并不自动合并语义对象。

## 14. 布尔运算执行方式

采用非破坏性预览与明确应用。

执行流程：

1. 用户选择参与运算的几何。
2. 指定运算类型。
3. 系统生成临时运算结果。
4. 用户检查结果。
5. 系统检查几何有效性和共享边界影响。
6. 用户明确确认应用。
7. 系统写入正式几何变化并生成历史记录。

预览及取消不产生正式地图历史变化。

运算失败或验证不通过时，原始几何必须保持不变。

应用时允许根据具体操作选择替换原几何、增加几何组成部分等结果处理方式。创建新对象必须交由 Object Operations 明确处理。

曲线精度和共享边界拓扑需要得到保护。

## 15. Geometry Split 默认行为

采用方案 B：

**拆分结果替换原 Geometry Components，但保持 Map Object 身份不变。**

例如，一个国家原来拥有一个多边形 Component，用户将其拆分为三个部分：

- 原 Component 被拆分结果替换。
- 新的三个 Components 仍然归属于原国家对象。
- 国家对象 ID 不变。
- 国家名称、政治属性及对象关系不因几何拆分自动改变。

如果用户希望其中某一部分成为独立国家，需要进一步执行 Object Operations。

## 16. 历史剧本制作：以四渡赤水为案例

四渡赤水是检验 World View 地图制作能力的重要案例。

它不是一张静态路线图，而是一段具有时间顺序、地理环境、军事力量、行军路线和历史事件的动态历史叙事。

World View 应当能够让用户从基础地图开始，逐步制作完整的历史剧本。

### 16.1 建立历史地图

创建一张真实地理地图，设置适合展示的地图范围。

绘制或导入：

- 赤水河及相关河流。
- 山脉、丘陵和地形。
- 城镇、村庄及重要地理位置。
- 道路、渡口、桥梁。
- 其他重要地理环境。

真实地理地图需要地理参考定位能力，以保证导入底图、矢量对象和历史路线的位置一致。

### 16.2 建立剧本参与对象

创建红军、国民党军等相关军事力量对象。

需要支持：

- 军队名称及身份。
- 部队层级与所属关系。
- 重要人物及指挥关系。
- 部队标记和地图符号。
- 部队当前所在位置。
- 相关历史资料和说明。

这里需要注意：军事力量不能只是一组装饰图标。它们应该是具有独立身份和历史变化能力的地图对象。

### 16.3 建立历史时间轴

将剧本的历史时间范围设置为 1935 年相关时间段。

按真实历史资料建立时间节点。

每个时间节点可以关联：

- 一个或多个历史事件。
- 部队位置变化。
- 行军路线。
- 重要地点。
- 相关人物。
- 事件说明和资料来源。

时间轴负责组织历史进程，不要求用户编写复杂模拟规则。

### 16.4 编辑四次渡河行动

四次渡河行动分别作为可独立编辑的历史行动阶段。

每个阶段至少需要：

- 行动名称。
- 开始和结束时间。
- 起点和终点。
- 行军路线。
- 行进方向。
- 参与部队。
- 重要事件和地点。
- 历史说明。
- 相关地图状态变化。

路线需要是具有语义身份的对象，而不只是普通装饰线。

路线可以使用独立线几何表达，并支持箭头、方向、时间范围、颜色、线型和动画表现。

需要注意：历史路线应依据可靠史料绘制，不能因为视觉上连贯就自动推断实际行军路线。

### 16.5 时间推进与地图变化

当用户拖动时间轴时：

- 地图展示对应历史时间的有效状态。
- 部队位置随历史变化。
- 已发生的路线和事件可以保留或按展示策略显示。
- 尚未发生的事件可以隐藏或显示为预告。
- 已经发生的历史行动可以通过颜色、线型或状态区分。

具体采用哪种显示策略应由剧本展示配置决定，而不是修改历史事实本身。

地图状态变化仍遵循 World View 已有的 Command、State Change、Branch 和历史重建机制。

### 16.6 历史事件详情

用户点击地图上的事件标记时，可以查看：

- 事件名称。
- 发生时间。
- 发生地点。
- 参与部队及人物。
- 相关路线。
- 事件经过。
- 历史资料和引用来源。
- 事件前后地图变化。

事件、地图对象、时间轴和路线应当相互关联。

### 16.7 最终展示

完成编辑后，支持形成可交互的历史展示：

1. 按时间自动播放历史进程。
2. 用户手动拖动时间轴。
3. 点击事件查看详细说明。
4. 高亮某一部队及其行动路线。
5. 对比某一历史阶段之前和之后的地图状态。
6. 按阶段进行讲解和展示。

这使 World View 不仅能够制作地图，还能将地图作为历史叙事的核心媒介。

## 17. 产品设计原则

1. 地图制作是核心，历史剧本是地图能力的重要应用。
2. 地图对象的语义身份不能被几何操作自动改变。
3. 图层、几何、对象和历史是不同层次的概念。
4. 日常编辑应直观、即时，复杂历史机制不应侵占普通编辑体验。
5. 所有重要地图变化都应可追溯、可重建。
6. 用户不需要理解底层几何算法和拓扑实现，就能完成专业地图制作。
7. 历史展示必须能够还原时间、事件、路线和地图状态之间的关系。

- 几何运算对多个共享边界引用对象的影响。
- Undo/Redo 与编辑事务机制。
- 地图对象属性和关系编辑器。
- 地理环境、政治对象及 POI 的专业绘制工具。
- Raster 绘制与矢量对象的协作。
- 真实地理坐标、地图投影和地理参考导入。
- 历史剧本、时间轴、事件、路线及部队行动的完整产品模型。

## 附注：与已冻结 ADR 的核对（落档时记录，2026-11-19）

本基线与 ADR-001~005 及 Phase 2 领域模型核对，**未发现冲突**，属互补轨（本文件=地图编辑器/几何制作；Phase 2=历史状态引擎）。以下三个衔接点为后续设计必须兑现的接口，已列入待设计范围：

1. **共享边界一改多（§11）**：修改一条共享边界会影响所有引用对象 → 「一个 Command 产生多对象几何变化」是 P2-01 Command 模型尚未覆盖的新情形，需要在 Command 模型中补充该类命令的记录与重放方式。
2. **部队位置随时间变化（§16.2/§16.5）**：按 Phase 2 第一原则（World State 是计算结果），部队某时刻位置应为历史 Command 的计算结果，而非对象上的存储属性；§16.2「部队当前所在位置」应理解为编辑期视图，落档特此明确。
3. **时间轴播放（§16.5）**：剧本时间轴播放必须落在 ADR-003 的命令驱动 + 单线播放 + Branch 先选定框架内；§16.5 已声明遵循现有机制，后续剧本模型设计（§18 待设计项）兑现此约束。

另注：本基线 §18「Undo/Redo 与编辑事务机制」与 ADR-004（仅批量修复可撤销/重做）范围不重叠；未来设计编辑级 Undo/Redo 时，须与 ADR-004 的裁决划清边界，不得互相覆盖。
