# World View — Generation Session 与数据生命周期 V0.1

- 文档状态：阶段性设计提案
- 版本：V0.1
- 日期：2026-11-19
- 范围：生成会话、候选对象、差异集、批准与正式写入之间的生命周期边界

## 1. 设计目标

AI 生成过程可能持续较长时间，包含多个 Agent、多个阶段和多次局部修改。必须将生成过程与正式地图数据隔离，避免未审阅的模型输出直接改变地图。

为此引入 **Map Generation Session** 作为一次生成工作的生命周期容器。

## 2. 核心对象

### 2.1 Generation Session
代表一次用户发起或授权的地图生成工作。关联目标地图、发起者、权限上下文、规格版本、计划版本、任务和审计记录。

### 2.2 Generation Spec
记录用户意图的结构化版本。一个 Session 可经历规格修订，但必须明确当前采用的版本。

### 2.3 Generation Plan
记录阶段、任务、依赖、预算和验收条件。计划修订应保留版本差异。

### 2.4 Generation Task
代表可调度的工作单元，可由内置模型、外部 Agent 或确定性算法执行。

### 2.5 Candidate
尚未正式写入地图的候选对象、几何、属性、样式或关系。Candidate 使用会话内临时身份，不等同于正式 Map Object。

### 2.6 Validation Report
记录结构、几何、空间、语义和规格校验结果。

### 2.7 Change Set
表达候选结果相对于某一地图基准状态的拟议变更集合。

### 2.8 Approval Record
记录谁在何时批准、拒绝或要求修改哪些变更，以及批准所依据的 Change Set 版本。

## 3. 生命周期

推荐主流程：

1. `created`：Session 建立；
2. `specifying`：生成规格草案；
3. `planning`：制定生成计划；
4. `generating`：执行生成任务；
5. `validating`：执行校验；
6. `preview_ready`：生成预览和 Change Set；
7. `awaiting_approval`：等待人工处理；
8. `applying`：应用已批准变更；
9. `completed`：正式写入完成；
10. `failed / cancelled / stale`：失败、取消或上下文失效等终态/待处理状态。

上述为状态概念建议。最终状态机需定义迁移条件、重试路径、部分成功和多轮修订行为。

## 4. 与正式地图数据隔离

- Candidate 存储在生成工作区或等效隔离存储中。
- Candidate 不应被普通地图查询误认为正式 Map Object。
- Session 失败或取消不应导致正式地图回滚，因为它原则上尚未写入。
- 用户可以查看、比较、修改或丢弃候选结果。
- 候选结果可在受控条件下继续编辑或重新校验。

## 5. Change Set 语义

Change Set 必须绑定：
- 目标地图；
- 生成会话和规格版本；
- 计划版本；
- 生成时读取的地图基准版本/状态标识；
- 候选对象及操作集合；
- 校验报告；
- 保护对象清单；
- 批准范围和批准状态。

操作类型可包括新增、修改、删除对象，以及关系、图层和样式变化。删除必须显式列出，不允许通过缺少对象的方式隐式表达删除。

## 6. 预览后的并发冲突

预览完成到用户批准之间，地图可能被其他用户或任务修改。因此应用前必须：
1. 检查 Change Set 的基准状态是否仍有效；
2. 检查目标对象是否已被修改、删除或改变状态；
3. 识别冲突和可安全自动重算的内容；
4. 对无法安全合并的冲突阻止应用并要求重新预览或人工处理。

不得用旧候选结果覆盖更新后的正式地图。

## 7. 人工批准

- 默认正式写入需要人工明确批准。
- 批准应绑定具体 Change Set 版本和具体范围。
- Change Set 发生实质变化后，旧批准不得自动沿用。
- 用户可以拒绝全部、接受允许独立处理的部分，或要求重新生成。
- 后续如支持自动应用，必须另行定义受控策略、授权范围和审计要求；本版本不默认启用。

## 8. 正式应用与历史机制

Generation Session 不等于 Map Branch、正式版本或历史 Command。

批准后的 Change Set 交给 World View 正式写入服务：
- 由领域服务分配/确认正式对象身份；
- 执行领域规则和最终状态检查；
- 形成适当的正式地图操作；
- 遵循既有 Command、State Change、Branch、Checkpoint 和历史重建规则；
- 记录生成来源与人工批准的关联。

不得由 Generation Engine 另建一套与正式历史平行的地图状态系统。

## 9. 幂等与事务边界

- 每次应用请求应具备幂等保护，避免重复创建对象。
- 同一 Change Set 不得因网络重试重复应用。
- 应用结果应明确记录成功、部分成功或失败。
- 对需要原子性的变更集合，应在正式服务层定义事务边界。
- 如果无法整体原子应用，必须显式设计分组应用和补偿/恢复策略，不能假装整体成功。

## 10. 审计与追踪

至少记录：
- Session 发起者和时间；
- Spec、Plan 和 Task 版本；
- 使用的 Agent、模型或生成器标识（可用时）；
- 输入资料和来源；
- 候选内容版本；
- 校验结果；
- Change Set 差异；
- 批准、拒绝和修改记录；
- 正式应用结果及对应历史记录引用。

## 11. 数据保留与清理

候选数据、失败任务日志和生成产物的保留期限、归档与清理策略尚待确定。清理候选数据不得影响已正式写入的地图对象和历史记录。审计记录的保留策略应单独定义。
