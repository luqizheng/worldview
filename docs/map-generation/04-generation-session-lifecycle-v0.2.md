# World View — AI Map Task Session 与数据生命周期 V0.2

- 文档状态：修订版设计基线
- 版本：V0.2
- 日期：2026-11-20
- 范围：内置 AI Assistant 地图任务、候选结果、预览、确认和正式应用之间的生命周期边界
- 前序版本：V0.1（保留作为历史讨论记录）

## 1. 设计目标与定位

World View 内置 AI Assistant 的地图任务可能只需一次简单编辑，也可能持续较长时间，包含多阶段规划、资料读取、模型生成、确定性运算、校验和用户决策。

本文件定义复杂任务所需的生命周期和数据隔离原则。**Session 是后台任务生命周期记录，不是用户必须理解或管理的独立产品概念。**

简单、明确、低风险的地图操作可以直接通过领域服务完成，不必强制创建完整 Session、Candidate 和 Change Set。复杂生成或高影响变更则应使用足够的任务记录和候选隔离机制。

AI Assistant 是统一的用户交互入口。后台可以分阶段执行或并行处理，但不要求多个外部 Agent，也不允许外部 Agent 成为核心运行依赖。

## 2. 核心概念

### 2.1 AI Map Task Session

代表一次用户发起或授权的地图制作任务生命周期。关联目标地图、发起者、权限上下文、当前地图/Branch/时间上下文、任务规格、计划、步骤和必要审计信息。

Session 是任务管理记录，不等同于 Map Branch、正式版本或历史 Command。

### 2.2 Task Specification

记录用户意图的结构化任务依据。可对应独立 Spec 版本，也可以是简单任务的轻量内部描述。Spec 不属于正式地图数据。

### 2.3 Task Plan

记录复杂任务的阶段、步骤、依赖、资源约束和验收条件。简单任务可以没有独立 Plan 实体。

### 2.4 Task Step

代表一个可执行工作单元。可由内置 LLM、确定性算法或 World View 内部领域服务完成。实现上不要求每个 Step 都由独立 Agent 执行。

### 2.5 Candidate

尚未正式应用地图的候选对象、几何、属性、样式或关系。Candidate 使用任务内临时身份，不等同于正式 Map Object。简单的低风险操作可以不经过 Candidate。

### 2.6 Validation Report

记录结构、几何、空间、拓扑、语义、任务约束、来源和内容一致性检查结果。

### 2.7 Change Set

在需要预览、影响分析或用户确认时，表达候选结果相对于某一地图基准状态的拟议变更集合。不是每次地图编辑都必须生成 Change Set。

### 2.8 Decision / Approval Record

当某项操作确实需要用户确认时，记录用户对具体变更范围和版本的决定。普通低风险自动执行不需要人为制造审批记录，但仍应按系统策略保留必要操作审计。

## 3. 生命周期

复杂任务的推荐生命周期：

1. `created`：任务记录建立；
2. `understanding`：理解意图和上下文；
3. `planning`：按需制定计划；
4. `executing`：执行任务步骤；
5. `validating`：验证候选或操作结果；
6. `preview_ready`：需要预览时形成预览；
7. `awaiting_user_decision`：确需用户决策时等待；
8. `applying`：经授权向正式领域服务应用；
9. `completed`：任务目标完成；
10. `partially_completed`：部分目标完成；
11. `blocked / failed / cancelled / stale`：受阻、失败、取消或上下文失效。

简单任务可以跳过不适用阶段。状态名称是设计建议，最终状态机、迁移条件和恢复路径待技术设计确定。

## 4. 与正式地图数据隔离

- Candidate 存储在任务候选区或等效隔离机制中；
- Candidate 不得被普通地图查询误认为正式 Map Object；
- 任务失败或取消不应把未应用候选污染到正式地图；
- 用户可在适用场景下查看、比较、修改、重新验证或丢弃候选；
- 正式地图数据只能由 World View Domain Services 创建或修改；
- 任务记录和候选数据不能成为另一套正式地图状态系统。

对于已通过授权直接应用的低风险操作，正式结果按正常地图领域数据和操作历史保存，不需要伪造一个“候选已批准”的流程。

## 5. Change Set 语义

需要预览或用户确认时，Change Set 应绑定：

- 目标地图；
- 任务 Session 和 Spec 版本（如有）；
- Plan 版本（如有）；
- 生成时读取的地图基准状态标识；
- 候选内容和拟议操作；
- 校验报告；
- 保护对象和影响范围；
- 决策状态及其对应版本（如需要）。

操作类型可包括新增、修改、删除对象，以及关系、图层和样式变化。删除必须显式列出，不得通过候选中缺少某对象来隐式表达删除。

## 6. 预览后的并发冲突

预览完成到正式应用之间，地图可能被用户或其他任务修改。因此应用前必须：

1. 检查 Change Set 的基准状态是否仍有效；
2. 检查目标对象是否已被修改、删除或改变状态；
3. 识别冲突和可安全重新计算的内容；
4. 对无法安全处理的冲突阻止应用，并要求重新预览或人工处理。

不得用旧候选结果覆盖更新后的正式地图。重新计算后若变更实质发生变化，先前针对旧版本的用户确认不得自动沿用。

## 7. 用户决策

不是所有正式地图写入都必须逐项人工批准。是否需要确认由操作风险、影响范围、可逆性、语义重要程度和用户授权范围共同决定。

需要用户决策时：

- 决策绑定具体 Change Set 版本和具体范围；
- 用户可以接受、拒绝或要求修改；
- 允许独立处理的变更可支持部分接受；
- 变更实质变化后，旧决策失效；
- 用户授权自动执行的范围必须明确并可审计；
- 任何自动执行都不能绕过权限、领域校验和历史规则。

## 8. 正式应用与历史机制

批准或已获授权的变更交给 World View 正式领域服务：

- 由领域服务分配或确认正式对象身份；
- 执行领域规则和最终状态检查；
- 形成适当的正式地图操作；
- 遵循 Command、State Change、Branch、Checkpoint 和历史重建规则；
- 记录任务来源、必要的用户决策和正式历史记录之间的关联。

Generation/AI Task Session 不等于 Map Branch、正式版本或历史 Command。不得由 AI Task Engine 另建一套与正式历史平行的地图状态系统。

任务取消不自动撤销已经正式应用的内容。撤销已应用内容应通过地图编辑器 Undo/Redo 或相应正式领域操作处理。

## 9. 幂等与事务边界

- 正式应用请求应具备幂等保护，避免重试导致重复创建对象；
- 同一 Change Set 不得因网络重试重复应用；
- 应用结果应明确记录成功、部分成功或失败；
- 需要原子性的变更集合，其事务边界由正式领域服务定义；
- 如果无法整体原子应用，必须明确分组应用和补偿/恢复策略，不能将部分成功伪装成整体成功；
- 任务步骤重试不得绕过对象状态和权限复核。

## 10. 审计与追踪

按任务复杂度和风险记录必要信息：

- Session 发起者和时间；
- 地图、Branch 和时间上下文；
- Spec、Plan 和 Task Step 版本（如有）；
- 使用的模型、内部工具或算法标识（可用时）；
- 输入资料和来源；
- 候选内容版本（如有）；
- 校验结果；
- Change Set 差异（如有）；
- 用户确认、拒绝或修改决定（如有）；
- 正式应用结果及对应历史记录引用。

审计记录应区分 AI 提议、领域服务执行结果和用户决策，不能把模型输出记录成已成功写入。

## 11. 数据保留与清理

候选数据、失败任务日志和生成产物的保留期限、归档与清理策略尚待确定。清理候选数据不得影响已正式写入的地图对象、历史记录和必要审计信息。审计记录的保留策略应单独定义。
