## 1. 文档目的与使用规则

本文档汇总 D01 系列跨多个对话形成的讨论结果，建立统一的阶段性讨论基线。

本文档的目的：

1. 保存用户已经表达的架构选择和产品意图。
2. 统一 Command、State Change、World State、Branch、Historical Time 等概念。
3. 记录后续修正，避免继续沿用已经被推翻的方案。
4. 为后续 P2-01 Domain Model 修订提供依据。
5. 为未来正式 ADR 和实施任务提供输入。

### 1.1 裁决状态

本文档中的结论属于讨论阶段的人工选择，尚未经过完整的正式架构审查。

因此：

- 不等于 Phase 2 已经冻结。
- 不等于已经批准开发实施。
- 不得将助手提出但用户没有选择的建议视为用户裁决。
- 后续正式文档应以本文档为讨论依据，并继续进行一致性审查。

### 1.2 核心产品定位

World View 是世界观与历史地图创作软件，不是自动经营世界的游戏，也不是复杂世界模拟器。

软件的主要职责：

- 帮助作者表达历史设计。
- 根据作者的设计重建世界历史。
- 检查设计中的冲突和不合理之处。
- 解释错误产生的原因。
- 提供有限、明确的修复建议。

软件不能：

- 擅自修改作者的创作意图。
- 为了让历史继续执行而自动改变用户命令。
- 自动补充作者没有设计的历史行为。
- 把软件建议当成用户已经接受的设计。

核心原则：

**软件负责检查、解释和建议；作者负责创作决策。**

# 2. Command 与 State Change

## 2.1 D01-01：基本关系

阶段性选择：C。

Command 是用户创作行为的权威历史记录。

State Change 表达 Command 所产生的状态变化语义，是历史重建过程中可以解释或产生的派生结果。

World State 是按照历史时间解释并执行 Command 后得到的世界状态。

三者关系：

- Command：作者希望世界发生什么变化。
- State Change：这些操作所表达或产生的状态变化。
- World State：执行历史操作后，在某个时间点得到的世界状态。

不要求 Command 和 State Change 固定一对一对应。

一条 Command 可以：

- 不产生实际状态变化。
- 产生一个状态变化。
- 产生多个阶段性状态变化。

State Change 不自动成为第二套独立的用户创作历史。

## 2.2 D01-02：State Change 的生成方式

阶段性选择：C。

Command 只保存操作本身。

State Change 的语义可以根据 Command 类型解释，也可以由一条 Command 表达多个状态变化。

不要求每条 Command 固定生成一个或固定数量的 State Change。

## 2.3 D01-03：持续 Command

阶段性选择：C。

Command 可以持续一段历史时间。

例如：

`cmd(第一军团, move, 目标位置, duration=3 days)`

系统可以在持续执行过程中产生多个阶段性 State Change。

这些阶段性结果：

- 属于可重建的派生数据。
- 不成为独立的用户历史命令。
- 不改变 Command 作为权威记录的地位。

动画帧和视觉插值不等于 State Change。

必须区分有历史意义的状态变化与纯粹视觉表现。

## 2.4 D01-04：派生结果重建一致性

阶段性选择：C。

Command 是权威记录，同时可以保存必要的执行依据或可验证派生结果。

重建时必须优先保证历史一致性。

不能因为算法升级而悄悄改变既有历史。

算法可以升级，但必须避免旧历史在没有明确处理的情况下产生不同结果。

具体执行上下文、规则版本、算法版本及派生结果的精确保存模型仍待设计。

# 3. Command 执行失败与用户意图

## 3.1 D01-05：执行条件失效

用户明确选择：

Command 无法执行时，系统发出警告，让用户自己处理。

软件是创作软件，应该帮助作者发现设计中的不合理，而不是擅自解决创作问题。

因此：

- 不自动修改路线。
- 不自动延长时间。
- 不自动改变目标。
- 不自动寻找替代方案并直接执行。
- 不自动改变用户 Command。

## 3.2 D01-06：执行条件恢复

阶段性选择：B。

条件恢复后，系统提示用户原 Command 已经具备继续执行的条件。

必须由用户确认后才能恢复。

不允许自动恢复。

后续关于历史修复和重新重建的规则，进一步明确：用户修复的是历史设计，系统需要重新计算受影响的历史，而不是把修复操作当成新的历史时间事件。

## 3.3 D01-07：历史修改后的旧警告

阶段性选择：B。

保留旧警告记录。

当原异常条件不再成立时：

- 将旧警告标记为已解决。
- 不直接删除警告。
- 保留警告产生原因。
- 保留警告解决原因。

需要区分历史发生时间和软件诊断时间。

## 3.4 D01-08：修改已有 Command

阶段性选择：A。

用户直接修改原 Command。

Command 不需要保留版本，不建立 Command Revision 链。

修改意味着作者修正原有创作内容，不是向世界历史追加一个新的命令。

修改后需要重新计算受影响的派生结果、World State、警告和 Branch。

不保留 Command 内容版本，不代表删除所有诊断记录。

## 3.5 D01-09：父地图 Command 修改与 Branch

阶段性选择：A。

父地图 Command 修改后，自动继承修改并重建所有受影响的 Branch。

如果修改导致 Branch 自己的 Command 无法执行：

- 产生警告。
- 不擅自修改 Branch 自己的 Command。

Branch 是父地图历史的动态继承关系，不是创建时刻的静态历史快照。

## 3.6 D01-10：Branch 后续 Command 执行失败

原始讨论选择 C：

按依赖关系停止，无法执行的 Command 及依赖它的后续 Command 受阻；不依赖它的 Command 可以继续执行。

**后续修正：**

D01-58 和 D01-59 改变了完整历史重建的错误处理方式。

最终阶段性规则是：

- 完整历史重建遇到第一个执行错误，立即停止后续重建。
- 不再继续执行无关的后续 Command。
- 不生成错误位置之后的有效 World State。
- 可以保留失败原因和依赖关系等必要诊断信息。

因此，D01-10 原先的“无依赖 Command 仍可继续执行”不再适用于完整历史重建流程。

# 4. Command 依赖与路线

## 4.1 D01-11：Command 依赖关系

阶段性选择：B。

依赖关系来源包括：

1. 用户显式指定的依赖。
2. 系统执行时发现的隐式依赖。

隐式依赖例如：

- 行军路线经过桥梁。
- 移动受到地形影响。
- 行动受到道路状态影响。
- 操作受到其他对象状态影响。

依赖关系可以动态发现。

系统需要能够解释依赖链。

依赖关系属于可重建派生信息，不是第二套权威历史。

## 4.2 D01-12：移动路线确定方式

阶段性选择：C。

用户可以：

- 自己指定路线。
- 让系统计算建议路线。

系统不能擅自改变用户指定路线。

系统建议路线与用户接受后的路线必须区分：

- 建议路线：候选结果，不改变 Command。
- 用户接受：路线纳入 Command。
- 用户直接指定：路线直接成为 Command 的执行依据。

## 4.3 D01-13：修改已指定路线

阶段性选择：A。

用户修改 Command 的路线后：

- 从该 Command 开始时间起重新计算派生结果。
- 旧派生结果失效。
- 重建受影响的 World State。
- 重新评估依赖命令。
- 重新检查警告。
- 重建受影响 Branch。

不保留旧路线作为另一份世界历史。

## 4.4 D01-14：修改 Command 历史时间

阶段性选择：A。

修改 Command 的历史时间后，从新旧时间中较早的时间开始重建受影响历史及 Branch。

这个时间点是重建起点，不意味着必须从地图初始时间全部重新计算。

## 4.5 D01-15：删除 Command

阶段性选择：A。

删除 Command 只删除该 Command 本身。

不自动删除依赖它的其他 Command。

依赖它的命令保留并重新评估，必要时产生警告。

受影响的派生 State Change 失效，并重建受影响的 World State 和 Branch。

旧警告可能重新变成有效，需要重新诊断。

## 4.6 D01-16：任意历史时间插入 Command

阶段性选择：A。

允许在任意历史时间插入新 Command。

插入后：

- 从最早受影响的时间重建。
- 后续 Command 保留。
- 按依赖关系重新评估。
- 重建受影响 Branch。

历史时间是创作内容的组织维度，不是用户操作顺序。

# 5. 同一历史时间的顺序规则

## 5.1 D01-17：同一时间多个 Command 的顺序

阶段性选择：B。

用户可以指定顺序。

用户没有指定时，系统自动排序。

## 5.2 D01-18：自动排序原则

阶段性选择：C。

先根据依赖关系排序。

无法确定时，再使用固定规则处理不影响结果的技术性排序。

如果存在歧义，需要警告。

固定规则不能代替用户决定会改变世界状态的语义歧义。

## 5.3 D01-19：顺序歧义处理

阶段性选择：B。

当不同顺序会产生不同结果，且无法判断用户意图时：

- 暂停相关 Command。
- 等待用户指定顺序。
- 不影响其他无依赖关系的 Command 的独立诊断。

但根据 D01-58、D01-59，完整历史重建仍采用遇到第一个错误即停止的规则。

## 5.4 D01-20：用户指定顺序的保存

阶段性选择：A。

保存为两个 Command 之间的显式顺序约束。

后续其他 Command 插入时，尽量遵守该约束。

不是只保存当前排序结果，也不是单纯保存编号。

## 5.5 D01-21：时间精度模型

阶段性选择：B。

每条 Command 可以选择时间精度，最高支持到秒。

精度不足时，同一时间范围内仍需要通过顺序约束解决冲突。

时间精度不同不代表优先级不同。

## 5.6 D01-22：不同时间精度的排序

阶段性选择：B。

优先根据已有依赖关系推断先后。

没有足够依赖依据时，要求用户裁决。

不能简单地因为某条 Command 使用年份精度，就将其自动排在具体日期时间之前。

## 5.7 D01-23：时间修改导致顺序约束冲突

阶段性选择：B。

保留用户指定的顺序约束。

时间信息与顺序约束冲突时：

- 发出警告。
- 暂停相关 Command。
- 等待用户处理。
- 不自动删除顺序约束。
- 不影响无关 Command 的独立诊断。

完整重建时仍遵守 Fail-Fast 规则。

## 5.8 D01-24：循环顺序约束

阶段性选择：B。

允许保存造成循环的新约束。

发现循环后：

- 标记为冲突。
- 暂停循环中的 Command。
- 暂停依赖它们的后续 Command。
- 不擅自删除用户约束。
- 不影响其他无依赖关系 Command 的独立诊断。
- 用户解除循环后重建受影响历史。

## 5.9 D01-25：删除顺序约束

阶段性选择：B。

用户删除一条顺序约束后：

- 重新检查显式依赖。
- 重新检查隐式依赖。
- 如果仍可确定顺序，就继续。
- 如果存在影响结果的歧义，则警告并暂停相关 Command。

## 5.10 D01-26：Branch 继承顺序约束

阶段性选择：A。

顺序约束属于父地图历史，Branch 自动继承。

Branch 可以增加自己的顺序约束。

父地图修改约束后，受影响 Branch 动态重新评估和重建。

## 5.11 D01-27：父地图约束与 Branch 自有约束冲突

阶段性选择：B。

保留父地图和 Branch 的全部约束。

发生循环或冲突时：

- Branch 标记冲突。
- 暂停相关 Command 及依赖链。
- 等待用户处理。
- 不自动删除 Branch 自有约束。
- 不冻结整个 Branch 的创作能力。

完整重建仍受 Fail-Fast 规则约束。

## 5.12 D01-28：Branch 是否允许覆盖父地图顺序约束

用户明确选择：

Branch 不允许覆盖或改写继承来的父地图历史顺序约束。

即使用户主动希望改变继承来的顺序，也不允许直接在 Branch 内 override。

但允许增加一个独立功能：

**将父分支与当前子分支组合成一张新地图。**

组合地图不是 Branch 内部覆盖，也不是 Git 式 Merge，需要独立设计。

阶段性选择：A。

> **已被后续裁决修正（2026-11-19，D01-74）**："继承父地图完整历史，再吸收子地图全部新增历史"的表述过于宽泛。修正后的整合模型：只采用父地图**截至分叉点**的最新有效历史（`C = A_latest(<=1200) + B_own(>1200)`），**不吸收**父地图分叉点之后的 Command。当前整合语义见第 16 章 D01-74。以下原文保留，未作删除。

组合地图继承父地图完整历史，再吸收子地图分支后的全部新增历史，形成新的独立历史。

不是只取某个时间点作为初始状态，也不是要求用户逐条挑选历史。

组合结果不是运行时动态引用源地图，而是独立历史。

## 6.2 D01-30：父地图分支后继续发展

阶段性选择：A。

> **部分修正（2026-11-19，D01-74）**：下方示例中"继承 A 的完整历史，并吸收 B 的分支新增历史"不再准确——A 在分叉点（1050 年）**之后**新增的历史（如第 1070 年 Command）**不纳入**组合结果 C。历史采用 Copy 而非 Reference、来源追溯、组合后相互独立等其余结论继续有效。以下原文保留，未作删除。

示例：

- B 在 A 的第 1050 年历史点分支。
- B 增加第 1060 年 Command。
- A 后来又增加第 1070 年 Command。
- 组合地图 C 时，继承 A 的完整历史，并吸收 B 的分支新增历史。

历史采用 Copy，不是 Reference。

组合完成后：

- A 的后续修改不影响 C。
- B 的后续修改不影响 C。
- C 的修改不影响 A、B。
- C 是独立历史。

保存来源追溯信息，但来源追溯不等于运行时引用。

## 6.3 D01-31：组合地图的历史冲突

阶段性选择：A。

组合时自动排序。

发生冲突时：

- 发出警告。
- 仍允许创建新地图。
- 不擅自修改原 Command。

结合 D01-19 和后续 Fail-Fast 规则：

允许创建组合地图，不代表所有历史都成功执行。

无法确定且存在结果歧义的相关 Command 仍需暂停，不能假装生成了完整有效历史。

## 6.4 D01-32：组合地图是否保留 Branch 关系

阶段性选择：B。

新地图 C 保存：

- 来源地图 A、B 的身份信息。
- 组合时的来源关系。
- 历史来源追溯信息。

但 C 是独立 Copy，不再是 A 或 B 的 Branch，没有运行时继承关系。

## 6.5 D01-33：组合地图中的 Command ID

阶段性选择：B。

C 中每条 Command 生成新 ID。

同时记录：

- 原始来源地图 ID。
- 原始来源 Command ID。

来源 ID 只用于历史追溯，不构成运行时依赖。

C 中的 Command 可以独立修改和删除。

## 6.6 D01-34：组合地图中的顺序约束 ID

阶段性选择：A。

每条复制过来的顺序约束生成新 ID。

引用重新映射到 C 中的新 Command ID。

保存原始来源约束 ID 用于追溯，不引用源地图原始约束。

## 6.7 D01-35：组合时依赖关系的复制

阶段性选择：C。

只复制显式依赖。

复制时：

- 重新分配依赖 ID。
- 重新映射 Command 引用。

隐式依赖是可重建派生信息，不直接复制。

在新地图中重新发现和验证隐式依赖。

来源追溯可以保留，但不构成运行时引用。

## 6.8 D01-36：组合地图中的执行依据

阶段性选择：C。

Command 本身完整复制并生成新 ID。

用户明确指定的参数和执行依据随 Command 复制，例如用户指定的移动路线。

系统自动计算的内容不作为权威数据直接复制，包括：

- 自动计算路线。
- 隐式依赖关系。
- 阶段性 State Change。

新地图需要重新验证执行条件。

如果原执行依据在新地图中不再成立：

- 产生警告。
- 不擅自修改用户指定内容。
- 保留必要的来源追溯信息。

# 7. Historical Time 与 Calendar

## 7.1 D01-37：内部时间模型

阶段性选择：B。

用户提出：地图系统内部日期应当从第 0 天开始，以累计天数持续记录；显示出来是什么属于显示问题。

因此：

- 内部历史时间与日历显示分离。
- 内部时间不依赖公元纪年、月份、闰年和年号。
- 不同日历是同一内部时间的不同显示表达。
- 不同来源时间体系在组合地图时需要明确时间映射转换。
- 时间精度最高支持秒。
- 内部存储避免浮点精度误差。

具体数值存储方案仍需技术设计。

## 7.2 D01-38：地图第 0 天

阶段性选择：C。

每张地图独立定义自己的第 0 天。

组合地图时，允许用户建立来源地图到新地图的时间轴映射。

不默认共享时间原点。

## 7.3 D01-39：Branch 时间轴

阶段性选择：A。

Branch 完全继承父地图时间轴，包括第 0 天定义。

Branch 不允许独立改变时间轴或第 0 天。

组合地图可以有独立时间轴及来源时间映射。

## 7.4 D01-40：日历显示规则

阶段性选择：C。

每张地图有一种默认日历。

同时允许显示其他辅助日历。

所有日历都是同一内部累计时间的不同表达。

切换日历不改变 Command 执行顺序或历史内容。

## 7.5 D01-41：用户自定义日历

阶段性选择：C。

第一版支持基本自定义：

- 一年天数。
- 月份结构。
- 纪年起点。
- 简单闰年规则。

复杂天文周期、多个太阳/月亮周期联动等以后扩展。

## 7.6 D01-42：默认日历按历史时间分段生效

阶段性选择：B。

默认日历可以按历史时间区间生效。

允许在历史时间线上发生历法改革。

日历改革只改变日期解释，不改变内部累计天数或 Command 执行时间。

## 7.7 D01-43：日历改革与 Command

阶段性选择：C。

日历改革既可以作为一条 Command 记录，也有独立的 Calendar Configuration。

- Command 表达历史行为。
- Calendar Configuration 表达具体历法规则。
- Command 执行可以触发日历配置在指定历史时间生效。

## 7.8 D01-44：删除日历改革 Command

阶段性选择：A。

删除日历改革 Command 时，自动删除其对应的新历法配置，恢复旧历法。

日历改革 Command 与对应 Calendar Configuration 建立明确关联。

修改改革 Command 生效时间时，重新计算配置生效区间，后续日历显示重新计算。

用户手动创建、但未通过该 Command 启用的独立日历配置，不受影响。

## 7.9 D01-45：日历改革追溯生效

阶段性选择：A。

允许追溯修改日历改革的生效时间。

由于事件和 Command 的内部时间都使用累计天数：

- 修改日历改革生效时间不影响其他历史数据。
- 不改变 Command 内部时间。
- 不改变 State Change 执行时间。
- 不改变事件先后关系。
- 不需要重建 World State。
- 只需重新计算受影响时间区间的日历显示。

内部 Historical Time 是权威数据，Calendar Date 是显示表达。

## 7.10 D01-46：内部时间数值表达

阶段性选择：C。

使用整数天数 + 当天内的时间偏移表达内部时间。

例如：

`day=1, offset=43200 seconds`

表示第 1 天中午。

建议当天内偏移使用整数秒，避免浮点精度误差。

未来更高精度可扩展，尚未独立裁决。

## 7.11 D01-47：Command 的时间表达

阶段性选择：C。

瞬时 Command 只有一个历史时间点。

持续 Command 有开始时间和结束时间。

持续时间可以由开始时间 + 持续时间计算，也可以由开始时间 + 结束时间确定。

持续 Command 可以产生多个阶段性 State Change，它们是可重建派生结果。

## 7.12 D01-48：持续 Command 暂停时的结束时间

阶段性选择：B。

最初讨论中，暂停时保留原开始时间和结束时间。

用户可以手动修改结束时间，系统不自动修改。

修改结束时间后，重新计算剩余阶段及受影响历史。

**D01-49 对暂停时间的后续纠正必须同时考虑。**

## 7.13 D01-49：持续 Command 暂停期间的历史时间

用户纠正了此前“暂停期间仍然消耗行动时间”的解释。

最新阶段性规则：

- 世界历史时间继续推进。
- 当前持续 Command 自身的执行时钟和行动进度暂停。
- 暂停期间不消耗剩余行动时间。
- 恢复时从暂停时的进度继续。
- 预计完成时间应考虑暂停造成的顺延。
- 用户可以手动修改结束时间。
- 系统不得擅自修改用户的结束时间。

示例：

- 第 100 天开始。
- 原计划需要 3 天。
- 第 101 天暂停。
- 第 105 天恢复。
- 剩余 2 天。
- 预计第 107 天完成。

这里暂停的是持续 Command 自身的执行时间，不是整个世界的全局历史时间。

# 8. 持续 Command、暂停与路线修复

## 8.1 D01-50：暂停时目标对象的状态

阶段性选择：A。

例如军团已经走完一半路线，因为桥梁被摧毁而暂停：

- 保留暂停时最后一个有效位置。
- 军团停留在那里。
- 不回滚到 Command 开始前的位置。
- 不把位置变成未知。
- 恢复后从暂停时的位置和进度继续。

## 8.2 D01-51：单条 Command 遇到执行障碍

阶段性选择：B。

用户强调，必须区分作者明确设计的等待行为与系统擅自补充的等待行为。

情况一：作者明确设计三条 Command：

1. 军团移动到断桥处等待。
2. 军团驻扎，等待桥梁恢复。
3. 军团从驻扎地移动到目标。

系统应按作者明确设计的三条命令执行。

情况二：作者只设计一条从当前位置移动到目标的 Command，但路线遇到断桥。

系统不能擅自解释成：

- 自动停在桥边。
- 自动驻扎。
- 自动等待桥梁恢复。
- 自动继续前进。

正确行为：

- 发现命令无法执行。
- 终止该 Command 的播放。
- 通知用户障碍及原因。
- 等待用户处理。

核心原则：

**系统不能替作者补充没有设计的历史行为。**

## 8.3 D01-52：恢复后原路线失效

阶段性选择：C。

如果等待条件恢复，但原路线已经不可用：

1. 系统重新检查原路线。
2. 原路线失效时，自动计算替代路线作为建议。
3. 向用户展示原路线失效原因和替代路线。
4. 不修改原 Command。
5. 不自动接受替代路线。
6. 用户确认后，才将新路线写入 Command。

允许自动计算建议路线，不允许自动修改用户指定路线或自动恢复执行。

## 8.4 D01-53：撤销原问题

此前曾讨论“路线改变后执行时间如何处理”，但该问题建立在把历史修复误解为现实时间继续推进的前提上。

用户明确纠正：

World View 是设计软件。

用户发现冲突后开始修复，修复完成后，冲突不应继续存在。系统应重新从原历史时间执行新的设计方案。

因此撤销原 D01-53 的 A/B/C 选择题，不保留“105 天确认”这一概念。

正确理解：

- 第 100 天开始执行。
- 第 101 天发现执行冲突。
- 用户修复历史设计。
- 系统从第 100 天重新执行。
- 再次检查整个执行过程。

修复不是追加一个新的历史事件。

## 8.5 D01-54：冲突修复后的后续历史

阶段性选择：A。

用户修复历史冲突后：

- 从最早受影响的历史时间重新执行。
- 自动重新执行所有受影响的后续 Command。
- 根据依赖关系确定执行顺序。
- 无法执行的 Command 产生错误。
- 不擅自修改后续 Command。
- 重新评估受影响的 World State、派生 State Change、警告和 Branch。

## 8.6 D01-55：后续 Command 执行失败后的诊断

阶段性选择：C。

系统提供：

1. 失败信息。
2. 具体失败原因。
3. 相关依赖链。
4. 针对问题的修复建议。
5. 由用户决定是否采用修复建议。

## 8.7 D01-56：修复建议的范围

阶段性选择：A。

修复建议只针对每条失败的 Command 单独提出。

不主动分析整条受影响依赖链并生成一套相互协调的整体修复方案。

但是系统仍需展示依赖链和问题来源。

区分：

- 诊断范围：可以展示完整依赖关系。
- 修复建议范围：只针对当前失败的 Command。

## 8.8 D01-57：修改 Command 后仍然失败

阶段性选择：A。

用户修改 Command 后，即使重新执行仍然失败：

- 保留用户修改后的 Command。
- 标记执行失败。
- 持续显示警告或错误。
- 保留失败原因。
- 允许用户继续编辑其他历史。
- 不自动回滚用户修改。
- 后续修复后重新计算受影响历史。

软件不能擅自撤销作者的创作决定。

# 9. 编译器式历史重建

## 9.1 D01-58：执行失败后的时间线处理

阶段性选择：B。

用户明确提出，World View 的历史重建更像编译软件。

基本工作方式：

1. 用户编写历史 Command。
2. 系统按历史时间检查并重建。
3. 发现错误，停止后续重建。
4. 报告错误及原因。
5. 用户修改设计。
6. 系统重新重建。
7. 直到所有 Command 成功执行，得到完整历史结果。

错误之后的历史：

- 不展示为有效的执行结果。
- 即使后续 Command 没有直接依赖失败 Command，也不能将它们的结果作为完整有效历史展示。
- 不删除后续 Command。
- 不代表后续 Command 本身全部有错误。
- 只是当前完整历史重建尚未成功。

## 9.2 D01-59：遇到第一个错误后的检查策略

阶段性选择：B。

一旦遇到第一个无法执行的 Command：

- 立即停止所有后续检查。
- 不继续检查后续 Command。
- 只报告当前第一个错误。
- 用户修复后重新执行。

用户明确表示，不需要建立过于复杂的多错误报告体系。

因此采用简单的 Fail-Fast 方式。

不引入复杂的：

- 并行错误收集。
- 多错误关联。
- 批量错误诊断。
- 整体依赖链自动协调修复。

## 9.3 D01-60：修复后的重建起点

阶段性选择：B。

默认从刚刚修复的错误所在时间开始重建，尽可能复用此前成功的结果。

用户补充：

- 可以拉动播放条选择历史时间点。
- 可以修改某个播放点的内容。
- 修改后重新播放。

需要区分：

**播放起点：** 用户主动选择从哪个历史时间开始观看。

**重建起点：** 系统根据修改影响范围确定必须从哪里重新计算。

用户选择播放起点，不代表系统可以忽略更早的未解决历史错误。

如果更早修改实际影响更早时间，则仍需从实际最早受影响位置重建。

## 9.4 D01-61：播放条遇到历史错误

阶段性选择：A。

播放条只能播放到最近一次成功重建的时间点。

如果第 105 天发生 Command 执行错误：

- 第 105 天之前已成功重建的历史可以播放。
- 第 105 天显示错误。
- 第 105 天之后不能播放未经验证的历史结果。
- 用户修复并重新重建后，播放范围才向后扩展。

播放条展示的是当前已经成功重建的可信历史范围。

## 9.5 D01-62：Command 修改后的重建触发

阶段性选择：B。

用户可以连续修改多条 Command，不立即自动重建。

由用户主动点击“重新播放 / 重建”后，系统统一执行：

1. 确定最早受影响的历史时间。
2. 复用此前仍然有效的结果。
3. 从重建起点开始按顺序执行 Command。
4. 遇到第一个错误立即停止。
5. 展示错误和修复提示。
6. 用户继续修改后，再次主动重建。

## 9.6 D01-63：未重建修改期间的播放

阶段性选择：B。

只要用户修改了 Command，但尚未重新重建：

- 暂停时间线播放。
- 不允许继续播放旧的重建结果。
- 提示用户存在尚未验证的修改。
- 用户主动点击“重新播放 / 重建”后，才恢复播放能力。
- 重建失败则停留在错误位置，等待用户修复。

播放结果必须与当前创作内容保持一致，不能让用户误以为旧结果代表最新设计。

## 9.7 D01-64：重建状态

阶段性选择：A。

界面明确区分三种状态：

| 状态 | 含义 |
|---|---|
| 未重建 | 用户已修改内容，但尚未重新验证 |
| 重建失败 | 已经执行重建，但发现错误并停止 |
| 重建成功 | 当前创作内容已成功完成历史重建 |

三种状态不能混淆：

- 未重建不代表设计有错误。
- 重建失败意味着已经发现具体问题。
- 重建成功意味着当前历史已通过执行检查。

# 10. World State 缓存与 Checkpoint

> **补充（2026-11-19，D01-72）**：Checkpoint **按 Branch 归属**，保存该 Branch 指定历史时间点的完整合成 World State（祖先继承状态 + Shared Object 在该 Branch 的有效状态 + 局部对象 + 自有 Command 执行结果）；祖先历史修改使受影响 Checkpoint 失效并重新生成。见第 16 章 D01-72。本章 D01-65~69"派生缓存、非权威"的定位不变。

## 10.1 D01-65：重建结果是否保存

**最终修正选择：B。**

此前选择 A，后来用户明确要求改为 B。

最终阶段性规则：

- Command 是唯一权威历史数据。
- World State 重建结果允许保存为缓存。
- 播放时优先读取可用缓存，提高性能。
- 缓存不是权威数据。
- 缓存可以删除和重新生成。
- Command 或初始状态发生变化时，相关缓存失效。
- 缓存丢失不影响历史数据完整性。

明确边界：

**保存计算结果，不等于保存第二套权威历史。**

## 10.2 D01-66：Checkpoint 检查点机制

阶段性选择：B。

允许建立可重建的 Checkpoint，加速历史定位和播放。

规则：

1. 系统可以在历史时间线上建立检查点。
2. 用户跳转到某个历史时间时，从最近的有效检查点继续计算。
3. Command 是权威历史数据。
4. Checkpoint 是派生缓存，不是独立历史。
5. Command 修改后，受影响的后续 Checkpoint 失效。
6. Checkpoint 丢失时可以重新计算。
7. Checkpoint 不得改变历史重建结果。

## 10.3 D01-67：Checkpoint 建立位置

阶段性选择：A。

由系统自动决定 Checkpoint 的建立位置。

系统根据：

- 历史长度。
- Command 数量。
- 计算成本。

判断检查点位置。

不要求用户手动管理检查点。

## 10.4 D01-68：失效 Checkpoint 的处理

阶段性选择：A。

Command 修改导致后续 Checkpoint 失效时：

1. 立即删除所有受影响的 Checkpoint。
2. 保留不受影响的有效 Checkpoint。
3. 用户主动重新重建时，系统重新生成需要的 Checkpoint。
4. 不保留失效 Checkpoint，避免误用旧结果。

## 10.5 D01-69：Checkpoint 保存范围

阶段性选择：A。

Checkpoint 保存指定历史时间点的完整 World State。

包括该地图在该时间点的完整合成状态。

例如包含：

- Shared Object 状态。
- Map-local Object 状态。
- Branch 继承的对象状态。
- 其他构成该地图 World State 的必要状态。

读取时直接恢复完整状态，不需要每次重新合成父地图、共享对象和地图局部状态。

# 11. 创作工程与发布作品

在 D01-69 讨论中，用户提出：

如果作者发布地图给其他用户查看，发布作品是否不包含 Command？

讨论后形成以下阶段性产品方向。

## 11.1 创作工程

创作工程是作者继续创作和编辑的完整工程数据。

可能包含：

- 初始地图数据。
- Command 及其顺序约束。
- Branch 和历史关系。
- 日历配置。
- 地图资源。
- 可选的 Checkpoint 缓存。
- 其他创作所需数据。

Command 是创作工程中的权威历史数据。

## 11.2 发布作品

发布作品是从创作工程生成的只读交付物。

可以不包含 Command。

发布作品可以包含：

- 已经重建的地图状态。
- 地图资源和展示所需数据。
- 日历及历史时间显示信息。
- 历史播放所需的状态数据。

**不包含 Command，不代表不包含历史。**

例如作者发布一张从公元 1000 年到 1500 年的地图，其他用户仍然可以拖动时间轴观看历史变化。

为实现这一点，发布作品需要携带足够的派生结果，例如历史时间点的状态数据或可播放的历史状态序列。

作者可以不公开内部 Command、创作过程和设计逻辑。

## 11.3 当前确定的边界

阶段性产品方向：

**发布作品是从创作工程生成的只读交付物，不是创作工程本身。**

但以下内容尚未讨论：

- 发布作品的具体文件格式。
- 历史状态序列的存储结构。
- 历史播放数据的压缩策略。
- 发布版本与源工程的关联方式。
- 发布作品是否支持离线下载、复制或二次分发。
- 发布作品的更新和撤回机制。

这些内容不属于本轮 D01 已裁决范围。

# 12. 当前统一架构认识

根据 D01-01 至 D01-69，形成以下阶段性模型。

## 12.1 权威数据与派生数据

| 对象 | 阶段性定位 |
|---|---|
| Command | 用户创作历史的权威记录 |
| Initial State | 地图初始状态 |
| State Change | Command 执行产生的状态变化语义及派生结果 |
| World State | 某个历史时间点的世界状态 |
| Dependency | Command 执行依赖，可重建派生信息 |
| Checkpoint | 按 Branch 归属的完整合成 World State 派生缓存（D01-72），用于加速重建，非权威历史；唯一性、完整性校验、完成标记与 MD5、保存内容等专题规则见第 18 章（D01-101~143） |
| Calendar Configuration | 日历规则配置 |
| Calendar Reform Command | 历史上的日历改革行为 |
| Order Constraint | Command 之间的显式顺序约束 |
| Shared Object | 表达共享对象身份及共享基础数据；共享身份不等于跨 Branch 共享运行时修改结果（D01-70） |
| Branch | 动态继承父地图截至分叉点的有效历史结果、只保存自有 Command 的创作分支，不是创建时冻结的历史副本（D01-71） |
| Combination Map | 通过历史路径固化（History Path Materialization，D01-74）形成的独立地图：父地图截至分叉点最新有效历史 + 分支分叉点后自有历史 |

## 12.2 历史重建工作流程

阶段性工作流程：

1. 用户创建或修改 Command。
2. 用户可以连续修改多个 Command。
3. 用户主动点击重新播放 / 重建。
4. 系统确定重建起点。
5. 复用仍然有效的缓存或 Checkpoint。
6. 按历史时间和顺序约束执行 Command。
7. 遇到第一个无法执行的 Command，立即停止。
8. 展示错误、原因及必要的依赖信息。
9. 用户修改设计。
10. 用户再次主动重建。
11. 全部 Command 成功后，生成完整 World State。
12. 保存可重建的缓存和 Checkpoint。

## 12.3 播放规则

- 只能播放当前创作内容已经成功重建的历史结果。
- 有未重建修改时，暂停播放。
- 有历史错误时，不能越过错误播放后续历史。
- 用户可以拖动播放条选择历史时间点。
- 播放起点和重建起点是两个不同概念。
- 播放结果必须与当前创作内容一致。

## 12.4 错误处理规则

采用简单的 Fail-Fast 方式。

- 遇到第一个错误立即停止后续重建。
- 不继续收集后续错误。
- 不建立复杂的并行错误报告体系。
- 不自动修改 Command。
- 不自动回滚用户修改。
- 提供针对失败 Command 的单项修复建议。
- 由用户决定是否采用修复建议。

## 12.5 后续审查补充（2026-11-19，D01-70~75）

以下四点为第 16 章裁决在本章的对应更新，细节以第 16 章为准：

1. **Shared Object**：共享对象身份，不等于跨 Branch 共享运行时修改结果；对 Shared Object 的局部修改属于当前 Branch 自己的 Command，不改变 Shared History（D01-70）。
2. **Branch**：动态继承模型——继承父地图截至分叉点（≤分叉时刻）的有效历史结果，只保存自有 Command；祖先分叉点及之前（≤）的 Command 后续新增或修改自动传播，分叉点之后（>）的新增或修改不影响（D01-71，V0.3 闭式边界）。
3. **Checkpoint**：按 Branch 归属，保存完整合成 World State（祖先继承状态 + Shared Object 在该 Branch 的有效状态 + 局部对象 + 自有 Command 执行结果）；祖先修改使受影响 Checkpoint 失效并重新生成（D01-72）。
4. **Combination Map**：整合语义修正为历史路径固化 `C = A_latest(<=1200) + B_own(>1200)`，不再是"继承父地图完整历史，再吸收子地图全部新增历史"（D01-74/75）。

## 12.6 后续讨论补充（2026-11-19，D01-76~100）

以下要点为第 17 章讨论结论在本章的对应更新，细节以第 17 章为准：

1. **重建单位**：用户一次只激活一条 Branch 时间线；按选定 Branch 的继承路径连续执行 Command；Shared Object 在该路径重建中持续接收 Command 影响，不是独立于 Branch Local Command 的权威历史（D01-76）。
2. **活动 Branch 与切换**：同一时刻只有一条活动 World State；切换 Branch 按目标 Branch 的有效 Checkpoint 恢复并继续执行；不存在有效 Checkpoint 时立即按祖先到后代顺序重建（D01-78/95）。
3. **Checkpoint 管理**：逐层复用祖先 Checkpoint；Checkpoint 保存生成时的完整继承路径版本组合，读取或使用前校验；重建任务建立使用引用，引用期间不物理淘汰；逻辑失效与物理淘汰分离；系统自动管理位置与数量，分叉点优先（D01-77/88/89~92）。
4. **失效与重建调度**：祖先历史修改触发受影响 Checkpoint 与路径版本的全局逻辑失效，只立即重建当前活动路径，非活动路径切换时按需重建；同一继承路径祖先到后代顺序执行，独立 Branch 可并行，调度不得改变历史语义（D01-84/94）。其中 D01-94 决定重建任务的触发范围，D01-84 决定已具备重建资格任务的调度方式；并行调度不得绕过 D01-94 主动启动已失效的非活动 Branch（V0.4.1）。
5. **失败处理**：Fail-Fast 约束单条继承路径的重建；严格区分重建失败（可进入受限修复模式）与继承阻断（只读）；一个 Branch 失败只阻断自己的后代；祖先修复后沿继承链恢复活动路径重建（D01-81/82/83/94/97~100）。

## 12.7 后续讨论补充（2026-11-19，D01-101~143）

以下要点为第 18 章 Checkpoint 专题讨论结论在本章的对应更新，细节以第 18 章为准：

1. **基本定位与继承**：Checkpoint 是恢复缓存非权威历史；每个 Branch 每个历史时间点最多一个；按 Branch 归属；后代复用祖先分叉点有效 Checkpoint 后继续执行自有 Command；使用前校验完整继承路径版本（不能只查自身版本）；祖先历史变化沿路径传播失效；活动路径优先重建、非活动按需重建（D01-101~108）。
2. **创建与失败处理**：创建受唯一性约束；同一 Checkpoint 同时只能有一个有效生成任务；生成失败不发布；生成中继承路径版本变化旧任务立即失效；发布前再次完整校验；发布原子完成；不完整数据不可用（D01-109~114）。
3. **数据完整性与损坏**：恢复前必须完整性检查；单个损坏只影响自身、祖先损坏不连带后代失效；活动 Branch 自动恢复、非活动 Branch 只逻辑失效切换时按需重建；不建复杂损坏历史；仅在恢复失败或影响操作时通知（D01-115~122）。
4. **用户触发的全部重建与批量调度**：不能手动删除单个 Checkpoint；可要求全部重新创建（覆盖当前 Branch 及完整祖先继承路径、按祖先到后代顺序执行）；批量重建期间地图级锁定、不得切换 Branch 绕过；支持继续/修复与强制全部两种模式；目标范围启动时固定；进度与错误可查看；失败/取消/再次启动/祖先历史再次变化严格沿用既有裁决（D01-123~137）。
5. **单机应用与重启恢复**：单机应用软件；正常关闭或关机时安全停止重建任务、不要求关机期间继续计算；轻量级任务持久化 + 完成标记；启动时检查标记——有标记仍须通过版本与完整性校验，无标记视为未完成需重新创建（D01-138~140）。
6. **完成标记与 MD5**：完成标记只表示写入流程完成、不代替校验；`md5.txt` 记录组成文件与校验值，读取/恢复时重算比较，不一致或缺失即不可用需重建；防意外损坏、非防恶意篡改；与原子发布职责区分（D01-141/142）。
7. **保存内容**：指定 Branch 指定历史时间点的完整合成 World State，足以独立恢复并继续执行后续 Command；不含 Command、State Change、顺序约束、可重算警告/错误、隐式依赖、UI 状态（D01-143）。

# 15. 当前阶段性结论

D01-01 至 D01-75 已形成一套相对完整的讨论方向：

**World View 以 Command 作为权威创作历史，以历史重建得到 World State，以可重建缓存和 Checkpoint 优化性能，以编译器式 Fail-Fast 机制发现设计冲突，并由作者决定如何修复。**

核心边界：

- 作者决定历史。
- Command 记录创作意图。
- State Change 和 World State 是可重建结果。
- 系统检查执行条件。
- 系统发现错误后停止重建。
- 用户修复设计后主动重新重建。
- 系统可以提出单项修复建议，但不能代替作者决定。
- Branch 动态继承父地图历史：继承分叉点及之前（≤分叉时刻）的历史状态，不复制祖先 Command；分叉点之后（>分叉时刻）的父历史新增或修改不影响分支（D01-71）。
- Shared Object 只共享对象身份与基础数据，不等于跨 Branch 共享运行时修改结果（D01-70）。
- 删除后的局部修改规则（持续警告、不自动复活、不阻断）同样适用于 Branch 的动态继承与重新重建（D01-73）。
- 组合地图（Branch 整合）通过历史路径固化形成独立历史：`C = A_latest(≤分叉点) + B_own(>分叉点)`；整合采用 Copy 并换发新 ID、重映射依赖与顺序约束、保留来源追溯；整合后与来源地图相互独立（D01-74/75）。
- 内部历史时间与日历显示分离。
- Branch Checkpoint 按 Branch 归属、保存完整合成 World State，仅是性能优化的派生缓存，不是权威历史（D01-65~69、D01-72）。
- 发布作品与创作工程分离。

**V0.4 增补（D01-76~100）**：后续讨论在上述方向上补充确认：

- 同一时刻只有一条活动 Branch 时间线 / 活动 World State；重建以选定 Branch 的继承路径为单位连续执行 Command，Shared Object 在该路径重建中持续接收 Command 影响，不构成独立的权威历史（D01-76/78）。
- Checkpoint 逐层复用祖先 Checkpoint，仍是完整 World State 的派生缓存；Checkpoint 与重建任务携带完整继承路径版本组合，发布或使用前校验（D01-77/86/87/88）。
- 祖先历史修改触发受影响 Checkpoint 与路径版本的全局逻辑失效，只立即重建当前活动路径，非活动路径切换时按需重建（D01-79/92/94/95）。
- Fail-Fast 约束单条继承路径的重建；重建失败（可进入受限修复模式）与继承阻断（只读）严格区分；一个 Branch 失败只阻断它自己的后代（D01-81/83/100）。
- Command 编辑权限按状态区分：正常 / 正在重建（暂时禁止历史编辑）/ 重建失败（受限修复，仅失败点及之前）/ 继承阻断（只读）/ 修复后重建成功（恢复正常），汇总表见 17.26.2（D01-96~100；重建结果状态汇总见 17.26.1）。
- Checkpoint 由系统自动管理位置与数量（分叉点优先），支持使用引用保护与淘汰；历史有效性与缓存物理生命周期分离（D01-89~92）。

**V0.5 增补（D01-101~143）**：Checkpoint 专题讨论补充确认：

- Checkpoint 是恢复缓存非权威历史：每个 Branch 每个历史时间点最多一个、按 Branch 归属；后代复用祖先分叉点有效 Checkpoint，恢复后继续执行自有 Command；使用前校验完整继承路径版本（不能只查自身版本）；祖先历史变化沿路径传播失效；活动路径优先重建、非活动按需重建（D01-101~108）。
- 创建与发布受唯一性、单一有效生成任务、生成中版本变化即失效、发布前完整校验与原子发布约束；生成失败与不完整数据不得发布或使用（D01-109~114）。
- 数据损坏只影响自身、不沿继承路径连带；祖先损坏不自动使后代失效；活动 Branch 自动恢复、非活动 Branch 逻辑失效后按需重建；不建复杂损坏历史，仅在恢复失败或影响操作时通知（D01-115~122）。
- 用户不能手动删除单个 Checkpoint，可要求重新创建全部 Checkpoint：覆盖当前 Branch 及完整祖先继承路径、按祖先到后代顺序执行；批量重建期间地图级锁定且不得切换 Branch 绕过；支持继续/修复与强制全部两种模式；目标范围启动时固定；进度与错误可查看；失败/取消/再次启动/祖先历史再次变化严格沿用既有裁决（D01-123~137）。
- 单机应用软件：正常关闭或关机时安全停止重建任务、不要求关机期间继续计算；轻量级任务持久化 + 完成标记 + MD5 校验保障完整性，不引入复杂恢复日志（D01-138~142）。
- Checkpoint 保存完整合成 World State（足以独立恢复并继续执行后续 Command），不保存 Command、State Change、顺序约束、可重算警告与隐式依赖、UI 状态；完成标记与 MD5 信息属于完整性管理信息，不属于 World State（D01-143）。

以上均为阶段性讨论结论，状态仍为 Proposed / Discussion（见第 17、18 章）。

**本文档仅作为 D01 讨论阶段的汇总基线。正式冻结前仍需完成整体一致性审查，并由用户明确批准。**

## 16.1 D01-70：Shared Object 与 Branch Local Command 的关系

用户确认：

- Shared Object 表达共享对象身份及共享基础数据。
- Shared Object 不意味着所有地图或 Branch 共享同一份运行时状态。
- 对 Shared Object 的局部修改属于当前 Branch 自己的 Command。
- 该 Command 只在当前 Branch 的历史重建过程中执行。
- 不改变 Shared History，也不直接改变其他 Branch 的历史结果。
- 地图重建时，先取得继承的历史状态，再执行当前 Branch 自己的 Command。
- 不使用简单的地图局部属性覆盖值来表达这种历史操作。

核心原则：

**共享对象身份，不等于跨 Branch 共享运行时修改结果。**

## 16.2 D01-71：Branch 动态继承模型

用户确认，假设 Branch B 从 Branch A 的 1200 年分叉：

1. B 继承 A 截至 1200 年（≤1200）的有效历史结果。
2. B 不复制 A 的祖先 Command。
3. B 只保存自己的 Command。
4. B 重建时，先取得 A 在 1200 年的最新有效状态，再执行 B 自己的 Command。
5. A 在 1200 年之后（>1200）新增的 Command 不影响 B。
6. A 在 1200 年及之前（≤1200）的 Command，其后续新增或修改，均影响 B 的继承状态：B 自动继承修改后的结果，并重新计算自己的历史。
7. B 自有 Command 不会因为祖先历史变化而被自动修改。
8. 如果祖先历史修改导致 B 自有 Command 无法执行，系统报告问题，不擅自修改 B 的 Command。

边界澄清（2026-11-19 用户裁决，采用闭区间方案 A）：

- A 在恰好 1200 年的 Command **属于继承范围**：继承边界为 ≤1200（闭式），不得理解为严格早于 1200 年（<1200）。
- A 在 1200 年之后（>1200）的历史变化（新增或修改）不传播到 B。
- 本条是父地图到分支的**单方向动态继承**，不是 Git 式合并，不是 Command 复制，也不是双向同步。

核心原则：

**Branch 是动态继承的创作分支，不是创建时冻结的历史副本。**

## 16.3 D01-72：Branch Checkpoint 归属与保存范围

用户确认：

- Checkpoint 按 Branch 归属。
- 每个 Branch 的 Checkpoint 保存该 Branch 在指定历史时间点的完整合成 World State。
- 包括祖先历史继承状态、Shared Object 在该 Branch 中的有效状态、Branch 局部对象及自有 Command 的执行结果。
- 恢复 Checkpoint 时可以直接恢复完整状态，不必重新合成全部祖先历史。
- Checkpoint 是派生缓存，不是权威历史。
- 祖先历史修改影响后代 Branch 时，相关 Checkpoint 必须失效并重新生成。
- 不同 Branch 的 Checkpoint 不得混淆归属。

与 D01-65 至 D01-69 保持一致：Checkpoint 不成为第二套权威历史。

## 16.4 D01-73：删除对象后的局部修改规则适用于 Branch

用户确认，此前已经裁决的删除后局部修改规则同样适用于 Branch 动态继承和重新重建。

示例：

- A 在 1150 年删除共享 POI「王都」。
- B 从 A 的 1200 年分叉。
- B 在 1250 年有针对「王都」的局部修改 Command。

处理规则：

1. B 的局部 Command 保留。
2. 系统产生持续警告，说明对象已删除却又被修改。
3. 不得自动复活王都。
4. 该异常不阻断 Command 执行流程。
5. 祖先历史发生变化、Branch 动态继承或重新重建时，仍需重新检查。
6. 只有异常条件真正解除后，警告才标记为已解决，不删除历史记录。

特别强调：

**允许 Command 执行，不代表已删除对象可以被隐式复活。**

## 16.5 D01-74：地图整合采用历史路径固化

用户对原 D01-29 至 D01-36 的地图整合语义进行了进一步澄清。

**修正声明**：D01-29 原先"继承父地图完整历史，再吸收子地图全部新增历史"的描述不再是当前整合语义（第 6 章原文保留并已标注）；当前采用本条确认的分叉时间边界和历史路径固化模型。D01-30 至 D01-36 的逐项衔接说明见 D01-75（V0.3 补全）。

假设：A 是父地图；B 从 A 的 1200 年分叉；整合时生成独立地图 C。

用户确认的整合规则：

1. 采用整合当时 A 最新的、截至 1200 年的有效历史。
2. 使用该历史重建 1200 年的分叉状态。
3. 接入 B 在 1200 年之后的自有 Command 历史。
4. 不接入 A 在 1200 年之后的 Command。
5. 1200 年至 B 第一条 Command 之前，保持 1200 年的继承状态，不执行 A 的后续 Command。
6. C 是独立地图，不再动态继承 A 或 B。
7. C 后续修改不影响 A、B；A、B 后续修改也不影响 C。
8. 保留来源地图及来源 Command 的追溯信息。

核心公式：

`C = A_latest(<=1200) + B_own(>1200)`

整合边界必须明确：

- A 在 1200 年及之前的历史纳入 C。
- B 只贡献严格晚于 1200 年的自有历史。
- B 在恰好 1200 年的 Command 不纳入 C。
- A 在恰好 1200 年的 Command 纳入 C。

该操作定义为：

**Branch 历史路径固化（History Path Materialization）**

它不是 Git Merge，也不是把两份完整历史逐条合并。

## 16.6 D01-75：Branch 整合后的独立性

用户确认：

- C 整合完成后拥有独立完整历史。
- C 中 Command 使用新的 ID。
- 显式依赖及顺序约束需要重新映射。
- 保留来源追溯信息。
- 隐式依赖和派生 State Change 需要在 C 中重新发现、验证或重建。
- C 必须独立进行完整历史验证。
- A、B 后续修改不再影响 C。
- C 的修改不影响 A、B。

与原 D01-30 至 D01-36 的逐项衔接（2026-11-19，V0.3 补全；兼容性判断依据各条原文与 D01-70~75 裁决，非机械套用）：

- **D01-30（Copy 而非 Reference）**：继续适用，但仅适用于**整合操作本身**——固化生成的 C 是独立 Copy，不运行时引用 A、B（与 D01-74 规则 6/7、D01-75 一致）。必须区分两个不同操作：**整合 = Copy 历史；分支运行时 = 动态继承历史状态而不复制祖先 Command**（D01-71 规则 2/3）。两者互不否定，不得混为一谈。其示例中"吸收 A 分叉后新增历史"的部分已被 D01-74 修正（第 6 章已标注，不得恢复）。
- **D01-31（整合时自动排序与冲突处理）**：继续适用——整合时自动排序，冲突时警告且不擅改原 Command；结合 Fail-Fast 规则，允许创建 C 不代表其全部历史成功执行（与 D01-75"C 独立进行完整历史验证"一致）。
- **D01-32（来源关系保存、C 不再是 Branch）**：继续适用——C 保存来源地图身份与追溯信息，但不再是 A 或 B 的 Branch、无运行时继承关系（与 D01-74 规则 6/8 一致）。
- **D01-33（Command 新 ID 与来源追溯）**：继续适用——C 中 Command 使用新 ID，记录来源地图 ID 与来源 Command ID；来源 ID 仅用于追溯，不构成运行时依赖（与 D01-75 一致）。
- **D01-34（顺序约束 ID 重映射）**：继续适用——顺序约束生成新 ID 并重映射到 C 的新 Command ID，保存来源约束 ID 供追溯（与 D01-75"显式依赖及顺序约束需要重新映射"一致）。
- **D01-35（仅复制显式依赖）**：继续适用——隐式依赖是可重建派生信息，不直接复制，在 C 中重新发现与验证（与 D01-75"隐式依赖和派生 State Change 需要在 C 中重新发现、验证或重建"一致）。
- **D01-36（执行依据复制边界）**：继续适用——用户明确指定的参数和执行依据随 Command 复制；自动计算路线、隐式依赖、阶段性 State Change 等系统自动计算内容不作为权威数据直接复制；C 需重新验证执行条件，原依据不再成立时产生警告且不擅改用户指定内容。

以上各条均未被 D01-70~75 替代。被后续裁决修正的只有 D01-29 的历史范围语义（及 D01-30 示例中相应的整合范围表述），不得恢复旧规则。整合不是 Git 式 Merge。

## 17.1 D01-76：Shared Object 与 Branch 历史重建关系

阶段性选择：C（分层重建与时间约束结合）。

**后续澄清（用户确认，与选择 C 共同构成本条完整裁决）：**

- 用户一次只激活一条 Branch 时间线。
- Shared Object 不应被理解为一套独立于 Branch Local Command 的权威历史。
- 应按选定 Branch 的继承路径连续执行 Command。
- Shared Object 在该路径重建过程中持续接收 Command 影响。
- 不同 Branch 中同一个 Shared Object 可以具有不同的运行时状态。

**模型修正声明：** 不得继续按"独立 Shared Object History 与 Branch Local History 两套历史交错合成"的模型理解本条——那是错误模型。正确模型为上述继承路径连续重建模型：Shared Object 不是第三套权威历史，共享对象状态在选定 Branch 的继承路径重建过程中形成。D01-70"共享对象身份，不等于跨 Branch 共享运行时修改结果"的原则不变，并由本条澄清进一步具体化。

核心原则：

**按选定 Branch 的继承路径连续重建；同一个 Shared Object 在不同 Branch 中可以具有不同的运行时状态。**

## 17.2 D01-77（重拟）：Checkpoint 继承与复用

**重拟说明：** 本条为重新拟定（重拟）的议题。此前讨论中的旧 D01-77 议题已被撤回，撤回的旧议题内容不构成裁决、不记录于本文档、不得恢复为有效结论。本条以重拟后的议题为准。

阶段性选择：A（逐层复用祖先 Checkpoint）。

以 A→B→C 继承链为例：

1. A 在 1200 年保存 Checkpoint。
2. B 从 A 的 1200 年继承，在 1500 年保存 Checkpoint。
3. C 重建时，先恢复 A@1200。
4. 执行 B 在 1200—1500 年之间的 Command。
5. 恢复 B@1500 Checkpoint。
6. 再执行 C 自己的 Command。

规则：

- Checkpoint 是完整 World State 的派生缓存，不是权威历史。
- Checkpoint 缺失时可以重新构建。

（衔接说明：与 D01-65~69、D01-72 一致——Checkpoint 仍为按 Branch 归属的派生缓存；祖先 Checkpoint 在后代继承路径重建过程中被复用，不改变其归属，也不使其成为权威历史。示例的精确恢复策略见第 13.7 节第 8 项，本文档未自行补充。）

## 17.3 D01-78：活动 Branch 切换

阶段性选择：A。

- 同一时刻只有一条活动 World State。
- 切换 Branch 时，按目标 Branch 的有效 Checkpoint 恢复。
- 从最近有效 Checkpoint 继续执行。
- 其他 Branch 的 Checkpoint 可以保留，但不作为当前活动状态。

## 17.4 D01-79：祖先修改后的 Checkpoint 失效传播

阶段性选择：A。

- 祖先历史修改后，失效所有受影响的祖先及后代 Checkpoint。
- 沿继承路径检查受影响后代。
- 不受影响的历史区间与 Checkpoint 可以保留。
- 后代自己的 Command 不删除、不自动修改。

（衔接说明：与 D01-72"祖先历史修改使受影响 Checkpoint 失效并重新生成"一致；本条补充传播范围与保留边界。失效判定的版本机制见 D01-86~88。）

## 17.5 D01-80：祖先修改导致后代 Command 执行失败

阶段性选择：A。

- 保留后代 Command。
- 重建在失败点停止。
- 报告失败 Command、时间、祖先历史变化及原因。
- 不自动寻找替代路线，不自动补建对象，不修改后代 Command。

（衔接说明：与 D01-71 第 8 条、D01-09 一致，并延续 D01-05"不自动寻找替代方案、不擅自修改 Command"的原则；Fail-Fast 适用。）

## 17.6 D01-81：重建失败与继承阻断的区别

阶段性选择：A。

必须区分：

- **重建失败**：Branch 自己的 Command 执行失败，重建在失败点停止。
- **继承阻断**：Branch 无法取得有效祖先继承状态。

配套规则：

- 祖先修改后，受影响后代标记为待重建。
- 不得使用失效的旧 Checkpoint 作为当前有效状态。
- 祖先修复后沿继承链恢复重建。

## 17.7 D01-82：祖先修复后的自动恢复

阶段性选择：A。

- 先重建发生修改的祖先 Branch。
- 祖先重建成功后自动检查直接后代。
- 后代继承起点有效则启动重建。
- 成功后继续向下传播。
- 后代自身失败则其后代进入继承阻断。

**范围说明（V0.4，衔接 D01-94；V0.4.1 更新交叉引用）：** 本条确立祖先修复后自动恢复沿继承链向下传播的机制；其"立即重建"的执行范围由后续 D01-94 限定为用户当前活动路径，非活动路径切换时按需重建（见 17.19）。两条须合并理解，不得将本条单独解读为"所有后代无论是否活动都立即自动重建"。合并理解的规则关系已经明确（V0.4.1，见第 13.7 节第 7 项）：**自动传播检查机制与实际重建任务的启动范围是两个不同概念**——本条的自动检查与传播沿继承链进行，实际重建任务只对当前活动路径上的后代自动启动，非活动 Branch 保持待重建状态、切换时按需重建；具体任务调度实现仍待技术设计。

## 17.8 D01-83：失败 Branch 对其他 Branch 的影响范围

阶段性选择：A。

- 一个 Branch 失败，只阻断它自己的后代。
- 不影响其他独立 Branch。
- Fail-Fast 约束单条历史重建路径，而不是整个 Branch 树。

## 17.9 D01-84：多 Branch 重建调度

阶段性选择：C。

- 同一继承路径必须按照祖先到后代顺序执行。
- 独立 Branch 可以并行。
- 系统根据资源、任务数量及缓存情况动态选择并行或串行。
- 调度方式不能改变历史语义，串行与并行结果必须一致。

**范围说明（V0.4.1，衔接 D01-94）：** 本条决定**已经具备重建资格的任务如何调度**，不决定重建任务的触发范围：

- 同一继承路径仍必须按照祖先到后代的顺序执行。
- 独立 Branch 在具备重建资格且任务已被触发的前提下，可以并行或串行。
- 系统根据资源、任务数量及缓存情况动态决定调度方式。
- 并行或串行不得改变历史语义，结果必须一致。

**特别强调：本条的并行调度能力，不意味着系统可以绕过 D01-94，主动启动所有已经失效的非活动 Branch。** 重建任务的触发范围由 D01-94 决定（见 17.19）。

## 17.10 D01-85：重建期间祖先 Command 再次修改

阶段性选择：A。

- 旧重建任务立即失效。
- 不允许旧任务发布结果。
- 系统尽快终止不再需要的计算。
- 使用最新历史重新重建。
- 不受影响的独立 Branch 任务可以继续。
- 即使旧任务已经完成计算，只要尚未完成最终版本校验和发布，也必须作废。

## 17.11 D01-86：Branch 继承路径版本

阶段性选择：C。

- 按继承路径维护版本。
- Branch 自己或祖先历史改变，只更新受影响路径版本。
- 不相关独立 Branch 不更新版本。
- 重建任务记录对应路径版本。

## 17.12 D01-87：重建任务版本校验

阶段性选择：C。

- 主动传播版本失效。
- 任务启动时记录完整继承路径版本组合。
- 发布前再次校验完整版本组合。
- 任一相关版本发生变化，旧结果不得发布。
- 最终校验作为主动失效机制的补充防线。

## 17.13 D01-88：Checkpoint 版本有效性

阶段性选择：C。

- Checkpoint 保存生成时完整继承路径版本组合。
- 祖先修改后主动识别并使相关 Checkpoint 失效。
- 读取或使用前再次校验路径版本。
- 不匹配时不得用于恢复当前 World State。
- 不受影响的 Checkpoint 可以继续复用。

## 17.14 D01-89：Checkpoint 数量和保存位置

阶段性选择：A。

- 系统自动管理 Checkpoint 的保存位置与数量。
- 分叉点优先作为候选位置。
- 根据重建成本、访问频率、缓存空间等决定其他保存位置。
- 可以淘汰 Checkpoint。
- 缺失时从有效祖先 Checkpoint 或初始状态重建。

## 17.15 D01-90：祖先 Checkpoint 淘汰策略

阶段性选择：A。

- 允许淘汰祖先 Checkpoint。
- 不因为存在后代就永久保护。
- 多个活跃后代依赖时提高保留优先级。
- 综合后代活跃程度、访问频率、重建成本及缓存空间。
- 淘汰不影响历史权威性。

## 17.16 D01-91：正在使用的 Checkpoint

阶段性选择：A。

- 重建任务读取 Checkpoint 时建立使用引用。
- 有引用期间不能物理淘汰。
- 任务完成、取消或失败后释放引用。
- 所有引用释放后重新评估淘汰。
- 必须处理异常终止，避免引用泄漏。

## 17.17 D01-92：Checkpoint 逻辑失效与物理淘汰

阶段性选择：A。

- 祖先修改后立即逻辑失效。
- 即使仍有任务引用，也不得继续作为有效结果使用。
- 有引用时物理数据暂留。
- 任务取消或停止并释放引用后，再进行物理淘汰。
- 历史有效性与缓存物理生命周期分离。

**衔接说明（V0.4；V0.4.1 更新规则关系表达）：** 第 10 章 D01-68 规定失效 Checkpoint"立即删除、不保留"，确立于无并发重建任务的场景；本条在存在重建任务引用的场景将物理删除时点延后至引用释放。两条规则的共同不变量完全一致：**失效 Checkpoint 在任何场景下都不得作为有效结果使用。** 两条按 Checkpoint 生命周期不同阶段统一理解，规则关系已经明确（见第 13.7 节第 5 项）：失效即立即逻辑失效，不得用于恢复当前 World State；没有任务引用时立即物理淘汰；仍有任务引用时暂缓物理删除，所有引用释放后物理淘汰；物理数据暂时存在不代表 Checkpoint 仍然有效。具体引用计数、引用释放及异常恢复机制仍待技术设计。本条与 D01-68 原文均未被改写。

## 17.18 D01-93：旧重建任务撤销

阶段性选择：A。

- 旧任务立即失去有效执行资格。
- 不允许发布结果。
- 系统发出取消信号，尽快终止计算。
- 底层无法立即终止时允许短暂清理，但结果必须丢弃。
- 释放 Checkpoint 引用及其他运行资源。

## 17.19 D01-94：全局失效、活动路径优先重建

**条目性质说明：** 本条不是 A/B/C 选择题，而是用户补充并确认的完整机制。

场景：用户当前正在 C Branch，继承路径为 A→B→C，同时存在 A→B→D 或 A→B→C→E 等其他 Branch。

如果 A 的祖先历史发生改变：

1. 立即使所有受影响 Branch 的 Checkpoint 逻辑失效。
2. 只立即重建用户当前活动路径 A→B→C。
3. 非活动 Branch（例如 D、E）不立即重建。
4. 用户切换到 D 或 E 时，才启动目标路径重建。
5. 物理淘汰仍遵守 D01-91、D01-92 的引用保护规则。

核心概括：

**全局失效，活动路径优先重建，非活动路径按需重建。**

**范围说明（V0.4；V0.4.1 更新交叉引用）：** 本条将 D01-82 自动恢复传播的"立即重建"范围限定为当前活动路径。D01-82 与本条按"自动传播检查机制"与"实际重建任务启动范围"两个不同概念合并理解，规则关系已经明确（见 17.7 与第 13.7 节第 7 项）；具体任务调度实现仍待技术设计。

**与 D01-84 的边界（V0.4.1）：** 本条决定重建任务的**触发范围**：

- 祖先历史修改后，所有受影响 Branch 的 Checkpoint 立即逻辑失效。
- 只立即触发当前活动路径的重建。
- 非活动 Branch 不主动启动重建，切换时才按需重建。

已经具备重建资格的任务如何调度由 D01-84 决定（见 17.9）。**D01-84 的并行调度能力，不意味着系统可以绕过本条，主动启动所有已经失效的非活动 Branch。**

## 17.20 D01-95：切换到非活动 Branch

阶段性选择：A。

- 切换后目标 Branch 成为唯一活动 Branch。
- 如果存在有效 Checkpoint，直接恢复。
- 如果不存在有效 Checkpoint，立即启动目标路径重建。
- 按祖先到后代顺序执行。
- 失败时遵守 Fail-Fast 与继承阻断规则。
- 不得将旧 Checkpoint 对应状态作为当前有效状态展示。

## 17.21 D01-96：活动 Branch 重建期间的编辑权限

阶段性选择：A。

- 活动 Branch 正在重建时进入临时重建锁定状态。
- 禁止新增、修改、删除、移动 Command 等历史编辑操作。
- 用户可以查看重建进度和浏览其他页面。
- 重建成功后解除锁定，恢复正常编辑。
- 重建失败后解除计算锁定，进入失败处理阶段。

**阶段区分说明：** 重建执行期间的编辑锁定（本条），与重建失败后的修复权限（D01-97~100）是两个不同阶段，不得混淆。

## 17.22 D01-97：重建失败后的修复模式

阶段性选择：A。

- 允许用户进入修复模式。
- 用户可以查看第一个错误及相关 Command。
- 可以修改、删除、调整自己的 Command。
- 每次修复保存后，根据最新历史触发重建。
- 再次失败时仍按 Fail-Fast 报告第一个错误。
- 不自动修改祖先或其他后代 Branch 的 Command。

（衔接说明：修复模式下"每次修复保存即触发重建"是重建失败状态的确认流程；正常状态下的"连续修改、用户主动触发重建"规则（D01-62）继续适用，状态边界见 17.26.1/17.26.2 与第 13.7 节第 6 项。）

## 17.23 D01-98：失败点之前的 Command 修改范围

阶段性选择：A。

- 允许修改失败 Command 本身。
- 允许修改失败时间点之前的任意 Command。
- 允许删除或调整相关 Command。
- 每次修复保存后重新检查和重建。
- 在历史恢复有效之前，不允许修改失败点之后的 Command。
- 如果修复后错误位置发生变化，以最新重建报告的第一个错误为准。

## 17.24 D01-99：修复期间失败点之后的 Command 编辑权限

阶段性选择：A。

- 严格禁止修改失败点之后的 Command。
- 必须先修复失败点及之前的历史。
- Branch 重建成功、历史恢复有效后，才能继续修改失败点之后的 Command。
- 不采用草稿或待验证 Command 作为绕过限制的方式。

## 17.25 D01-100：继承阻断期间后代 Branch 的修复权限

阶段性选择：A。

场景：

- A 的历史修改导致 B 重建失败。
- C 继承 B，因此无法取得有效继承状态。
- C 自己的 Command 可能没有执行错误。

用户确认：

- C 应保持继承阻断状态。
- C 只允许查看，不允许进入修复模式。
- 不允许修改 C 自己的 Command。
- 必须先修复 B，使 B 恢复有效状态。
- 之后 C 才能恢复正常重建流程。

必须明确区分：

**重建失败**：当前 Branch 自己的 Command 执行失败，可以进入受限修复模式。

**继承阻断**：当前 Branch 无法取得有效祖先状态，只能查看，不能修复自己的 Command。

## 17.26 状态与编辑权限规则总结（D01-64、D01-96~100 确认规则汇总）

本节为已确认规则的汇总，便于后续讨论引用。**本节是已确认规则的汇总，不是新的状态机设计，不得据此擅自推导或补充尚未讨论的其他状态转换、状态名称或权限规则。**

**V0.4.1 整理说明：** 原表将重建结果状态与 Branch 编辑权限混合在同一列中。两者是不同维度——D01-64 明确重建结果状态（未重建 / 重建失败 / 重建成功），D01-96~100 讨论 Branch 当前所处的操作阶段及 Command 编辑权限。现拆分为 17.26.1 与 17.26.2 两个独立部分。本次仅为按维度整理既有规则的表达，不是重新设计状态机，未新增状态转换、状态名称或权限规则。

### 17.26.1 重建结果状态

D01-64 已确认三种重建结果状态，覆盖"当前历史是否完成有效重建"维度：

| 重建结果状态 | 含义 |
|---|---|
| 未重建 | 当前历史尚未完成有效重建 |
| 重建失败 | 重建过程中发生错误，未得到有效完整结果 |
| 重建成功 | 当前历史已完成有效重建 |

（D01-64 原文见 9.7，未改动；本表为其汇总表达，语义一致。不得在这里新增重建状态。）

### 17.26.2 Branch 编辑权限与操作阶段

D01-96 至 D01-100 已确认 Branch 当前所处的操作阶段及对应 Command 编辑权限，覆盖与 17.26.1 不同的维度：

| Branch 操作阶段 | Command 编辑权限 |
|---|---|
| 正常编辑 | 按正常规则编辑 |
| 正在重建 | 暂时禁止历史编辑 |
| 自身重建失败 | 进入受限修复模式，只能修改失败点及之前的 Command |
| 继承阻断 | 只允许查看，不允许修改自己的 Command |
| 修复后重建成功 | 恢复正常编辑权限 |

补充边界（原有，全部保留）：

- 失败点之后的 Command 在重建失败期间禁止修改（D01-99）。
- 继承阻断期间，后代 Branch 连受限修复权限也没有（D01-100）。
- 重建执行期间的编辑锁定与重建失败后的修复权限是两个不同阶段（D01-96）。
- 修复模式下每次保存后触发重新检查和重建（D01-97/98）。
- 不得利用草稿或待验证 Command 绕过失败点之后的编辑限制（D01-99）。

两个维度的关系：17.26.1（D01-64）覆盖重建验证维度，17.26.2（D01-96~100）覆盖 Branch 活动与 Command 编辑权限维度；两表并行使用，不得互相混用，也不得据以推导新状态。

## 18.1 D01-101：Checkpoint 基本定位

用户确认：

- Checkpoint 是 World State 的恢复缓存，不是权威历史。
- Command 仍是唯一权威历史数据；Checkpoint 丢失不影响历史数据完整性，可以重新生成。

（衔接说明：与 D01-65/66、D01-72 一致，本轮在 Checkpoint 专题下再次确认该定位；本章全部规则均以该定位为前提。）

## 18.2 D01-102：Checkpoint 唯一性

用户确认：

- 每个 Branch 在每个历史时间点最多有一个 Checkpoint。
- 不存在同一 Branch 同一历史时间点的多份 Checkpoint。

（衔接说明：唯一性是生成任务管理（D01-110）与发布规则（D01-114）的前提约束。）

## 18.3 D01-103：Checkpoint 按 Branch 归属

用户确认：

- Checkpoint 按 Branch 归属。
- 不同 Branch 的 Checkpoint 不得混淆归属。

（衔接说明：与 D01-72 一致。）

## 18.4 D01-104：后代复用祖先分叉点 Checkpoint

用户确认：

- 后代 Branch 可以复用祖先在分叉点的有效 Checkpoint。
- 复用的前提是该 Checkpoint 通过完整继承路径版本校验（D01-106）。

（衔接说明：与 D01-77"逐层复用祖先 Checkpoint"一致，并将其落实为分叉点 Checkpoint 复用规则；不改变 D01-77 原文与示例。）

## 18.5 D01-105：恢复后继续执行自有 Command

用户确认：

- 从 Checkpoint 恢复后，继续执行当前 Branch 自有的 Command。
- Checkpoint 恢复不改变 Command 权威数据，也不改变历史重建语义。

（衔接说明：与 D01-76"按选定 Branch 的继承路径连续执行 Command"、D01-71 动态继承一致。）

## 18.6 D01-106：完整继承路径版本校验

用户确认：

- 使用或恢复 Checkpoint 前，必须检查完整继承路径版本。
- 不能只检查 Checkpoint 自身版本。
- 完整继承路径中任何一环版本不匹配，该 Checkpoint 都不得使用。

（衔接说明：与 D01-88 一致并强化——校验对象是完整继承路径版本组合，不是 Checkpoint 单点版本。）

## 18.7 D01-107：祖先历史变化的失效传播

用户确认：

- 祖先历史变化时，沿继承路径传播失效。
- 受影响路径上的 Checkpoint 逻辑失效，不得再作为有效状态使用。

（衔接说明：与 D01-79/86/87 一致；失效传播针对"历史变化导致的逻辑失效"，与数据损坏（D01-116/117）是两类不同问题。）

## 18.8 D01-108：活动路径优先重建

用户确认：

- 活动路径优先重建。
- 非活动 Branch 按需重建（用户切换到该 Branch 时才启动）。

（衔接说明：与 D01-94"全局失效，活动路径优先重建，非活动路径按需重建"一致；本章后续损坏处理（D01-118/119）沿用同一原则。）

## 18.9 D01-109：创建的唯一性约束

用户确认：

- Checkpoint 的创建受唯一性约束：同一 Branch 同一历史时间点最多生成一个有效 Checkpoint（D01-102）。
- 生成任务的产出不得突破该唯一性约束。

（衔接说明：本条为创建规则的前提，与 D01-102 配套。）

## 18.10 D01-110：同一 Checkpoint 单一有效生成任务

用户确认：

- 同一 Checkpoint 同时只能有一个有效生成任务。
- 不允许两个任务同时生成同一份 Checkpoint。

（衔接说明：与 D01-85"重建期间祖先 Command 再次修改时旧任务立即失效"配套——旧任务失效并释放后，该 Checkpoint 位置才可被新任务使用；任务终止与资源释放见 D01-93。）

## 18.11 D01-111：生成失败不发布

用户确认：

- Checkpoint 生成失败时，不能发布有效 Checkpoint。
- 失败任务不得输出任何可被后续恢复使用的 Checkpoint 数据。

（衔接说明：与 D01-92 的共同不变量一致——未成功生成或已失效的数据都不得作为有效结果使用。）

## 18.12 D01-112：生成中版本变化即失效

用户确认：

- 生成过程中继承路径版本发生变化，旧生成任务立即失效。
- 失效任务不允许发布结果。

（衔接说明：与 D01-85/87/93 一致，将"旧任务立即失效"规则落实到 Checkpoint 生成任务。）

## 18.13 D01-113：发布前完整版本校验

用户确认：

- Checkpoint 发布前，再次检查完整继承路径版本。
- 版本不匹配时不得发布。

（衔接说明：与 D01-87"发布前再次校验完整版本组合"一致，落实到 Checkpoint 发布环节；最终校验是主动失效机制的补充防线（D01-87）。）

## 18.14 D01-114：原子发布与不完整数据

用户确认：

- Checkpoint 发布必须原子完成。
- 不完整数据不能作为有效 Checkpoint 使用。

（衔接说明：原子发布指发布过程的完整性——要么完整发布、要么不发布，不产生"半份"可见 Checkpoint。它与完成标记（D01-141，写入流程完成标志）、MD5 校验（D01-142，数据完整性检测）职责不同，不得混淆。恢复时的数据完整性检查见 D01-115。）

## 18.15 D01-115：恢复前完整性检查

用户确认：

- 恢复 Checkpoint 前，必须检查数据完整性。
- 完整性检查未通过的 Checkpoint 不得用于恢复。

（衔接说明：完整性检查的手段见 D01-140（完成标记检查）与 D01-142（MD5 校验）。）

## 18.16 D01-116：单个损坏只影响自身

用户确认：

- 单个 Checkpoint 损坏只影响自身，不自动连带失效其他 Checkpoint。
- 数据损坏不触发沿继承路径的失效传播。

（衔接说明：必须与历史变化导致的失效传播（D01-79/107）区分：失效传播针对"历史变化使缓存对应版本不再有效"；损坏是单个缓存数据自身的问题，不改变其他 Checkpoint 对应历史区间的有效性。）

## 18.17 D01-117：祖先损坏不连带后代失效

用户确认：

- 祖先 Checkpoint 损坏，不自动导致后代 Checkpoint 失效。
- 后代 Checkpoint 自身数据与版本校验仍然有效时，可继续使用。

（衔接说明：需要祖先状态而祖先 Checkpoint 不可用时，按既有重建规则处理——D01-89：从有效祖先 Checkpoint 或初始状态重建。）

## 18.18 D01-118：活动 Branch 损坏自动恢复

用户确认：

- 活动 Branch 的 Checkpoint 损坏后，系统自动恢复（自动重建该 Checkpoint）。
- 自动恢复不改变 Command 权威数据，也不等同于用户修改历史后的重建流程。

（衔接说明：与 D01-62 不冲突——D01-62 约束"用户修改 Command 后由用户主动触发重建"；损坏自动恢复是缓存自愈，不涉及任何用户修改。活动路径优先原则与 D01-94/108 一致。）

## 18.19 D01-119：非活动 Branch 损坏按需处理

用户确认：

- 非活动 Branch 的 Checkpoint 损坏后，只做逻辑失效，不立即重建。
- 用户切换到该 Branch 时，按需启动重建。

（衔接说明：与 D01-94/95 一致——全局失效、活动路径优先重建、非活动路径按需重建。）

## 18.20 D01-120：不建复杂损坏历史记录

用户确认：

- 不额外建立复杂的损坏历史记录。
- 损坏检测服务于恢复可靠性，不扩展为审计或历史追踪功能。

（衔接说明：与 D01-59"不引入复杂的多错误报告体系"的简化原则精神一致。）

## 18.21 D01-121：通知时机

用户确认：

- 只有当损坏导致恢复失败，或影响用户操作时，才需要通知用户。
- 不为每次损坏检测单独打扰用户。

（衔接说明：与 D01-07 警告规则精神一致——诊断服务于用户需要处理的问题；被自动恢复覆盖的损坏（D01-118）不需通知。）

## 18.22 D01-122：损坏处理小结

用户确认（本条为 D01-115~121 已确认规则的小结性归纳，未引入新机制）：

- Checkpoint 不可用有两类原因：历史失效（逻辑失效，沿继承路径传播，D01-107）与数据损坏（单个发生、不传播，D01-116/117）。
- 两类的处理路径一致：不可用即不得用于恢复；损坏 Checkpoint 的恢复手段是重新创建（活动 Branch 自动恢复，非活动 Branch 按需重建）。
- 损坏与失效都不影响 Command 权威历史，都不改变历史语义。

（衔接说明："需要重新创建"与 D01-141/142 校验失败的处理一致。）

## 18.23 D01-123：不提供单个 Checkpoint 的手动删除

用户确认：

- 用户不能手动删除单个 Checkpoint。
- Checkpoint 的保留与淘汰由系统按既有规则自动管理（D01-89/90），不提供用户手动删除单个 Checkpoint 的操作。

（衔接说明：与 D01-67"由系统自动决定 Checkpoint 位置、不要求用户手动管理"一致。）

## 18.24 D01-124：用户可要求重新创建全部 Checkpoint

用户确认：

- 用户可以要求重新创建全部 Checkpoint。

（衔接说明：与 D01-123 相对——不提供单个删除操作，但提供全部重新创建的入口；批量任务的范围、顺序与锁定见 D01-125~127。）

## 18.25 D01-125：全部重建的覆盖范围

用户确认：

- 全部重新创建覆盖当前 Branch 及完整祖先继承路径。
- 目标范围在任务启动时确定并固定（D01-135）。

（衔接说明：与 D01-77/104 的继承复用结构一致——祖先路径是当前 Branch 重建的依赖基础。）

## 18.26 D01-126：祖先到后代顺序执行

用户确认：

- 批量重建按祖先到后代顺序执行。

（衔接说明：与 D01-84 一致——同一继承路径必须按照祖先到后代顺序执行；本条将其落实到批量重建任务。）

## 18.27 D01-127：批量重建期间的地图级锁定

用户确认：

- 批量重建期间，地图不可操作。
- 该锁定是地图级锁定：批量重建任务执行期间，整个地图进入锁定状态。

（衔接说明：D01-96 的重建锁定针对活动 Branch 的单次重建；本条适用于批量重建场景，锁定范围提升为地图级。两条是不同场景的锁定，互不否定。）

## 18.28 D01-128：批量重建模式一：继续/修复重建

用户确认：

- 支持"继续/修复重建"模式：保留已成功生成的 Checkpoint，从失败或中断位置继续按序重建。

（衔接说明：与 D01-60"尽可能复用此前成功的结果"的原则一致。）

## 18.29 D01-129：批量重建模式二：强制全部重建

用户确认：

- 支持"强制全部重建"模式：对目标范围内全部 Checkpoint 重新生成，不依赖既有 Checkpoint。
- 强制全部重建同样按祖先到后代顺序执行（D01-126），同样受地图级锁定约束（D01-127）。

## 18.30 D01-130：两种模式的边界

用户确认：

- 继续/修复重建与强制全部重建是批量重建任务的两种模式。
- 两种模式都不改变重建的目标范围（D01-125）、祖先到后代顺序（D01-126）与地图级锁定（D01-127），都不改变历史语义。

（衔接说明：模式选择的交互方式未在本轮单独裁决，列入第 13.8 节待技术设计。）

## 18.31 D01-131：批量重建失败的处理

用户确认：

- 批量重建过程中出现失败时，严格沿用已确认裁决：Fail-Fast 停止（D01-58/59）、报告第一个错误及原因（D01-55/58）、失败 Branch 进入受限修复模式、其后代进入继承阻断（D01-81/100）。
- 不因批量场景引入新的失败处理机制。

## 18.32 D01-132：批量任务取消

用户确认：

- 用户可以取消批量重建任务。
- 取消严格沿用 D01-93：任务立即失去有效执行资格、不允许发布结果、发出取消信号尽快终止计算、释放 Checkpoint 引用及其他运行资源。

## 18.33 D01-133：批量任务再次启动

用户确认：

- 批量重建失败或取消后，用户可以再次启动批量重建。
- 再次启动严格沿用已确认裁决：由用户主动触发（D01-62 的主动重建原则），启动时重新确定并固定目标范围（D01-135），按所选模式执行（D01-128~130）。

## 18.34 D01-134：批量重建期间祖先历史再次变化

用户确认：

- 批量重建期间祖先历史再次变化时，严格沿用已确认裁决：旧重建任务立即失效、不允许发布结果（D01-85）；发布前完整版本校验不通过即不得发布（D01-87/113）；失效沿继承路径传播（D01-94/107）。
- 已失效的批量任务不得发布任何结果。

## 18.35 D01-135：批量任务目标范围启动时固定

用户确认：

- 批量重建任务的目标范围在启动时固定。
- 任务执行过程中目标范围不变；祖先历史再次变化按 D01-134 处理（任务失效，而非扩大或改写目标范围）。

## 18.36 D01-136：不得通过切换 Branch 绕过锁定

用户确认：

- 批量重建锁定期间，不允许通过切换到其他 Branch 绕过地图级锁定。
- 该规则不改变正常状态下的 Branch 切换规则（D01-78/95）；锁定解除后，切换规则照常适用。

## 18.37 D01-137：批量任务进度与错误可查看

用户确认：

- 批量重建期间，任务进度、错误信息等可以查看。
- 查看是只读的，不解除地图级锁定（D01-127）。

（衔接说明：与 D01-96"用户可以查看重建进度"一致。）

## 18.38 D01-138：单机应用定位与关闭行为

用户确认：

- World View 是单机应用软件，不是浏览器应用。
- 正常关闭应用或操作系统关机时，安全停止当前重建任务。
- 不要求关机期间继续计算。

（衔接说明："安全停止"的具体行为（终止计算、不发布部分结果、释放引用）与 D01-93 的取消/终止语义一致；细节待技术设计。）

## 18.39 D01-139：轻量级任务持久化与完成标记

用户确认：

- 使用轻量级任务持久化，不引入复杂的恢复日志。
- 每个 Checkpoint 写入完成后，有特定的完成标记。
- 应用启动时检查完成标记。

（衔接说明：完成标记的职责限定见 D01-141；启动时的校验规则见 D01-140。）

## 18.40 D01-140：启动时的校验规则

用户确认：

- 有完成标记的 Checkpoint，仍须通过继承路径版本校验（D01-106）和数据完整性校验（D01-115），才可作为有效 Checkpoint 使用。
- 没有完成标记的 Checkpoint 视为未完成，需要重新创建。

（衔接说明：完成标记只证明"写入流程已完成"，不证明"仍然有效"——有效性由版本校验与完整性校验决定（D01-141）。）

## 18.41 D01-141：完成标记的职责

用户确认：

- 使用完成标记表示 Checkpoint 写入流程已完成。
- 完成标记不能代替继承路径版本校验和数据完整性校验。

（衔接说明：完成标记、原子发布（D01-114）、MD5 校验（D01-142）职责不同：原子发布保证发布过程不产生半份数据；完成标记标志写入流程结束；MD5 检测组成文件是否意外损坏。）

## 18.42 D01-142：MD5 校验

用户确认：

- 使用 `md5.txt` 记录 Checkpoint 所有组成文件的文件名和 MD5 校验值。
- 读取或恢复 Checkpoint 时，重新计算 MD5 并与 `md5.txt` 比较。
- 校验不一致，或校验文件不存在时，该 Checkpoint 不可用，需要重新创建。
- MD5 用于检测意外数据损坏，不作为防恶意篡改机制。

（衔接说明：与 D01-115 恢复前完整性检查、D01-140 启动校验衔接；校验失败的后续处理与损坏处理规则一致（D01-118/119：活动 Branch 自动恢复、非活动 Branch 按需重建）。）

## 18.43 D01-143：Checkpoint 保存内容与边界

用户确认：

**Checkpoint 保存：**

指定 Branch 在指定历史时间点的完整合成 World State。

保存内容必须足以独立恢复该时间点的世界状态，并继续执行后续 Command。

至少包括：

- 地形、地貌等地图状态。
- POI 的身份、位置和当前属性。
- 人物及其他世界对象的当前状态。
- 国境线及区域状态。
- 道路、桥梁等基础设施状态。
- 对象之间的关系，例如所属区域、连接关系。
- Shared Object 在当前 Branch 中的有效状态及局部变化。
- 其他影响后续 Command 执行的世界状态。

特别注意：

**B@1500 不是只保存 B 自己修改的部分，而是保存从 A@1200 继承并执行 B 自有 Command 后形成的完整合成 World State。**

**Checkpoint 不保存：**

- Command。
- State Change。
- Command 执行顺序约束。
- 可重新计算的警告和错误信息。
- 可重新发现的隐式依赖信息。
- UI 状态、面板布局、选中状态等。
- 其他不属于 World State 的数据。

完成标记、MD5 校验信息属于 Checkpoint 完整性管理信息，不属于 World State。

（衔接说明：与 D01-69"保存指定历史时间点的完整 World State"、D01-72"完整合成 World State"一致；B@1500 示例与 D01-71/77 的继承链（A→B）一致。不保存清单与第 12.1 节的定位一致：Command 与顺序约束属于创作历史数据而非 World State；警告、错误与隐式依赖是可重建派生信息（D01-11/55）；UI 状态不属于世界状态。完成标记与 MD5 信息是完整性管理信息，同样不属于 World State。）
